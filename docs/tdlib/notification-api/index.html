API уведомлений #

В этой статье описан API уведомлений TDLib, представленный в TDLib 1.4.0.¶

Обзор API уведомлений #

TDLib берёт на себя всё, что связано с обработкой уведомлений (как обычно, за исключением того, каким именно образом они будут показаны пользователю). TDLib определяет, когда уведомления показываются пользователю, когда редактируются и удаляются, гарантирует согласованность уведомлений с состоянием базы данных и сохранение активных уведомлений между перезапусками клиента.¶

Все показываемые пользователю уведомления объединяются в группы уведомлений. Например, уведомления об обычных сообщениях из одного чата принадлежат одной группе уведомлений. Группировка автоматически выполняется TDLib на основе содержимого сообщений и настроек уведомлений пользователя. Сейчас существует 4 различных типа групп уведомлений:¶

  • Группы уведомлений Messages содержат уведомления с обычными непрочитанными сообщениями из чата.
  • Группы уведомлений Mentions содержат уведомления о непрочитанных упоминаниях текущего пользователя, ответах на его сообщения и закреплённых сообщениях в чате.
  • Группы уведомлений SecretChat содержат одно уведомление о создании нового секретного чата.
  • Группы уведомлений Calls содержат уведомления о полученных звонках в чате.

TDLib гарантирует, что число показываемых пользователю в любой момент групп уведомлений ограничено значением параметра notification_group_count_max, а число активных уведомлений, показываемых пользователю в группе уведомлений в любой момент, — значением параметра notification_group_size_max. Когда число групп уведомлений с активными уведомлениями превышает notification_group_count_max, TDLib отправляет обновление, скрывающее все уведомления из самой старой группы. Если впоследствии все уведомления будут скрыты в другой группе, первая группа может быть незаметно возвращена обновлением TDLib. Аналогично, когда число активных уведомлений в группе превышает notification_group_size_max, TDLib отправляет обновление, скрывающее самые старые уведомления в группе. Если впоследствии из группы будут удалены более новые уведомления, старые уведомления могут быть незаметно возвращены обновлением TDLib.¶

Чтобы включить API уведомлений TDLib, необходимо установить параметр notification_group_count_max в положительное значение; чтобы отключить API уведомлений, можно снова изменить значение параметра на 0 или установить для него пустое значение.¶

Каждая группа уведомлений имеет уникальный ID — постоянное небольшое целое число, последовательно назначаемое начиная с 1. Клиенту не следует считать, что тип и другие поля группы неизменны, поскольку TDLib может повторно использовать ID группы уведомлений, когда известно, что эта группа больше никогда не будет использоваться. Каждое уведомление принадлежит группе уведомлений и имеет глобально уникальный ID — постоянное небольшое целое число, последовательно назначаемое начиная с 1. ID уведомлений никогда не используются повторно и могут применяться вместе с ID группы уведомлений для однозначной идентификации уведомления. Внутри группы уведомления должны отображаться в порядке, определяемом их ID. Если группировка уведомлений недоступна в операционной системе, существование групп уведомлений можно безопасно игнорировать и обрабатывать уведомления отдельно только по их уникальному ID.¶

Сейчас существует 4 различных вида уведомлений:¶

  • Уведомления NewMessage содержат полную информацию о новом входящем сообщении, полученном от сервера. Они могут находиться в группах уведомлений Messages и Mentions.
  • Уведомления NewPushMessage содержат информацию о новом входящем сообщении, полученном в push-уведомлении. Они содержат лишь частичные данные о сообщении и будут заменены уведомлениями NewMessage, как только клиент загрузит необходимые данные. Они могут находиться в группах уведомлений Messages и Mentions.
  • Уведомления NewSecretChat сообщают о создании нового секретного чата. В каждой группе уведомлений SecretChat будет находиться только одно такое уведомление. Группа может быть повторно использована сразу после удаления уведомления.
  • Уведомления NewCall содержат информацию о новом входящем звонке. Они находятся в группе уведомлений Calls. Группа может быть повторно использована сразу после удаления уведомлений.

Сообщения из уведомлений о новых push-сообщениях не будут показаны в списке сообщений чата, но их идентификаторы известны, и на них всё равно можно отвечать и использовать в вызовах ViewMessages.¶

Обработка обновлений API уведомлений #

API уведомлений добавил 4 новых обновления от TDLib: updateActiveNotifications, updateNotificationGroup, updateNotification и updateHavePendingNotifications.¶

Если API уведомлений включён, при запуске клиент получает обновление updateActiveNotifications, содержащее все уведомления, которые должны быть показаны пользователю. Клиенту необходимо синхронизировать список показываемых пользователю уведомлений со списком, полученным в updateActiveNotifications, и сохранять в памяти информацию обо всех активных уведомлениях, поскольку последующие обновления будут содержать только изменения списка активных уведомлений.¶

Всякий раз, когда уведомление добавляется в группу или удаляется из неё, TDLib отправляет клиенту обновление updateNotificationGroup. Помимо списка добавленных уведомлений и списка идентификаторов удалённых уведомлений, обновление содержит полную информацию о новом типе группы уведомлений, идентификаторе чата, которому теперь принадлежат все уведомления группы, идентификаторе чата, настройки уведомлений которого должны использоваться для показа уведомления, флаге, определяющем, следует ли показывать уведомление со звуком или без него, и новом общем числе непрочитанных уведомлений в группе. Следует учитывать, что общее число непрочитанных уведомлений в группе может быть больше числа активных уведомлений. Также следует учитывать, что старые уведомления могут добавляться через updateNotificationGroup при удалении новых, поэтому клиент должен обеспечивать правильный порядок уведомлений на основе их идентификаторов. Когда возможно, обновления updateNotificationGroup для группы объединяются в одно обновление, поэтому клиент может применить изменения вместе. TDLib также управляет задержкой перед показом уведомлений пользователю, чтобы дать ему возможность прочитать сообщения с другого устройства до показа уведомления; поэтому клиент должен обрабатывать обновления немедленно, без дополнительных задержек.¶

Когда активное уведомление изменяется, TDLib отправляет клиенту обновление updateNotification. Оно содержит новое содержимое уведомления. Клиент должен быть готов обработать смену типа уведомления, например с NewPushMessage на NewMessage.¶

Когда имеются полученные, но отложенные уведомления либо могут существовать ещё не полученные уведомления из-за недоступного сетевого соединения с серверами Telegram, TDLib сообщает об этом клиенту через обновление updateHavePendingNotifications. Предполагается, что клиент будет поддерживать приложение запущенным, чтобы получить все отложенные уведомления. Если поддерживать приложение запущенным невозможно, клиент может закрыть экземпляр TDLib, чтобы немедленно получить все отложенные обновления уведомлений.¶

TDLib старается гарантировать, что при отправке уведомления о закреплённом сообщении закреплённое сообщение уже доступно локально в памяти, поэтому клиент может использовать новый запрос getMessageLocally для его получения. Кроме того, updateNotification будет отправляться всякий раз при изменении закреплённого сообщения, хотя само уведомление не изменилось.¶

Настройка API уведомлений #

Клиент управляет максимальным числом активных групп уведомлений с помощью параметра notification_group_count_max. Значение этого параметра по умолчанию равно 0, то есть активных групп уведомлений нет и API уведомлений фактически отключён. В качестве значения параметра можно использовать любое целое число от 0 до 25. Значения больше 25 не допускаются, поскольку большинство операционных систем всё равно не покажет столько групп уведомлений.¶

Клиент также управляет максимальным числом активных уведомлений в группе с помощью параметра notification_group_size_max. Значение этого параметра по умолчанию равно 10 и может быть любым целым числом от 1 до 25. Значения больше 25 не допускаются, поскольку большинство операционных систем всё равно не покажет столько уведомлений в группе.¶

Пользователь может выбрать показ закреплённых сообщений или упоминаний среди обычных сообщений в группе уведомлений Messages вместо группы уведомлений Mentions, а также не применять к ним настройки уведомлений из личного чата отправителя. Это можно сделать для каждого чата отдельно или для всей области уведомлений чатов через новые параметры disable_pinned_message_notifications и disable_mention_notifications, добавленные в классы chatNotificationSettings и scopeNotificationSettings.¶

Обработка push-уведомлений #

Для поддержки нескольких учётных записей в одном приложении метод registerDevice теперь возвращает глобально уникальный идентификатор подписки на push-уведомления. Этот идентификатор можно использовать, чтобы сопоставить push-уведомление с соответствующей учётной записью и обрабатывать уведомление только той учётной записью, для которой оно было отправлено.¶

При получении push-уведомления клиент должен вызвать синхронный метод getPushReceiverId, передав полезную нагрузку push-уведомления. Метод вернёт глобально уникальный идентификатор подписки на push-уведомления (также называемый ID приёмника push-уведомлений), по которому можно найти экземпляр TDLib, который следует запустить и использовать для обработки push-уведомления. Если метод возвращает 0 в качестве ID приёмника push-уведомлений, push-уведомление следует обработать всем клиентам (обычно это происходит, когда клиент только один).¶

Для обработки уведомления необходимо вызвать метод processPushNotification в экземпляре или экземплярах TDLib, найденных по ID приёмника push-уведомлений. Этот метод можно вызвать до авторизации, и его выполнение будет автоматически отложено до инициализации TDLib. Метод возвращает результат только после отправки всех обновлений, вызванных push-уведомлением; после этого экземпляр TDLib можно безопасно закрыть. Если метод возвращает ошибку с кодом 406, push-уведомление считается неподдерживаемым и для получения новых данных требуется соединение с сервером. При любой другой ошибке произошла ошибка при обработке push-уведомления, то есть не удалось расшифровать или разобрать полезную нагрузку уведомления. В этом случае соединение с сервером не требуется, однако там могут быть новые уведомления. После успешного ответа от processPushNotification экземпляр TDLib можно немедленно закрыть, чтобы уменьшить расход батареи. Либо клиент может дождаться обновления updateHavePendingNotifications, сообщающего, что отложенных или неполученных уведомлений больше нет.¶

Клиенты Android и iOS могут выбрать получение push-уведомлений со сквозным шифрованием через VoIP-уведомления Firebase Cloud Messaging или Apple Push Notification service при подписке на push-уведомления методом registerDevice. В случае Firebase Cloud Messaging, если push-уведомления со сквозным шифрованием отключены, push-уведомления отправляются без содержимого, поэтому уведомления типа NewPushMessage не будут создаваться, а клиенту всегда потребуется подключаться к серверам Telegram для загрузки новых сообщений при получении push-уведомления.¶

Удаление пользователями активных уведомлений #

Существуют два метода удаления уведомлений из списка активных уведомлений, когда пользователь скрывает их. Если пользователь удаляет одно уведомление, его можно удалить вызовом метода removeNotification. Если пользователь отклоняет всю группу уведомлений, это можно сделать с помощью метода removeNotificationGroup. Удалённые уведомления никогда не вернутся в список активных уведомлений, однако всё ещё могут учитываться в общем числе непрочитанных уведомлений группы.¶
