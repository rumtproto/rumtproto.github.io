Начало работы с TDLib #

TDLib — полнофункциональный клиент Telegram, который берёт на себя все детали работы с сетью, локальным хранилищем и согласованностью данных. В этом руководстве описываются основные понятия, понимание которых необходимо для эффективного использования TDLib.¶

Интерфейс TDLib #

В этом тексте под Client понимается интерфейс для взаимодействия с экземпляром TDLib, а под Application — программа, использующая TDLib для взаимодействия с Telegram.¶

Основной API TDLib полностью асинхронен. Application может отправить запрос в TDLib методом ClientManager.send и асинхронно получить ответ методом ClientManager.receive, когда тот станет доступен. Точные названия этих методов и способ сопоставления запросов с ответами различаются для разных интерфейсов TDLib, однако сама концепция остаётся той же. Например, в интерфейсе TDLib JSON эти методы называются td_send и td_receive, а для сопоставления запросов с соответствующими ответами необходимо использовать их поле @extra.¶

В высокоуровневом интерфейсе, используемом Application, сопоставление ответов с соответствующими запросами часто автоматизировано и некоторой обёрткой преобразуется в вызов продолжения, callback-функции, Promise или Future, чтобы упростить обработку ответов.¶

Помимо ответов на запросы, Application получает множество важных данных через входящие updates. Updates используются для передачи новых данных из TDLib в Application и часто управляют поведением Application, не оставляя возможности реализовать что-либо неверно. Правильная обработка updates критически важна для создания эффективного и корректно работающего Application.¶

В веб-документации приведён список всех доступных методов API TDLib. Описания всех доступных методов и классов TDLib также можно найти в схеме API TDLIB.¶

TDLib можно использовать из любого языка программирования. Множество примеров основанных на TDLib фреймворков на разных языках программирования приведено в нашем разделе примеров.¶

Глоссарий TDLib #

В этом разделе описаны основные понятия, необходимые для понимания TDLib API. Если вы пользовались основанным на TDLib Telegram Bot API, большинство из них вам уже знакомо.¶

Telegram — мессенджер, поэтому его основной объект — message. Каждое message принадлежит некоторому чату и имеет уникальный идентификатор в пределах этого chat. Messages внутри chat должны быть отсортированы по этому идентификатору. Telegram поддерживает множество разных видов messages, поэтому message может иметь много разных видов message content. Сейчас существует более 45 различных видов message content: например, messageText для текстовых сообщений, messagePhoto для фотографий или messageScreenshotTaken для уведомлений о снимках экрана, сделанных собеседником.¶

Пользователь Telegram называется user. У каждого user есть уникальный идентификатор и first name, а также среди прочих полезных полей могут быть необязательные last name, username и profile photo. Bot — особый тип user, которым можно управлять через Telegram Bot API.¶

У каждого chat есть members, то есть users, которые немедленно получают все messages, отправленные в chat. Сейчас существует 6 возможных статусов участника чата, описывающих различные права и ограничения user в chat: от владельца чата, у которого в chat больше прав, чем у любого другого user, до пользователя, заблокированного в чате, который banned в chat и не может самостоятельно вернуться в него или даже просматривать chat messages, даже если chat является public.¶

Как отмечалось ранее, каждое message принадлежит чату. Сейчас в Telegram есть 4 различных типа chats:¶

  • Личные чаты — обычные чаты один на один с другим user (либо с самим собой в случае специального чата «Saved messages»).
  • Обычные группы — это обычные группы с 0–200 members. У каждого basic group member есть собственная копия истории сообщений, поэтому новые basic group members могут не видеть старые messages (если только другой пользователь не перешлёт им свою копию).
  • Супергруппы — группы, насчитывающие до 200000 members, с общей историей сообщений, поэтому новые supergroup members могут видеть все ранее отправленные messages (если это явно не запрещено chat creator). Есть особые виды supergroups, называемые broadcast groups и channels; они могут иметь неограниченное число участников, а писать в них могут только chat creator и некоторые chat administrators. Все остальные chat members могут лишь читать messages в чатах channel и broadcast group
  • Секретные чаты — чаты один на один с другим user со сквозным шифрованием, доступные только на устройстве, с которого чат был инициирован и принят.

У каждого чата есть уникальный идентификатор, title и необязательная фотография чата. Чаты образуют отображаемые пользователю отсортированные списки, position в которых, грубо говоря, определяется временем последней активности. Правильный порядок чатов в списках поддерживает TDLib, поэтому Application достаточно отслеживать обновления, меняющие поле chat.positions, и сортировать все чаты по паре (position.order, chat.id) в заданном position.list.¶

Messages, chat photos и многие другие объекты могут содержать file. У каждого file есть идентификатор; он может быть доступен локально в локальном хранилище или удалённо на облачном сервере. Обычно file можно downloaded в локальное хранилище или uploaded на облачные серверы Telegram.¶

Messages с медиасодержимым, например photos или videos, могут иметь короткий сопроводительный текст, называемый caption. Тексты текстовых сообщений и подписи к медиа могут содержать фрагменты, которые следует оформить особым образом. Такие фрагменты называются text entities, а совокупность text и его entities называется formatted text.¶

TDLib передаёт множество важных данных в Application через updates. Например, если обнаружен неизвестный Application пользователь или изменились какие-либо данные о пользователе, TDLib немедленно отправляет в Application updateUser.¶

Авторизация пользователя #

Авторизация — пример поведения, которым TDLib управляет через updates. Всякий раз, когда для продолжения авторизации пользователя требуется действие, Application получает updateAuthorizationState с описанием текущего AuthorizationState. Для правильной реализации авторизации пользователя Application достаточно надлежащим образом обработать это update.¶

Первое authorization state, полученное Application, всегда имеет тип authorizationStateWaitTdlibParameters. При его получении Application должно передать параметры инициализации TDLib, вызвав метод setTdlibParameters. В этом методе Application потребуется указать, среди прочих параметров:¶

  • api_id — идентификатор Application для доступа к Telegram API; его можно получить на https://my.telegram.org.
  • api_hash — хеш идентификатора Application для доступа к Telegram API; его можно получить на https://my.telegram.org.
  • database_directory — путь к каталогу на локальном диске, в котором будет храниться база данных TDLib; он должен указывать на доступный для записи каталог.
  • use_message_database — если установлено значение true, библиотека будет поддерживать локальный кеш chats и messages.
  • use_secret_chats — если установлено значение true, будет включена поддержка secret chats
  • system_language_code — языковой тег IETF языка операционной системы user, например «en-GB».
  • device_model — модель устройства, на котором запущено Application, например «iPhone Z».

После успешного вызова setTdlibParameters Application получит updateAuthorizationState с новым состоянием и должно лишь обработать это обновление; явно делать ничего не требуется. Если вызов setTdlibParameters завершается неудачей, состояние авторизации не изменяется, и Application должно снова попытаться обработать текущее authorization state¶

Если пользователь ещё не авторизован, могут быть получены некоторые из authorization states authorizationStateWaitPhoneNumber, authorizationStateWaitEmailAddress, authorizationStateWaitEmailCode, authorizationStateWaitCode, authorizationStateWaitRegistration и authorizationStateWaitPassword. После завершения этих шагов авторизации Application получит authorizationStateReady, что означает успешную авторизацию и возможность отправлять обычные запросы.¶

Полные примеры авторизации user приведены в наших примерах на Java и C#.¶

Отправка сообщения #

Чтобы отправить message любого вида, Application должно вызвать метод sendMessage, передав идентификатор chat и содержимое отправляемого сообщения. Например, Application может отправить text message, использовав класс inputMessageText в качестве содержимого входящего сообщения, photo — с помощью inputMessagePhoto, а location — с помощью inputMessageLocation. Чтобы отправить локальный файл из локального хранилища, Application может использовать inputFileLocal как InputFile в этих объектах.¶

Примеры отправки text message приведены в наших примерах на Java и C#.¶

Обработка обновлений #

Все обновления и ответы на запросы должны обрабатываться в порядке их получения. Ниже приведён список наиболее важных обновлений и порядок их обработки:¶

  • updateAuthorizationState — обработка этого обновления необходима для правильной авторизации пользователя.
  • updateNewChat — это обновление приходит при обнаружении нового chat. Оно гарантированно приходит до того, как идентификатор chat будет возвращён Application. Поэтому, когда Application получает chat_id, ему никогда не требуется использовать запрос getChat, чтобы получить объект chat. Вместо этого оно должно поддерживать кеш chats, полученных через это обновление, и брать из него все необходимые данные о chats.
  • updateUser — это обновление приходит при обнаружении нового user или изменении каких-либо данных известного user. Оно гарантированно приходит до того, как идентификатор user будет возвращён Application. Поэтому, когда Application получает user_id, ему никогда не требуется использовать запрос getUser, чтобы получить объект user. Вместо этого оно должно поддерживать кеш users, полученных через это обновление, и брать из него все необходимые данные о users.
  • updateBasicGroup — это обновление приходит при обнаружении новой basic group или изменении каких-либо данных известной basic group. Оно гарантированно приходит до того, как идентификатор basic group будет возвращён Application. Поэтому, когда Application получает basic_group_id, ему никогда не требуется использовать запрос getBasicGroup, чтобы получить объект basicGroup. Вместо этого оно должно поддерживать кеш basic groups, полученных через это обновление, и брать из него все необходимые данные о basic groups.
  • updateSupergroup — это обновление приходит при обнаружении новой supergroup или изменении каких-либо данных известной supergroup. Оно гарантированно приходит до того, как идентификатор supergroup будет возвращён Application. Поэтому, когда Application получает supergroup_id, ему никогда не требуется использовать запрос getSupergroup, чтобы получить объект supergroup. Вместо этого оно должно поддерживать кеш supergroups, полученных через это обновление, и брать из него все необходимые данные о supergroups.
  • updateSecretChat — это обновление приходит при обнаружении нового secret chat или изменении каких-либо данных известного secret chat. Оно гарантированно приходит до того, как идентификатор secret chat будет возвращён Application. Поэтому, когда Application получает secret_chat_id, ему никогда не требуется использовать запрос getSecretChat, чтобы получить объект secret chat. Вместо этого оно должно поддерживать кеш secret chats, полученных через это обновление, и брать из него все необходимые данные о secret chats.
  • updateNewMessage — это обновление приходит всякий раз, когда в chat добавляется новое message
  • updateMessageSendSucceeded — это обновление приходит всякий раз, когда message успешно отправлено.
  • updateMessageContent — это обновление приходит всякий раз, когда изменяется content message
  • updateFile — это обновление приходит при обновлении информации о файле. Обработка этого обновления необходима для отслеживания хода загрузки или выгрузки файлов.
  • updateChatTitle, updateChatPhoto, updateChatPermissions, updateChatLastMessage, updateChatPosition, updateChatReadInbox, updateChatReadOutbox, updateChatActionBar, updateChatDraftMessage, updateChatMessageSender, updateChatMessageTtl, updateChatNotificationSettings, updateChatPendingJoinRequests, updateChatReplyMarkup, updateChatTheme, updateChatUnreadMentionCount, updateChatVideoChat, updateChatDefaultDisableNotification, updateChatHasProtectedContent, updateChatHasScheduledMessages, updateChatIsBlocked, updateChatIsMarkedAsUnread — эти обновления сообщают об изменениях свойств чата и должны обрабатываться для поддержания актуальности информации о chat.

Полный список доступных сейчас updates см. в документации класса Update.¶

Получение списков чатов #

Сейчас существует 3 различных типа списков чатов:
- Основной список чатов.
- Список чатов архива.
- Список чатов папки.¶

Позициями chats в chat lists управляет TDLib, поэтому Application достаточно отслеживать updates, меняющие поле chat.positions, поддерживать список всех chats, отсортированный по убыванию пары (position.order, chat.id), и вызывать loadChats только при необходимости получить больше chats. Для оптимальной производительности число загруженных chats выбирает TDLib, и оно может быть меньше указанного limit. Если Application требуется больше chats, оно должно отправить ещё один запрос loadChats.¶

Пример получения основного chat list приведён в нашем примере на Java.¶

Получение сообщений чата #

Application может использовать метод getChatHistory для получения messages в chat. Messages возвращаются в обратном хронологическом порядке (то есть в порядке убывания message_id). Application может передать from_message_id == 0, чтобы получить messages, начиная с последнего message. Чтобы получить больше messages, чем может быть возвращено в одном ответе, Application должно передать идентификатор последнего полученного message как from_message_id в следующий запрос. Для оптимальной производительности число возвращаемых messages выбирает TDLib, и оно может быть меньше указанного limit. Если Application требуется больше messages, оно должно изменить параметр from_message_id и повторить запрос.¶
