Зашифрованные CDN для скорости и безопасности #

После выхода версии 4.2 официальных приложений клиентским приложениям Telegram может потребоваться скачивать популярные файлы, опубликованные в публичных каналах с более чем 100 000 участников, из вторичных дата-центров сети доставки контента (CDN). Эти CDN DC расположены в регионах со значительным трафиком Telegram, где по разным причинам нежелательно размещать серверы Telegram.¶

CDN DC не являются частью облака Telegram, и их следует считать враждебной территорией. Поэтому каждый файл, отправляемый в эти CDN DC, шифруется уникальным ключом с помощью AES-256-CTR. CDN не может получить доступ к данным, которые хранит, поскольку эти ключи доступны только главному серверу MTProto и авторизованному клиенту.¶

См. также: Подробнее о CDN и правительствах в расширенном FAQ¶

Как это работает #

Когда файл из публичного канала с ~100 000 участников становится популярным в определённом регионе, сервер Telegram может зашифровать этот файл уникальным ключом AES-256-CTR и отправить его на хранение в соответствующий CDN DC.¶

Если файл хранится в CDN DC рядом с конечным пользователем, скорость скачивания будет значительно выше, поскольку данным нужно преодолеть меньшее расстояние и, вероятно, удастся избежать многих узких мест между регионами.¶

Это безопасно, потому что к CDN DC относятся так же, как к интернет-провайдерам или случайным третьим лицам:¶

  • У CDN DC нет ключей для расшифровки хранящихся там файлов, поэтому они не могут получить доступ к данным, даже если DC скомпрометирован.
  • Зашифрованные фрагменты файлов защищены от подмены хешем SHA-256, который клиент проверяет при получении.
  • В CDN DC не хранятся и не передаются никакие личные данные.
  • Сервер разрешает кэшировать в CDN DC только медиа из публичных каналов с более чем 100 000 подписчиков (включая медиа, пересланные из таких каналов, и вирусные медиа, первоначально появившиеся в других крупных публичных каналах).

Возможности CDN для обмена данными очень ограничены: главный дата-центр только загружает зашифрованные файлы на хранение и не принимает от CDN никаких данных. Клиентские приложения только скачивают зашифрованные файлы и не принимают других обновлений. Ключи для расшифровки файла клиентские приложения получают от главного сервера Telegram и проверяют целостность файла по хешу, поэтому CDN может предоставить только правильный файл — всё иное клиент немедленно отбросит.¶

CDN DC хранят файлы не на жёстких дисках, а только в памяти. Когда у CDN-сервера заканчивается память, простой алгоритм LRU заменяет наименее популярные файлы новыми.¶

Чем CDN DC отличаются от главных DC #

  • CDN могут быть недоверенными.
  • Разработчики клиентов могут использовать help.getCdnConfig, чтобы получить список открытых RSA-ключей CDN DC, отличающихся от открытых RSA-ключей главных DC.
  • CDN поддерживают только следующие методы: upload.getCdnFile, initConnection, invokeWithLayer.
  • При работе с CDN разработчикам клиентов следует помнить, что auth_key может быть удалён в любой момент (это приводит к ошибке -404, в таком случае необходимо сгенерировать новый ключ).
  • Клиентские приложения не должны принимать обновления от CDN DC (приложения должны принимать обновления только из своего основного соединения с главным DC).
  • Клиенты не должны разрешать CDN DC подменять ответы на запросы, отправленные в другие DC.
  • Клиенты не должны отправлять в CDN личные данные пользователя, передаваемые в initConnection.

Получение файлов из CDN #

После запроса upload.getFile API может вернуть конструктор upload.fileCdnRedirect. В этом случае клиент должен запросить нужный файл у CDN DC. Поле dc_id в ответе — идентификатор нового CDN. IP-адрес для соединения, как и для главных DC, будет доступен в help.getConfig. У соответствующего dcOption будет установлен флаг cdn:flags.3?true.¶

После успешного установления соединения с CDN DC, указанным в dc_id, клиент должен сгенерировать auth_key (предварительно подтвердив, что открытый RSA-ключ MTProto CDN DC совпадает с одним из ключей в списке, возвращённом help.getCdnConfig). Затем клиент должен выполнить запрос upload.getCdnFile для каждого offset. Для файлов неизвестного размера запрос необходимо повторять до получения пустого ответа.¶

upload.getCdnFile может вернуть конструктор upload.cdnFileReuploadNeeded. В этом случае клиенту необходимо отправить запрос upload.reuploadCdnFile в DC, получивший исходный запрос upload.getFile. После успешного выполнения upload.reuploadCdnFile приложение должно снова запросить файл у CDN DC.¶

Главный DC файла — это DC, где хранится его основная копия (не следует путать с главным DC пользователя): userProfilePhoto.dc_id, chatPhoto.dc_id, photo.dc_id или document.dc_id.¶

Расшифровка файлов #

В upload.fileCdnRedirect сервер отправляет ключ расшифровки и IV файла (поля encryption_key:bytes и encryption_iv:bytes соответственно).¶

Получив часть зашифрованных данных от CDN DC в upload.cdnFile, клиент должен расшифровать их с помощью AES-256-CTR. В качестве IV следует использовать значение encryption_iv, изменённое следующим образом: для каждого offset заменить последние 4 байта encryption_iv на offset / 16 в порядке байтов от старшего к младшему. Это позволяет клиентам эффективно расшифровывать файл и использовать произвольный доступ к его содержимому (например, для потоковой передачи).¶

Проверка файлов #

Чтобы убедиться, что CDN DC передал файл без изменений, клиенты должны проверять хеши каждой скачанной части. upload.fileCdnRedirect, upload.reuploadCdnFile и upload.getCdnFileHashes содержат конструкторы FileHash. Каждый из этих конструкторов содержит SHA-256-хеш части файла, начинающейся со смещения offset и имеющей длину limit байт.¶

Перед сохранением в файл каждой порции данных, полученной от CDN DC, клиент должен убедиться, что её хеш совпадает с хешем, полученным от главного DC. Если для какой-либо части файла хеш отсутствует, разработчикам клиентов необходимо получить его методом upload.getCdnFileHashes.¶

Схема #

fileHash#f39b035c offset:long limit:int hash:bytes = FileHash;

upload.fileCdnRedirect#f18cda44 dc_id:int file_token:bytes encryption_key:bytes encryption_iv:bytes file_hashes:Vector<FileHash> = upload.File;

upload.cdnFileReuploadNeeded#eea8e46e request_token:bytes = upload.CdnFile;
upload.cdnFile#a99fca4f bytes:bytes = upload.CdnFile;


dcOption#18b7a10d flags:# ipv6:flags.0?true media_only:flags.1?true tcpo_only:flags.2?true cdn:flags.3?true static:flags.4?true this_port_only:flags.5?true id:int ip_address:string port:int secret:flags.10?bytes = DcOption;

cdnPublicKey#c982eaba dc_id:int public_key:string = CdnPublicKey;


cdnConfig#5725e40a public_keys:Vector<CdnPublicKey> = CdnConfig;

---functions---

// CDN DC
upload.getCdnFile#395f69da file_token:bytes offset:long limit:int = upload.CdnFile;

// Master DC
upload.reuploadCdnFile#9b2754a8 file_token:bytes request_token:bytes = Vector<FileHash>;
upload.getCdnFileHashes#91dc3f31 file_token:bytes offset:long = Vector<FileHash>;

help.getCdnConfig#52029342 = CdnConfig;

Ограничения параметров upload.getFile и upload.getCdnFile #

  • offset должен делиться на 4096 байт
  • limit должен делиться на 4096 байт
  • 1048576 (1 МБ) должно делиться на limit
  • offset / (1024 * 1024) == (offset + limit - 1) / (1024 * 1024) (скачиваемые части файла всегда должны находиться внутри одного фрагмента размером в мегабайт)

Тестирование перенаправлений CDN #

Перенаправления файлов в CDN можно проверить, войдя в тестовые DC с аккаунтом DC 2 (номер телефона 999662YYYY, где YYYY — случайные числа, код входа 22222), загрузив, а затем снова скачав загруженный файл.¶

Убедитесь, что у выбранного тестового аккаунта нет тестовой подписки Telegram Premium, поскольку при включённой тестовой подписке Telegram Premium скачивание файлов из CDN в тестовых DC отключено (это можно проверить, убедившись, что user, возвращённый вызовом users.getUsers с inputUserSelf, не имеет установленного флага premium).¶
