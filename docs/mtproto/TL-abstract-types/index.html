Двоичная сериализация и абстрактные типы TL #

Язык TL описывает абстрактные типы данных в духе общей теории типов (точнее, теорий зависимых интуиционистских типов Мартина-Лёфа), никак не оговаривая, как значения этих типов должны быть представлены в памяти, при сохранении на диск или при передаче по сети. Статья же о двоичной сериализации посвящена задаче эффективной сериализации значений абстрактных типов. Для этого вводится понятие конкретного, или сериализованного, типа — множества сериализаций всех возможных значений соответствующего абстрактного типа. При этом сериализации принимают значения во множестве A* слов в алфавите A, состоящем из 2^32 символов — 32-битных целых чисел.¶

Чтобы схема TL (то есть «программа» на языке TL) описывала сериализацию значений абстрактных типов, нужно объяснить, как конкретный тип [T] (подмножество [T] множества A^*) связан с абстрактным типом T (определённым в TL) и как значения абстрактного типа T соответствуют значениям конкретного типа [T] (то есть элементам [T]).¶

Сериализация — это построение элемента [T] по значению абстрактного типа T. Обратный процесс называется десериализацией.¶

Значения абстрактного типа T можно представлять по-разному. Обычно в памяти используются деревья или графы, а при желании — набор узлов, каждый из которых содержит некоторый тег («тип узла») и несколько указателей на другие узлы и/или значения встроенных примитивных типов вроде int. Однако для общих рассуждений удобно записывать значения абстрактного типа T в виде строки, а именно S-выражения. Напомним, что S-выражение — это либо атом (значение примитивного типа, например целое число или строковая константа в кавычках, либо идентификатор, соответствующий встроенной или определённой функции), либо разделённый пробелами список S-выражений, заключённый в скобки. В нашем случае применяются S-выражения, первый элемент которых — идентификатор комбинатора, а остальные элементы (их количество зависит от арности комбинатора) — S-выражения, представляющие значения полей (или параметров) выбранного комбинатора. При этом типы S-выражений-аргументов и тип S-выражения результата (то есть всего выражения целиком) обязаны согласовываться.¶

Например, для схемы¶

pair x:int y:int = Pair;
pnil = PairList;
pcons hd:Pair tl:PairList = PairList;

вот примеры значений абстрактного типа PairList, записанных как S-выражения:¶

(pnil)
(pcons (pair 2 3) (pcons (pair 9 4) (pnil)))

Обычно мы пишем E : T (читается «E типа T»), когда хотим сказать, что E — значение типа T. Будем считать, что существует встроенный тип Type, значения которого — сами типы. Таким образом, запись T : Type означает, что T — это тип.¶

Например, можно написать:¶

PairList : Type;
(pcons (pair 2 3) (pcons (pair 9 4) (pnil))) : PairList;

Преобразование абстрактного значения в сериализованное, вообще говоря, устроено просто (и при желании может быть определено по индукции):¶

  • Значение n примитивного типа int сериализуется само в себя (как односимвольное слово в алфавите A).¶

  • Сериализация строковой константы (значения примитивного типа string) — это последовательность 32-битных чисел, описанная в статье Двоичная сериализация.¶

  • Сериализация S-выражения (C E1 ... Er) : T, где C — комбинатор арности r с типами аргументов T1, ..., Tr и типом результата T (то есть C : T1->T2->...->Tr->T), — это конкатенация номера комбинатора C (32-битного числа, однозначно определяющего комбинатор; обычно оно равно CRC-32 строки его описания на TL) и сериализаций значений E1 типа T1, E2 типа T2, ..., Er типа Tr.¶

Если обозначить через [T] конкретный тип, соответствующий абстрактному T, а через [E] — элемент [T], соответствующий значению E типа T, то последнее правило можно записать так:¶

  • [T] — это объединение по всем конструкторам типа C T1->T2->...->Tr->T (то есть возвращающим значение типа T) прямых произведений {C} x [T1] x [T2] x ... x [Tr], где {C} — одноэлементное множество, состоящее из номера комбинатора C. Поскольку {C}<>{C'} при C<>C', это задаёт взаимно однозначное отображение значений абстрактного типа T (записанных с помощью S-выражений) во множество [T].

Значения встроенных «одетых» типов Int и String сериализуются так, как если бы они были определены через int x:int = Int; и string s:string = String;, то есть сериализации целочисленной или строковой константы предшествует номер комбинатора (конструктора) int или string. В виде S-выражений это записывается как (int 5) или (string "Test").¶

Однако сказанное выше не учитывает некоторых тонкостей — например, существования «голых» типов или различия между функциями (активными комбинаторами, применение которых может быть редуцировано, то есть вычислено) и конструкторами (пассивными комбинаторами, для которых правил редукции нет и быть не может). Кроме того, мы не объяснили, как быть с полиморфными типами и необязательными параметрами комбинаторов. Попробуем разобраться с этим сейчас.¶

Константы, поверхностные значения и функциональные значения #

Разделив комбинаторы на конструкторы и функции, мы можем ввести следующие классы выражений (значений) абстрактного типа T:¶

  • Константные выражения: для типов int и string это все целочисленные и строковые константы; для T это все выражения вида (C E1 ... Er) : T, где комбинатор C : T1->T2->...->Tr->T — конструктор, а Ei : Ti — константные выражения типов Ti. Иначе говоря, константное выражение — это S-выражение, состоящее только из конструкторов и констант примитивных типов.¶

  • Поверхностные выражения — это выражения, которые снаружи содержат функциональный комбинатор, но его аргументы при этом константные выражения подходящих типов. Иначе говоря, функциональный комбинатор встречается только на внешнем уровне. (Это не вполне точно; полное объяснение приведено ниже.)¶

  • Функциональные выражения: это выражения, которые могут содержать любые комбинаторы или константы на всех уровнях.¶

На практике чаще всего нужны константные значения (для хранения и передачи любых структур данных, в частности ответов на RPC-запросы — запросы к удалённой процедуре, Remote Procedure Call) и поверхностные выражения (например, в качестве RPC-запросов: тогда функциональный комбинатор внешнего уровня — это имя RPC-функции, которую мы хотим вызвать, а её параметры — аргументы вызова, то есть константные значения). В некоторых случаях полезны произвольные функциональные выражения (например, если мы хотим удалённо передать результат одного RPC-запроса в другой RPC-запрос).¶

Через c(T) мы будем обозначать подтип абстрактного типа T, значениями которого являются константные выражения типа T. Очевидно, что у c(T) примерно те же конструкторы, что и у самого T (с заменой типов всех аргументов Ti на c(Ti)), но функциональных комбинаторов у него нет.¶

Аналогично через f(T) мы будем обозначать подтип T, значениями которого являются поверхностные выражения типа T. Очевидно, что комбинаторы f(T) — это по сути функциональные комбинаторы типа T, но к типам их аргументов применяется c(): комбинатор A : T1->...->Tr->T превращается в A' : c(T1)->...->c(Tr)->f(T). (Уточнение этого правила см. ниже.)¶

Таким образом, мы определили два «функционала» c : Type -> Type и f : Type -> Type, такие что forall T : Type, c(T) :- T и forall T : Type, f(T) :- T (запись T :- T' означает, что T содержится в T', то есть что T — подтип T').¶

Мы будем считать, что c и f идемпотентны.¶

Голые типы #

С точки зрения абстрактной теории типов голые типы (naked types — типы, сериализуемые без номера комбинатора, в отличие от встроенных примитивных типов вроде int и string) не нужны. Однако на практике они чрезвычайно полезны.¶

Поэтому в TL вводится (частично определённый) идемпотентный унарный оператор %, который превращает стандартный функционал (например, выражение типа ...->Type или просто Type) в другой стандартный функционал того же типа. Если T — тип, то с абстрактной теоретической точки зрения %T эквивалентно c(T). Иначе говоря, значения %T — это константные значения T. Если T — стандартное выражение арности k, то есть T : S1 -> ... -> Sk -> Type, где каждое Si=Type или #, то по определению %T — стандартное выражение той же арности k, которое задаётся равенством (%T) a1 ... ak = % (T a1 ... ak).¶

Когда константное значение типа %T сериализуется, оно сначала сериализуется как значение типа T (в предположении, что T сам ещё не является голым типом). Затем первый символ сериализации отбрасывается (то есть имя охватывающего комбинатора). Поэтому %T — корректное типовое выражение только тогда, когда для %T существует не более одного конструктора. Выражение %T, где T : S1 -> ... -> Sk -> Type, корректно, если при любом выборе параметров a1 : S1, ... , ak : Sk тип T a1 ... ak имеет не более одного конструктора. Использование % в остальных случаях некорректно.¶

Если при любых значениях параметров a1 : S1, ..., ak : Sk для T a1 ... ak существует ровно один конструктор C, то TL позволяет писать C a1 ... ak вместо %T a1 ... ak или %(T a1 .. ak). Иначе говоря, в определённых ситуациях идентификатор C служит синонимом %T. Это допускается только в контексте типа (при указании типа поля комбинатора или его результата).¶

Кроме того, предполагается, что %Int = int и %String = string.¶

Модификатор ! #

В TL идемпотентный оператор ! может модифицировать любой тип, фактически разрешая поверхностные значения там, где сериализуются его константные значения. Однако если T — стандартная функция вида S1->..->Sr->Type, то !T определяется равенством (!T) a1 ... ar = !(T a1 ... ar) для любых a1:S1, ..., ar:Sr.¶

Оператор ! допускается только в определении типов полей функциональных комбинаторов. Обычно он используется как префикс типа, например:¶

set_timeout {X:Type} timeout:int f:!X = X;

В этом случае определяется «обёртка» set_timeout. Она принимает два явных параметра: целое число timeout и поверхностное выражение типа X. Само X : Type — неявный параметр (оно не указывается явно, а выводится из значений остальных параметров и их типов). Обёртка такого рода может пригодиться для изменения поведения RPC-запросов, которые представляют собой поверхностные выражения различных типов. Например, пусть у нас есть функция¶

factorial n:int = int;

тогда мы можем обернуть RPC-запрос (factorial 100) следующим образом: (set_timeout 200 (factorial 100)). Это выражение по-прежнему остаётся поверхностным значением типа int, а значит, его можно передать как RPC-запрос.¶

Ещё один пример — последовательная пара из двух вычислений:¶

pair {X Y : Type} x:X y:Y = Pair X Y;  // constructor
seq_pair {X Y : Type} x:!X y:!Y = Pair X Y; // functional wrapper for sequential computation
par_pair {X Y : Type} x:!X y:!Y = Pair X Y; // functional wrapper for parallel computation

Теперь RPC-запрос (seq_pair (factorial 2) (factorial 3)) : Pair int int сначала вычисляет факториал 2, затем факториал 3 и возвращает пару (pair 2 6). В данном случае порядок операций не важен, поскольку они не имеют побочных эффектов. Точно так же можно было бы использовать (par_pair (factorial 2) (factorial 3)). Однако так бывает не всегда.¶

Мы можем также определить аналог операции «запятая»:¶

comma {X Y : Type} x:!X y:!Y = Y;

Например, эта операция могла бы сначала вычислить x, затем забыть результат, вычислить y и вернуть y.¶

Обратите внимание, что семантика обёрток seq_pair, par_pair и comma определяется именно там, где они реализованы (как и семантика всех прочих функциональных комбинаторов), а не их объявлением в TL.¶

В принципе, полиморфные обёртки вроде set_timeout могут применяться и, например, для «аннотирования» константных значений в ответе на RPC-запрос. Скажем, сервер может вернуть ответ на запрос вместе со временем его вычисления. Однако значение типа !X обязано быть константным, поскольку именно это ожидается в качестве значения охватывающего выражения. Иначе говоря, set_timeout 239 E будет константным (поверхностным) значением типа X тогда и только тогда, когда таково само E.¶

Модификатор $ #

Идемпотентный модификатор $ разрешает использовать произвольные функциональные значения подходящего типа там, где обычно допускаются только константы или поверхностные значения. Он рекурсивно преобразует все комбинаторы для всех задействованных типов, отменяя действие % и приписывая $ к типам параметров и к типу результата всех комбинаторов ($ также добавляется в начало имён преобразованных комбинаторов). Более того, встроенные типы тоже преобразуются (на завершающем этапе): $int = Int и $string = String.¶

Это может пригодиться для создания RPC-запроса, который выполняет «глубокое вычисление» переданного ему выражения:¶

compute {X:Type} expr:$X = X;

Например, теперь мы можем передать в качестве RPC-запроса следующее:¶

(compute ($factorial ($factorial (int 3)))) : int

(Обратите внимание, что тройка оказалась «одета»; комбинатор $factorial имеет тип $int -> $int.)¶

Это очень мощный инструмент. Его не обязательно реализовывать в самых простых версиях TL. В используемых сейчас схемах TL модификатор $ не встречается.¶

Подробнее о модификаторах #

По сути, по крайней мере в применении к сериализации, язык TL по умолчанию подразумевает модификатор c() вокруг типов параметров и результатов всех комбинаторов, а ! и $ его отменяют (точнее, ! только отменяет, а $ в некотором смысле обращает смысл на противоположный). Именно поэтому в TL нет явного модификатора c() и именно поэтому считается, что все функции принимают только константные значения и возвращают константные результаты, если не оговорено иное.¶

Может показаться, что некоторые функциональные комбинаторы могут иметь тип вида partial_factorial n:int = $int; и что RPC-запрос (partial_factorial 3) мог бы тогда неожиданно вернуть ($product (int 3) ($product (int 2) ($product (int 1) (int 1)))) : $int…¶

О модификаторе ! правильнее, по-видимому, думать так. Изначально все типы включают только константные значения (и только конструкторы). Модификатор ! создаёт из каждого типа новый тип — его двойник. У этого нового типа нет собственных конструкторов. Функциональные комбинаторы отличаются от конструкторов тем, что перед типом их результата неявно добавляется !. После этого (локальный или удалённый) процесс вычисления выражения можно представить полиморфной функцией eval : !X -> X.¶
