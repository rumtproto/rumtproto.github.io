Язык TL #

TL (Type Language) служит для описания используемой системы типов, конструкторов и имеющихся функций. По существу применяется формат описания комбинаторов, изложенный в разделе Двоичная сериализация данных.¶

Обзор #

Программа на TL обычно состоит из двух секций, разделённых ключевым словом ---functions---. Первая секция состоит из объявлений встроенных и составных типов (то есть их конструкторов). Вторая состоит из объявлений функций, то есть функциональных комбинаторов.¶

На самом деле и первая, и вторая секция состоят из объявлений комбинаторов, каждое из которых заканчивается точкой с запятой. Однако в первой секции встречаются только конструкторы, а во второй участвуют исключительно функции. Каждый комбинатор объявляется через «объявление комбинатора» в формате, описанном выше. При этом номер комбинатора и имена полей допускается задавать явно.¶

Если после объявления функций требуется объявить дополнительные типы, используется ключевое слово (разделитель секций) ---types---. Кроме того, функциональный комбинатор допускается объявить и в секции типов, если его результирующий тип начинается с восклицательного знака (фактически при интерпретации секции функций этот восклицательный знак добавляется автоматически).¶

Чтобы явно задать 32-битные имена комбинаторов, сразу после имени комбинатора ставится знак решётки (#), за которым следуют 8 шестнадцатеричных цифр.¶

Пространства имён #

В качестве идентификаторов конструкторов и типов можно использовать составные конструкции вида <namespace_identifier>.<constructor_identifier> и <namespace_identifier>.<Type_identifier>. Часть идентификатора слева от точки называется пространством имён. При этом правило о заглавной первой букве в идентификаторах типов и строчной — в идентификаторах конструкторов действует для той части конструкции, что стоит после точки. Например, auth.Message окажется типом, а auth.std_message — конструктором.¶

Пространства имён не требуют отдельного объявления.¶

Комментарии #

Комментарии такие же, как в C++.¶

Пример #

// built-in types
int#a8509bda ? = Int;
long ? = Long;
double ? = Double;
string ? = String;
null = Null;

vector {t:Type} # [ t ] = Vector t;
coupleInt {alpha:Type} int alpha = CoupleInt<alpha>;
coupleStr {gamma:Type} string gamma = CoupleStr gamma;  
/* The name of the type variable is irrelevant: "gamma" could be replaced with "alpha"; 
   However, the combinator number will depend on the specific choice. */

intHash {alpha:Type} vector<coupleInt<alpha>> = IntHash<alpha>;
strHash {alpha:Type} (vector (coupleStr alpha)) = StrHash alpha;
intSortedHash {alpha:Type} intHash<alpha> = IntSortedHash<alpha>;
strSortedHash {alpha:Type} (strHash alpha) = StrSortedHash alpha;

// custom types
pair x:Object y:Object = Pair;
triple x:Object y:Object z:Object = Triple;

user#d23c81a3 id:int first_name:string last_name:string = User;
no_user#c67599d1 id:int = User;
group id:int title:string last_name:string = Group;
no_group = Group;

---functions---

// Maybe some built-in arithmetic functions; inverse quotes make "identifiers" out of arbitrary non-alphanumeric strings
`+` Int Int = Int;
`-` Int Int = Int;
`+` Double Double = Double;
// ...

// API functions (aka RPC functions)
getUser#b0f732d5 int = User;
getUsers#2d84d5f5 (Vector int) = Vector User;

В данном случае конструктору user номер (0xd23c81a3) присвоен явно. На самом деле в этом не было необходимости: это значение и есть CRC32 строки "user id:int first_name:string last_name:string = User" — именно оно подставилось бы по умолчанию.¶

Для Vector int, Vector User, Vector Object и тому подобного специальные конструкторы не требуются — везде можно использовать один и тот же универсальный конструктор:¶

vector#1cb5c415 {t:Type} # [ t ] = Vector t;

Обратите внимание: при вычислении номера конструктора getUsers (Vector int) = Vector User; берётся CRC32 строки «getUsers Vector int = Vector User» (из которой удалены все скобки).¶

Запись T0<T1,T2,...,Tn> — это синтаксический сахар для (T0 (T1) (T2) ... (Tn)). Например, Vector<User> и (Vector User) полностью взаимозаменяемы.¶

Пример RPC-запроса #

Допустим, требуется вызвать getUsers([2,3,4]). Этот запрос будет сериализован в последовательность 32-битных целых чисел следующим образом:¶

0x2d84d5f5 0x1cb5c415 0x3 0x2 0x3 0x4

Учтите, что сериализация в TL даёт последовательности 32-битных целых чисел. Когда такую последовательность нужно поместить в поток байтов — например, в сетевой пакет, — каждое 32-битное целое представляется четырьмя байтами в порядке little-endian. Таким образом, приведённому выше запросу соответствует следующий поток байтов:¶

F5 D5 84 2D 15 C4 B5 1C 03 00 00 00 02 00 00 00 03 00 00 00 04 00 00 00

Ответ может выглядеть примерно так:¶

0x1cb5c415 0x3 0xd23c81a3 0x2 0x74655005 0x00007265 0x72615006 0x72656b 0xc67599d1 0x3 0xd23c81a3 0x4 0x686f4a04 0x6e 0x656f4403

Это приблизительно соответствует¶

[{"id":2,"first_name":"Peter", "last_name":"Parker"},{},{"id":4,"first_name":"John","last_name":"Doe"}]

Обратите внимание, что в обоих случаях используется один и тот же универсальный конструктор vector#1cb5c415: в запросе — для сериализации значения типа Vector int, а в ответе — при сериализации значения типа Vector User. Неоднозначности не возникает, поскольку в обоих случаях тип (де)сериализуемого значения известен ещё до начала (де)сериализации. Например, получив запрос, сервер видит, что первая его часть — 0x2d84d5f5, а она соответствует комбинатору getUsers#2d84d5f5 (Vector int) = Vector User. Отсюда ясно, что дальше пойдёт значение типа Vector int. Получив ответ на этот запрос, клиент знает, что должен принять значение типа Vector User, и десериализует ответ соответствующим образом.¶
