Мобильный протокол: подробное описание (версия 1.0, УСТАРЕЛО) #

Этот документ описывает MTProto v.1.0, его статус — УСТАРЕЛО. Сведения о шифровании, применяемом в актуальных клиентах Telegram, приведены в этом документе.¶

Прежде чем сообщение (или составное сообщение) будет передано по сети с помощью транспортного протокола, оно определённым образом шифруется, а в начало сообщения добавляется внешний заголовок: 64-битный идентификатор ключа (однозначно определяющий как авторизационный ключ для сервера, так и пользователя) и 128-битный ключ сообщения.¶

Ключ пользователя вместе с ключом сообщения задают фактический 256-битный ключ и 256-битный вектор инициализации, которыми сообщение шифруется алгоритмом AES-256 в режиме infinite garble extension (IGE — бесконечное расширение искажения). Обратите внимание: начальная часть шифруемого сообщения содержит переменные данные (сессия, идентификатор сообщения, порядковый номер, серверная соль), которые, очевидно, влияют на ключ сообщения (а значит, и на ключ AES с вектором инициализации). Ключ сообщения определяется как 128 младших бит SHA1 от тела сообщения (включая сессию, идентификатор сообщения и прочее). Составные сообщения шифруются как единое сообщение.¶

Шифрование MTProto между сервером и клиентом, облачные чаты¶

Терминология #

Авторизационный ключ #

2048-битный ключ (auth_key), общий для клиентского устройства и сервера; он создаётся при регистрации пользователя непосредственно на клиентском устройстве путём обмена ключами по Диффи — Хеллману и никогда не передаётся по сети. Каждый авторизационный ключ привязан к конкретному пользователю. Ничто не мешает пользователю иметь несколько ключей (соответствующих «постоянным сессиям» на разных устройствах), причём некоторые из них могут быть заблокированы навсегда, если устройство потеряно. См. также Создание авторизационного ключа.¶

Серверный ключ #

2048-битный RSA-ключ, которым сервер цифровой подписью подписывает собственные сообщения, пока идёт регистрация и генерируется авторизационный ключ. В приложение встроен открытый серверный ключ: с его помощью можно проверить подпись, но нельзя подписывать сообщения. Закрытый серверный ключ хранится на сервере и меняется очень редко.¶

Идентификатор ключа #

64 младших бита SHA1-хеша авторизационного ключа используются, чтобы указать, каким именно ключом зашифровано сообщение. Ключи обязаны однозначно определяться 64 младшими битами своего SHA1, и в случае коллизии авторизационный ключ генерируется заново. Нулевой идентификатор ключа означает, что шифрование не применяется; это допустимо для ограниченного набора типов сообщений, используемых при регистрации для выработки авторизационного ключа на основе обмена по Диффи — Хеллману.¶

Сессия #

(случайное) 64-битное число, которое клиент генерирует, чтобы различать отдельные сессии (session) — например, разные экземпляры приложения, созданные с одним и тем же авторизационным ключом. Сессия вместе с идентификатором ключа соответствует экземпляру приложения. Сервер может хранить состояние сессии. Ни при каких обстоятельствах сообщение, предназначенное одной сессии, не может быть отправлено в другую сессию. Сервер вправе в одностороннем порядке забыть любые клиентские сессии; клиенты должны уметь это обрабатывать.¶

Серверная соль #

(случайное) 64-битное число (server_salt), периодически (скажем, каждые 24 часа) меняемое по запросу сервера отдельно для каждой сессии. Все последующие сообщения обязаны содержать новую соль (хотя сообщения со старой солью принимаются ещё 300 секунд). Требуется для защиты от атак повторного воспроизведения и от некоторых уловок, связанных с переводом часов клиента в далёкое будущее.¶

Идентификатор сообщения (msg_id) #

(зависящее от времени) 64-битное число (msg_id), однозначно идентифицирующее сообщение внутри сессии. Идентификаторы клиентских сообщений делятся на 4; идентификаторы серверных сообщений по модулю 4 дают 1, если сообщение отвечает на клиентское, и 3 в противном случае. Идентификаторы клиентских сообщений обязаны монотонно возрастать (в пределах одной сессии), равно как и идентификаторы серверных, и должны примерно равняться unixtime*2^32. Тем самым идентификатор сообщения указывает на приблизительный момент времени, когда сообщение было создано. Сообщение отклоняется, если прошло более 300 секунд после его создания или если до его создания остаётся более 30 секунд (это нужно для защиты от атак повторного воспроизведения). В такой ситуации его обязательно отправляют повторно с другим идентификатором (или помещают в контейнер с бо́льшим идентификатором). Идентификатор сообщения-контейнера обязан быть строго больше идентификаторов вложенных в него сообщений.¶

Важно: для противодействия атакам повторного воспроизведения младшие 32 бита msg_id, передаваемого клиентом, не должны быть пустыми и обязаны представлять дробную часть момента времени, когда сообщение было создано. В ближайшем будущем сервер начнёт игнорировать сообщения, у которых в младших 32 битах msg_id слишком много нулей.¶

Сообщение, связанное с содержимым #

Сообщение, требующее явного подтверждения (ack). К ним относятся все пользовательские и многие сервисные сообщения — практически все, кроме контейнеров и подтверждений.¶

Порядковый номер сообщения (msg_seqno) #

32-битное число (msg_seqno), равное удвоенному количеству «связанных с содержимым» сообщений (то есть требующих подтверждения и, в частности, не являющихся контейнерами), созданных отправителем до данного сообщения, и увеличенное затем на единицу, если текущее сообщение само связано с содержимым. Контейнер всегда формируется после всего своего содержимого, поэтому его порядковый номер больше либо равен порядковым номерам вложенных в него сообщений.¶

Ключ сообщения #

128 младших бит SHA1-хеша той части сообщения, которая подлежит шифрованию (включая внутренний заголовок и исключая байты выравнивания).¶

Внутренний (криптографический) заголовок #

Заголовок (16 байт), добавляемый перед сообщением или контейнером до того, как всё это шифруется целиком. Состоит из серверной соли (64 бита) и сессии (64 бита).¶

Внешний (криптографический) заголовок #

Заголовок (24 байта), добавляемый перед зашифрованным сообщением или контейнером. Состоит из идентификатора ключа (64 бита) и ключа сообщения (128 бит).¶

Полезная нагрузка #

Внешний заголовок + зашифрованное сообщение или контейнер.¶

Вычисление ключа AES и вектора инициализации #

По 2048-битному авторизационному ключу (auth_key) и 128-битному ключу сообщения (msg_key) вычисляются 256-битный ключ AES (aes_key) и 256-битный вектор инициализации (aes_iv). Ими затем шифруется та часть сообщения, которая подлежит шифрованию, то есть всё, кроме внешнего заголовка, добавляемого позже, — алгоритмом AES-256 в режиме infinite garble extension (IGE).¶

Алгоритм вычисления aes_key и aes_iv из auth_key и msg_key выглядит так:¶

  • msg_key = substr (SHA1 (plaintext), 4, 16);
  • sha1_a = SHA1 (msg_key + substr (auth_key, x, 32));
  • sha1_b = SHA1 (substr (auth_key, 32+x, 16) + msg_key + substr (auth_key, 48+x, 16));
  • sha1_c = SHA1 (substr (auth_key, 64+x, 32) + msg_key);
  • sha1_d = SHA1 (msg_key + substr (auth_key, 96+x, 32));
  • aes_key = substr (sha1_a, 0, 8) + substr (sha1_b, 8, 12) + substr (sha1_c, 4, 12);
  • aes_iv = substr (sha1_a, 8, 12) + substr (sha1_b, 0, 8) + substr (sha1_c, 16, 4) + substr (sha1_d, 0, 8);

где x = 0 для сообщений от клиента к серверу и x = 8 для сообщений от сервера к клиенту.¶

Младшие 1024 бита auth_key в вычислениях не участвуют. Их допускается использовать (вместе с остальными битами или отдельно) на клиентском устройстве для шифрования локальной копии данных, полученных от сервера. Младшие 512 бит auth_key на сервере не хранятся, поэтому, если клиентское устройство шифрует ими локальные данные, а пользователь теряет ключ или пароль, расшифровать локальные данные невозможно (даже если данные с сервера удастся получить).¶

Когда с помощью AES шифруется блок данных, длина которого не кратна 16 байтам, непосредственно перед шифрованием данные дополняются случайными байтами до ближайшей длины, кратной 16 байтам.¶

Важные проверки #

При получении зашифрованного сообщения обязательно следует проверить, что msg_key действительно равен 128 младшим битам SHA1-хеша от ранее зашифрованной части, а также что msg_id чётен для сообщений от клиента к серверу и нечётен для сообщений от сервера к клиенту.¶

Кроме того, необходимо хранить идентификаторы (msg_id) последних N сообщений, полученных от другой стороны; если приходит сообщение с msg_id меньшим, чем все сохранённые значения, или равным любому из них, такое сообщение игнорируется. В противном случае msg_id нового сообщения добавляется в набор, и, если число сохранённых значений msg_id превышает N, самое старое (то есть наименьшее) забывается.¶

Кроме того, следует игнорировать значения msg_id, которые отстоят более чем на 30 секунд в будущее или более чем на 300 секунд в прошлое. Это особенно важно для сервера. Клиенту это тоже полезно (для защиты от атак повторного воспроизведения), но лишь при условии, что он уверен в своём времени (например, если оно синхронизировано с серверным).¶

Тем не менее некоторые сервисные сообщения от клиента к серверу, содержащие данные, отправленные клиентом на сервер (например, msg_id недавнего клиентского запроса), могут обрабатываться на клиенте даже тогда, когда время выглядит «неверным». Особенно это касается сообщений о смене server_salt и уведомлений о некорректном времени на клиенте. См. Мобильный протокол: сервисные сообщения.¶

Хранение авторизационного ключа на клиентском устройстве #

Пользователям, обеспокоенным безопасностью, можно предложить защитить авторизационный ключ паролем — примерно так же, как это сделано в ssh. Для этого SHA1 ключа дописывается в начало самого ключа, после чего вся строка шифруется алгоритмом AES в режиме CBC с ключом, равным (текстовому) паролю пользователя. Когда пользователь вводит пароль, сохранённый защищённый пароль расшифровывается и проверяется сравнением с SHA1. С точки зрения пользователя это практически то же самое, что пароль к приложению или к сайту.¶

В оригинале здесь сказано «the stored protected password», хотя расшифровывается и сверяется с SHA1 сам защищённый авторизационный ключ, а не пароль: пароль лишь служит ключом AES. Формулировка оригинала сохранена, неточность — на его совести.¶

Незашифрованные сообщения #

Специальные сообщения в открытом виде могут использоваться для создания авторизационного ключа, а также для синхронизации времени. Они начинаются с auth_key_id = 0 (64 бита), что означает отсутствие auth_key. Сразу за ним следует тело сообщения в сериализованном виде, без внутреннего и внешнего заголовков. Перед телом сообщения добавляются идентификатор сообщения (64 бита) и длина тела в байтах (32 байта).¶

«32 байта» — опечатка оригинала: поле длины занимает 32 бита, то есть 4 байта, как и message_data_length в таблице ниже. Читать следует «32 бита».¶

В открытом виде может передаваться лишь очень ограниченное число сообщений специальных типов.¶

Схематичное представление сообщений #

Зашифрованное сообщение #

auth_key_id
int64		msg_key
int128		encrypted_data
bytes

Зашифрованное сообщение: encrypted_data #

Содержит шифротекст следующих данных:¶

salt
int64		session_id
int64		message_id
int64		seq_no
int32		message_data_length
int32		message_data
bytes		padding 0..15
bytes

Незашифрованное сообщение #

auth_key_id = 0
int64		message_id
int64		message_data_length
int32		message_data
bytes

Создание авторизационного ключа #

Авторизационный ключ обычно создаётся один раз для каждого пользователя — в ходе установки приложения, непосредственно перед регистрацией. Сама регистрация в действительности происходит уже после создания авторизационного ключа. Впрочем, пользователю можно предложить заполнить регистрационную форму, пока авторизационный ключ генерируется в фоновом режиме. Интервалы между нажатиями клавиш пользователем допускается использовать как источник энтропии при получении качественных случайных чисел, необходимых для создания авторизационного ключа.¶

См. Создание авторизационного ключа.¶

При создании авторизационного ключа клиент получает свою серверную соль (она будет использоваться вместе с новым ключом для всего обмена данными в ближайшее время). Затем клиент создаёт зашифрованную сессию на основе только что сгенерированного ключа, и весь дальнейший обмен данными происходит внутри этой сессии (включая передачу регистрационных сведений пользователя и подтверждение номера телефона) — до тех пор, пока клиент не создаст новую сессию. Клиент вправе в любой момент создать новую или дополнительную сессию, выбрав новый случайный session_id.¶
