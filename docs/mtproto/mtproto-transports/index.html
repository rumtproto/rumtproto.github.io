Транспорты MTProto #

Ниже перечислены транспортные протоколы MTProto (полное объяснение — в напоминании о модели ISO/OSI):¶

  • Abridged
  • Intermediate
  • Padded intermediate
  • Full

Сервер распознаёт эти протоколы (и отличает их от HTTP) по заголовку. Дополнительно можно использовать следующие возможности транспорта:¶

  • Быстрое подтверждение (quick ack — короткая 4-байтовая квитанция о приёме, которую сервер присылает раньше полноценного ответа)
  • Транспортные ошибки
  • Обфускация транспорта

Примеры реализации этих протоколов можно посмотреть в tdlib и MadelineProto.¶

Abridged #

Самый лёгкий из доступных протоколов.¶

  • Накладные расходы: очень малые
  • Минимальная длина обёртки: 1 байт
  • Максимальная длина обёртки: 4 байта

Структура пакета:¶

+-+----...----+
|l|  payload  |
+-+----...----+
OR

+-+---+----...----+
|h|len|  payload  +
+-+---+----...----+

Прежде чем отправить в нижележащий сокет хоть что-нибудь (см. транспорты), клиент обязан первым байтом передать 0xef (сервер в первом ответе первым байтом 0xef не отправляет).
Далее полезная нагрузка оборачивается так:¶

Если длина пакета, делённая на четыре, меньше 127:¶

  • Длина: длина полезной нагрузки, делённая на четыре и записанная одним байтом
  • Полезная нагрузка: содержимое MTProto

Если длина пакета, делённая на четыре, больше или равна 127, вместо этого обязательно используется следующая обёртка:¶

  • Заголовок: один байт со значением 0x7f (127)
  • Длина: длина полезной нагрузки, делённая на четыре и записанная тремя байтами длины (little endian)
  • Полезная нагрузка: содержимое MTProto

Для этого транспорта можно включить быстрое подтверждение ».¶

Чтобы запросить у сервера быстрое подтверждение для зашифрованной полезной нагрузки MTProto, используйте для исходящих сообщений не описанную выше обёртку, а следующую.¶

Если длина пакета, делённая на четыре, меньше 127:¶

  • Длина: длина полезной нагрузки, делённая на четыре, плюс 128, записанная одним байтом ((length/4)+128 или (length >> 2) | (1 << 7)); то есть старший бит обязательно установлен.
  • Полезная нагрузка: содержимое MTProto

Если длина пакета, делённая на четыре, больше или равна 127, вместо этого обязательно используется следующая обёртка:¶

  • Заголовок: один байт со значением 0xff (255)
  • Длина: длина полезной нагрузки, делённая на четыре и записанная тремя байтами длины (little endian); так же, как в обычной обёртке abridged.
  • Полезная нагрузка: содержимое MTProto

Сервер отправляет токены быстрого подтверждения, меняя в них порядок байтов на обратный (то есть переворачивая порядок 4 байтов токена подтверждения) и передавая их отдельным 4-байтовым пакетом без заголовка длины.¶

+----+
|dcba|
+----+

Такие пакеты быстрого подтверждения легко отличить от обычных пакетов abridged: у них в первом байте всегда установлен старший бит (потому что у токенов быстрого подтверждения установлен старший бит последнего байта, а после перестановки байтов последний байт оказывается первым), тогда как длина или заголовок обычных пакетов, приходящих от сервера, всегда меньше либо равны 127 (то есть у обычной полезной нагрузки старший бит не установлен).¶

Intermediate #

Если требуется выравнивание данных по 4 байта, можно использовать промежуточную (intermediate) версию исходного протокола.¶

  • Накладные расходы: малые
  • Минимальная длина обёртки: 4 байта
  • Максимальная длина обёртки: 4 байта

Структура пакета:¶

+----+----...----+
+len.+  payload  +
+----+----...----+

Прежде чем отправить в нижележащий сокет хоть что-нибудь (см. транспорты), клиент обязан первым int передать 0xeeeeeeee (четыре байта; сервер в первом ответе первым int 0xeeeeeeee не отправляет).
Далее полезная нагрузка оборачивается так:¶

  • Длина: длина полезной нагрузки, записанная четырьмя байтами длины (little endian)
  • Полезная нагрузка: содержимое MTProto

Для этого транспорта можно включить быстрое подтверждение ».¶

Чтобы запросить у сервера быстрое подтверждение для зашифрованной полезной нагрузки MTProto, прибавьте к полю len значение 0x80000000 перед его кодированием (это равносильно len = len | (1 << 31), то есть установке старшего бита длины).¶

Сервер отправляет токены быстрого подтверждения отдельным 4-байтовым пакетом без заголовка длины.¶

+----+
|abcd|
+----+

Такие пакеты быстрого подтверждения легко отличить от обычных пакетов intermediate: у токенов быстрого подтверждения всегда установлен старший бит последнего байта, поэтому при попытке прочитать токен подтверждения как 32-битное целое в порядке little endian всегда получится значение, большее или равное 0x80000000, а такой длины пакета не бывает.¶

Padded intermediate #

Версия протокола intermediate с дополнением (padding), предназначенная для использования вместе с включённой обфускацией, чтобы обходить блокировки провайдеров.¶

  • Накладные расходы: от малых до средних
  • Минимальная длина обёртки: случайная
  • Максимальная длина обёртки: случайная

Прежде чем отправить в нижележащий сокет хоть что-нибудь (см. транспорты), клиент обязан первым int передать 0xdddddddd (четыре байта; сервер в первом ответе первым int 0xdddddddd не отправляет).
Далее полезная нагрузка оборачивается так:¶

+----+----...----+----...----+
|tlen|  payload  |  padding  |
+----+----...----+----...----+

Описание обёртки:¶

  • Общая длина: суммарная длина полезной нагрузки и дополнения, записанная четырьмя байтами длины (little endian)
  • Полезная нагрузка: содержимое MTProto
  • Дополнение: случайная строка дополнения длиной 0-15

Для этого транспорта можно включить быстрое подтверждение ».¶

Чтобы запросить у сервера быстрое подтверждение для зашифрованной полезной нагрузки MTProto, прибавьте к полю len значение 0x80000000 перед его кодированием (это равносильно len = len | (1 << 31), то есть установке старшего бита длины).¶

Сервер отправляет токены быстрого подтверждения отдельным пакетом длиной от 8 до 16 байт (не считая длины самого пакета, закодированной обычным образом), состоящим из 4-байтового заголовка, во всех битах которого выставлены единицы, за которым следует токен подтверждения (abcd), а затем от 0 до 8 случайных байтов дополнения.¶

+----+----+----+----...----+
|tlen|FFFF|abcd|  padding  |
+----+----+----+----...----+

Такие пакеты быстрого подтверждения легко отличить от обычных пакетов intermediate с дополнением: их длина всегда меньше либо равна 16, то есть меньше длины любого пакета MTProto.
От транспортных ошибок они отличаются тем, что первые 4 байта полезной нагрузки равны 0xFFFFFFFF, а такого кода транспортной ошибки не существует.¶

Full #

Базовый транспортный протокол MTProto¶

  • Накладные расходы: средние
  • Минимальная длина обёртки: 12 байт (length+seqno+crc)
  • Максимальная длина обёртки: 12 байт (length+seqno+crc)

Структура пакета:¶

+----+----+----...----+----+
|len.|seq.|  payload  |crc.|
+----+----+----...----+----+

Описание обёртки:¶

  • Длина: суммарная длина полей length+seqno+payload+crc, записанная четырьмя байтами длины (little endian; длину самого поля длины тоже нужно включать)
  • Порядковый номер: порядковый номер TCP для этого TCP-соединения (не путать с порядковым номером сообщения MTProto): первый отправленный пакет получает номер 0, следующий — 1 и так далее.
  • Полезная нагрузка: содержимое MTProto
  • CRC: 4 байта CRC32, вычисленные совместно по длине, порядковому номеру и полезной нагрузке.

Возможности транспорта #

Дополнительно можно использовать следующие возможности транспорта:¶

Quick ack #

Часть перечисленных выше TCP-транспортов поддерживает быстрые подтверждения (quick ack): это способ для клиента быстро получить подтверждение приёма пакета.¶

Чтобы запросить быстрое подтверждение для конкретной исходящей полезной нагрузки, клиент обязан установить старший бит (MSB) соответствующего поля транспортной обёртки — как описано выше в документации по каждому транспортному протоколу.¶

Кроме того, клиент обязан сформировать и сохранить токен быстрого подтверждения, связав его с исходящей полезной нагрузкой MTProto; для этого используется авторизационный ключ auth_key — долговременный секрет, общий у клиента и сервера:¶

  • Взять первые 32 бита SHA256 от зашифрованной части полезной нагрузки, к которой спереди приписаны 32 байта из авторизационного ключа (тот же хеш, что вычисляется при получении ключа сообщения, только вместо средних 128 бит берутся первые 32 бита).
  • Установить старший бит последнего байта в 1: иначе говоря, рассматривать полученные выше 32 бита как целое число в little endian и прибавить к нему 0x80000000 (то есть ack_token = msg_key_long[0:4] | (1 << 31) на little-endian системе).

Как только полезная нагрузка успешно получена, расшифрована и принята сервером к обработке, сервер отправит обратно тот же токен быстрого подтверждения, который мы сформировали выше, в кодировке, описанной в документации по каждому транспортному протоколу.¶

Обратите внимание: получение быстрого подтверждения не означает, что какие-либо RPC-запросы, содержащиеся в сообщении, выполнились успешно, завершились с ошибкой или вообще были выполнены. Оно означает лишь то, что они получены, расшифрованы и приняты сервером к обработке.¶

Сервер по-прежнему будет присылать конструкторы msgs_ack для содержательных (content-related) конструкторов и методов из тех полезных нагрузок, на которые было выдано быстрое подтверждение, а также, как обычно, ответы и ошибки на методы и конструкторы.¶

Ошибки транспорта #

При транспортной ошибке (отсутствует авторизационный ключ, флуд на транспорте и тому подобное) сервер может прислать пакет — выбранный транспорт MTProto оформляет его как обычную полезную нагрузку — с 4-байтовым знаковым числом в little endian, абсолютное значение которого содержит код ошибки (само число отрицательное).¶

Например, код ошибки 403 соответствует тем ситуациям, в которых протокол HTTP вернул бы HTTP-ошибку с тем же кодом.¶

Ошибка 404 (авторизационный ключ не найден) возвращается, когда дата-центр не может найти указанный идентификатор авторизационного ключа; при первоначальном рукопожатии MTProto, если какой-либо из указанных запросов некорректен; либо в обычном режиме работы, например если некорректны некоторые поля MTProto (скажем, длина пакета MTProto больше длины пакета, заданной транспортом, и тому подобное).¶

Ошибка 429 (флуд на транспорте) возвращается, когда с одного IP за слишком короткое время устанавливается слишком много транспортных соединений, либо когда достигнут какой-либо из лимитов на контейнеры или сервисные сообщения.¶

Ошибка 444 (неверный DC) возвращается при создании авторизационного ключа, подключении к MTProxy — прокси-серверу, который принимает обфусцированные соединения и передаёт их дата-центрам Telegram, — или в других ситуациях, если указан неверный идентификатор дата-центра.¶

При использовании транспортов HTTP и HTTPS транспортные ошибки передаются не так, как описано выше: они просто возвращаются в виде обычных кодов состояния HTTP (а полезную нагрузку HTTP следует игнорировать).¶

Обфускация транспорта #

Обфускация транспорта обязательна для использования транспортов WebSocket.¶

Обфускация транспорта, служащая для обхода блокировок со стороны провайдеров, реализована по описанному ниже протоколу, который в стеке ISO/OSI расположен под транспортом MTProto (см. напоминание о модели ISO/OSI); это значит, что полезная нагрузка сначала оборачивается в транспортную обёртку MTProto (поддерживаются все транспорты), а затем обфусцируется:¶

Перед установлением соединения (и, соответственно, перед отправкой заголовка конкретного транспорта MTProto) генерируется случайная инициализационная нагрузка длиной 64 байта (512 бит). При генерации нужно отдельно позаботиться о том, чтобы первое целое число (первые четыре байта) случайной строки не совпало с одним из известных идентификаторов протоколов (см. выше).
В частности, первые четыре байта не должны быть равны 0xdddddddd (padded intermediate), 0xeeeeeeee (intermediate), POST, GET, HEAD или любому другому методу HTTP, который принимают серверы MTProto.
Первый байт также не должен быть равен 0xef (abridged). Байты 4-8 тоже не должны быть равны 0x00000000, поскольку это указывало бы на использование транспорта full с начальным порядковым номером TCP (0).¶

Идентификатор протокола, если он есть, обязательно помещается в инициализационную нагрузку по смещению 56 байт: если его длина меньше 4, он дополняется самим собой до длины 4 (0xef => 0xefefefef); отдельно идентификатор протокола после этого отправлять не нужно.¶

Этот протокол применяется также (но не только) при подключении к MTProxy: только в этом случае по смещению 60 в инициализационную нагрузку нужно дополнительно поместить идентификатор дата-центра в специальной кодировке. Кодировка состоит просто в записи идентификатора DC как двухбайтового знакового числа в little endian; для подключения к тестовым серверам к идентификатору DC надо прибавить 10000; если дата-центр, к которому мы подключаемся, — медийный (не CDN), число надо сделать отрицательным.¶

Затем формируется вторичная инициализационная нагрузка — первичная нагрузка, записанная в обратном порядке байтов.¶

Из обеих инициализационных нагрузок извлекаются два ключа — из байтов по смещениям 8-40: ключ, извлечённый из первичной нагрузки, используется как ключ шифрования, ключ из вторичной нагрузки — как ключ расшифровки.¶

Из обеих инициализационных нагрузок извлекаются два вектора инициализации (IV) — из байтов по смещениям 40-56: IV, извлечённый из первичной нагрузки, используется как IV шифрования, IV из вторичной нагрузки — как IV расшифровки.¶

Только при использовании MTProxy для установления соединения с сервером MTProxy применяется секрет. Секрет — это 16-байтовая строка, которая обычно распространяется в шестнадцатеричном виде вместе с хостом и портом MTProxy в глубоких ссылках на прокси ».¶

Нередко встречается 17-байтовая версия секрета: она просто означает, что клиенту следует использовать конкретный транспорт MTProto (по первому байту; обычно это 0xdd, указывающий, что нужно применять протокол padded intermediate 0xdddddddd; впрочем, при обнаружении в секрете дополнительного байта клиентам в любом случае следует по умолчанию выбирать транспорт padded intermediate).¶

Извлечённые ключи шифрования и расшифровки обязательно склеиваются с секретом (первый байт которого следует пропустить, если это 17-байтовая версия), и ключом шифрования/расшифровки служит SHA256-хеш полученной строки.¶

Полученные пары ключ/IV для шифрования и расшифровки затем обязательно применяются в режиме AES-256-CTR — ими шифруются все исходящие и расшифровываются все входящие полезные нагрузки.
Итоговое значение счётчика шифрования/расшифровки после обработки полезной нагрузки MTProto обязательно служит вектором инициализации для следующей нагрузки — и так до закрытия TCP/WS-соединения.
Иначе говоря, переиспользуйте два экземпляра AES-256-CTR OpenSSL для шифрования и расшифровки вплоть до закрытия соединения.¶

Первое, что необходимо зашифровать ключом шифрования, — это сама инициализационная нагрузка. Затем байты 56-64 зашифрованной инициализационной нагрузки подставляются в исходную инициализационную нагрузку: это как раз та часть, которая содержит постоянный идентификатор транспортного протокола MTProto и идентификатор DC (только для MTProxy).¶

Полученную в итоге инициализационную нагрузку необходимо отправить в сокет как первые 64 байта после TCP-рукопожатия.¶

Пример псевдокода для формирования нагрузки подключения к MTProxy (медийный DC 4) с использованием обфусцированного транспорта padded intermediate.
Предупреждение: не используйте указанный секрет прокси ни в каком MTProxy, доступном из интернета.¶

protocol := 0xdddddddd
dc := 0xfcff

while True:
    init := (56 random bytes) + protocol + dc + (2 random bytes)
    
    if init[0] == 0xef:
      continue

	first_int := substr(init, 0, 4)
	if first_int == 0x44414548 || first_int == 0x54534f50 || first_int == 0x20544547 || first_int == 0x4954504f || first_int == 0x02010316 || first_int == 0xdddddddd || first_int == 0xeeeeeeee:
      continue
      
	second_int := substr(init, 4, 4)
    if second_int == 0x00000000:
      continue
      
	break

initRev := strrev(init)

encryptKey := substr(init, 8, 32)
encryptIV := substr(init, 40, 16)

decryptKey := substr(initRev, 8, 32)
decryptIV := substr(initRev, 40, 16)

secret := substr(0xdd99999999999999999999999999999999, 1, 16)

encryptKey = SHA256(encryptKey + secret)
decryptKey = SHA256(decryptKey + secret)

encryptedInit := CTR(encryptKey, encryptIV, init)

finalInit := substr(init, 0, 56) + substr(encryptedInit, 56, 8)

write(finalInit)
