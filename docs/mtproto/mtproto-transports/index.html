MTProto-транспорты: форматы кадров и обфускация

Оригинальное русскоязычное описание деталей кадрирования поверх TCP и транспортной обфускации. Первоисточник: core.telegram.org/mtproto/mtproto-transports. Общая картина транспортов — на странице Транспорты.

abridged (сокращённый формат)

  • Первый байт соединения: 0xef.
  • Длина кадра задаётся одним байтом l в единицах «слов по 4 байта»: при l < 0x7f полезная нагрузка имеет длину 4*l байт.
  • Длинные кадры: байт 0x7f, затем 3 байта длины (в словах, малоэндийные).

intermediate (промежуточный формат)

  • Первые 4 байта: 0xeeeeeeee.
  • Кадр: 32-битная длина в байтах (малоэндийные) + данные.

padded intermediate (промежуточный с дополнением)

  • Первые 4 байта: 0xdddddddd.
  • Как intermediate, но кадр может содержать случайное дополнение; длина указывается по полному кадру. Рекомендуемый формат.

quick ack (быстрые подтверждения)

Если в заголовке длины intermediate/padded установлен бит 0x80000000, сервер может немедленно прислать 4-байтовый код подтверждения (в таком коде установлен старший бит), не дожидаясь полного ответа. Быстрые подтверждения не заменяют протокольные msgs_ack — это лишь сигнал «сообщение получено на транспортном уровне».

Ошибки транспорта

Вместо полезной нагрузки сервер может вернуть 4-байтовый код ошибки транспорта, например:

  • ошибка разбора кадра;
  • неподдерживаемая версия или формат;
  • переполнение очереди сообщений.

Клиент должен распознавать такие коды и либо переподключаться, либо повторять запрос другим способом. Конкретные коды перечислены в оригинальной статье.

Транспортная обфускация

Цель — скрыть характерные сигнатуры (0xef, 0xeeeeeeee, 0xdddddddd) от наблюдателя.

  1. Клиент готовит 64 случайных байта (init) с ограничениями: первый байт не равен 0xef; первые 4 байта не совпадают ни с одной из известных сигнатур (включая сигнатуры других транспортов и ASCII-представления «HEAD», «POST», «GET », «OPTI»); первые 8 байт не нулевые.
  2. Байты 56–63 заменяются копией первых 8 байт, после чего первые 4 байта перезаписываются сигнатурой выбранного формата (например, 0xdddddddd).
  3. Из получившейся последовательности выводятся ключ и вектор инициализации потокового шифра для каждой из сторон; сам блок init отправляется серверу в зашифрованном виде.
  4. Сервер восстанавливает ключи из полученных 64 байт; весь дальнейший поток в обе стороны шифруется этим шифром.

После установки обфускации стороны обмениваются обычными кадрами выбранного формата, но их содержимое дополнительно зашифровано потоковым шифром.

Рекомендации

  • Используйте padded intermediate с обфускацией: такое сочетание устойчивее к фильтрации трафика по сигнатурам и размерам.
  • Не переиспользуйте init между соединениями.
  • Проверяйте, что первый ответ сервера корректно расшифровывается: если нет — сервер не поддерживает выбранный режим либо соединение искажается промежуточным оборудованием.
