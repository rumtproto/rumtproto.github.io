Мобильный протокол: подробное описание #

Начиная с версии 4.6 основные клиенты Telegram используют MTProto 2.0. MTProto v.1.0 устарел и постепенно выводится из обращения.¶

Эта статья описывает базовый слой протокола MTProto версии 2.0 (облачные чаты, шифрование между сервером и клиентом). Основные отличия от версии 1.0 (описана здесь для справки) таковы:¶

  • вместо SHA-1 используется SHA-256;
  • байты дополнения (padding) участвуют в вычислении msg_key;
  • msg_key зависит не только от шифруемого сообщения, но и от части auth_key;
  • вместо 0..15 байт дополнения, как в v.1.0, используется 12..1024 байта.

Смотрите также: MTProto 2.0: секретные чаты, сквозное шифрование¶

Описание протокола #

Прежде чем сообщение (или составное сообщение) будет передано по сети с помощью транспортного протокола, оно определённым образом шифруется, а в его начало добавляется внешний заголовок, состоящий из 64-битного идентификатора ключа auth_key_id (он однозначно определяет авторизационный ключ как для сервера, так и для пользователя) и 128-битного ключа сообщения msg_key (значение, вычисляемое по содержимому сообщения и участвующее в выработке ключа шифрования).¶

Авторизационный ключ auth_key (долговременный общий секрет клиента и сервера) вместе с ключом сообщения msg_key задают собственно 256-битный ключ aes_key и 256-битный вектор инициализации aes_iv, которыми сообщение шифруется алгоритмом AES-256 в режиме infinite garble extension (IGE). Обратите внимание, что начальная часть шифруемого сообщения содержит переменные данные (сессия, идентификатор сообщения, порядковый номер, серверная соль), которые, очевидно, влияют на ключ сообщения (а значит, и на ключ AES с вектором инициализации). В MTProto 2.0 ключом сообщения считаются 128 средних бит SHA-256 от тела сообщения (включая сессию, идентификатор сообщения, дополнение и прочее), перед которым дописаны 32 байта, взятые из авторизационного ключа. В более старом MTProto 1.0 ключ сообщения вычислялся как младшие 128 бит SHA-1 от тела сообщения, без учёта байтов дополнения.¶

Составные сообщения шифруются как одно целое сообщение.¶

Остались вопросы по этой схеме? — Загляните в расширенный FAQ!¶

Примечание 1 #

Каждое открытое сообщение, шифруемое в MTProto, всегда содержит следующие данные, которые проверяются при расшифровке, — это делает систему устойчивой к известным проблемам используемых компонентов:¶

  • серверная соль (64 бита)
  • идентификатор сессии
  • порядковый номер сообщения
  • длина сообщения
  • время
Примечание 2 #

Секретные чаты Telegram со сквозным шифрованием используют дополнительный слой шифрования поверх описанного выше. Подробности — в статье Секретные чаты, сквозное шифрование.¶

MTProto поддерживает Perfect Forward Secrecy (совершенную прямую секретность) как в облачных чатах, так и в секретных чатах.¶

Терминология #

Авторизационный ключ (auth_key) #

Ключ длиной 2048 бит, общий для клиентского устройства и сервера. Он создаётся при регистрации пользователя непосредственно на устройстве путём обмена ключами по Диффи — Хеллману и никогда не передаётся по сети. Каждый авторизационный ключ привязан к конкретному пользователю. Ничто не мешает пользователю иметь несколько ключей (они соответствуют «постоянным сессиям» на разных устройствах), причём часть из них может быть заблокирована навсегда, если устройство утеряно. Смотрите также Создание авторизационного ключа.¶

Ключ сервера #

RSA-ключ длиной 2048 бит, которым сервер подписывает собственные сообщения, пока идёт регистрация и вырабатывается авторизационный ключ. В приложение встроен открытый ключ сервера: с его помощью можно проверить подпись, но нельзя подписывать сообщения. Закрытый ключ сервера хранится на сервере и меняется очень редко.¶

Идентификатор ключа (auth_key_id) #

Младшие 64 бита SHA1-хеша авторизационного ключа служат указанием на то, каким именно ключом зашифровано сообщение. Ключи обязаны однозначно определяться младшими 64 битами своего SHA1, и в случае коллизии авторизационный ключ вырабатывается заново. Нулевой идентификатор ключа означает, что шифрование не используется; это допустимо для ограниченного набора типов сообщений, применяемых при регистрации для выработки авторизационного ключа в обмене по Диффи — Хеллману. В MTProto 2.0 здесь по-прежнему используется SHA1, поскольку auth_key_id должен определять применённый авторизационный ключ независимо от версии протокола.¶

Сессия #

(Случайное) 64-битное число, которое клиент генерирует, чтобы различать отдельные сессии (session) — например, разные экземпляры приложения, созданные с одним и тем же авторизационным ключом. Сессия вместе с идентификатором ключа соответствует экземпляру приложения. Сервер может хранить состояние сессии. Ни при каких обстоятельствах сообщение, предназначенное для одной сессии, не может быть отправлено в другую. Сервер вправе в одностороннем порядке забыть любые клиентские сессии; клиенты должны быть готовы это обработать.¶

Серверная соль #

(Случайное) 64-битное число (server_salt), которое по требованию сервера меняется каждые 30 минут — отдельно для каждой сессии. Все последующие сообщения обязаны содержать новую соль (хотя сообщения со старой солью принимаются ещё 1800 секунд). Соль нужна для защиты от атак повторного воспроизведения и от некоторых уловок, связанных с переводом часов клиента далеко вперёд.¶

Идентификатор сообщения (msg_id) #

(Зависящее от времени) 64-битное число msg_id, однозначно определяющее сообщение внутри сессии. Идентификаторы клиентских сообщений делятся на 4; идентификаторы серверных сообщений по модулю 4 дают 1, если сообщение служит ответом на клиентское, и 3 в остальных случаях. Идентификаторы клиентских сообщений обязаны монотонно возрастать (в пределах одной сессии), как и идентификаторы серверных, и обязаны примерно равняться unixtime*2^32. Таким образом, идентификатор сообщения указывает на приблизительный момент его создания. Сообщение отклоняется, если прошло более 300 секунд после его создания или если до его создания остаётся более 30 секунд (это нужно для защиты от атак повторного воспроизведения). В такой ситуации его обязательно отправить заново с другим идентификатором (либо поместить в контейнер с большим идентификатором). Идентификатор контейнера обязан быть строго больше идентификаторов вложенных в него сообщений.¶

Важно: для противодействия атакам повторного воспроизведения младшие 32 бита msg_id, передаваемого клиентом, не должны быть пустыми и обязаны представлять дробную часть момента времени, когда сообщение было создано.¶

Порядковый номер сообщения (msg_seqno) #

32-битное число msg_seqno, равное удвоенному количеству значимых по содержимому » сообщений, созданных отправителем до этого сообщения, и увеличенное затем на единицу, если текущее сообщение само значимо по содержимому.¶

Таким образом, seqno значимого по содержимому сообщения равен msg.seqNo = (current_seqno*2)+1 (а после его формирования локальный счётчик current_seqno необходимо увеличить на 1), а seqno сообщения, не значимого по содержимому, равен msg.seqNo = (current_seqno*2) (в этом случае current_seqno увеличивать на 1 не нужно).¶

Следовательно, значимость входящего сообщения MTProto по содержимому легко определить, проверив значение младшего бита его seqno (message.isContentRelated = (message.seqNo & 1) == 1).¶

Контейнер всегда формируется после всего своего содержимого, поэтому его порядковый номер больше или равен порядковым номерам вложенных в него сообщений.¶

Сообщение, значимое по содержимому #

При получении сообщения MTProto, помеченного как значимое по содержимому установленным младшим битом seqno, принимающая сторона обязана каким-либо образом его подтвердить.¶

Если принимающая сторона — клиент, подтверждать обязательно конструкторами msgs_ack.¶

Если принимающая сторона — сервер, обычно он подтверждает конструкторами msgs_ack, но допускается сделать это и ответом метода, ошибкой или иным способом — так, как указано в документации каждого метода или конструктора.¶

При использовании транспорта TCP значимость конструкторов по содержимому влияет на поведение сервера: сервер повторно отправит ещё не подтверждённые значимые по содержимому сообщения в новое соединение, если текущее соединение будет закрыто и затем открыто заново.¶

Клиент всегда обязан помечать все RPC-запросы уровня API как значимые по содержимому, иначе будет выдано bad_msg_notification с error_code=35.¶

Клиент никогда не должен помечать конструкторы msgs_ack, msg_container, msg_copy, gzip_packed (то есть контейнеры — сообщения-обёртки, объединяющие несколько сообщений в одно, — и подтверждения) как значимые по содержимому, иначе будет выдано bad_msg_notification с error_code=34.¶

Клиенту допускается помечать как значимый по содержимому любой другой конструктор, кроме четырёх перечисленных выше, — чтобы повысить надёжность при проблемах с сетью, запрашивая у сервера подтверждения.¶

Ключ сообщения (msg_key) #

В MTProto 2.0 — средние 128 бит SHA-256-хеша шифруемого сообщения (включая внутренний заголовок и байты дополнения для MTProto 2.0), перед которым дописан 32-байтовый фрагмент авторизационного ключа.¶

В MTProto 1.0 ключ сообщения определялся иначе — как младшие 128 бит SHA-1-хеша шифруемого сообщения, причём байты дополнения в вычислении хеша не участвовали. Авторизационный ключ в этом вычислении не использовался.¶

Внутренний (криптографический) заголовок #

Заголовок (16 байт), добавляемый перед сообщением или контейнером до того, как всё это шифруется целиком. Состоит из серверной соли (64 бита) и сессии (64 бита).¶

Внешний (криптографический) заголовок #

Заголовок (24 байта), добавляемый перед зашифрованным сообщением или контейнером. Состоит из идентификатора ключа auth_key_id (64 бита) и ключа сообщения msg_key (128 бит).¶

Полезная нагрузка #

Внешний заголовок + зашифрованное сообщение или контейнер.¶

Вычисление ключа AES и вектора инициализации #

2048-битный авторизационный ключ (auth_key) и 128-битный ключ сообщения (msg_key) используются для вычисления 256-битного ключа AES (aes_key — ключ симметричного шифрования) и 256-битного вектора инициализации (aes_iv — начальный блок для режима шифрования), которыми затем шифруется шифруемая часть сообщения (то есть всё, кроме внешнего заголовка, добавляемого позже) алгоритмом AES-256 в режиме infinite garble extension (IGE).¶

Для MTProto 2.0 алгоритм вычисления aes_key и aes_iv из auth_key и msg_key выглядит так.¶

  • msg_key_large = SHA256 (substr (auth_key, 88+x, 32) + plaintext + random_padding);
  • msg_key = substr (msg_key_large, 8, 16);
  • sha256_a = SHA256 (msg_key + substr (auth_key, x, 36));
  • sha256_b = SHA256 (substr (auth_key, 40+x, 36) + msg_key);
  • aes_key = substr (sha256_a, 0, 8) + substr (sha256_b, 8, 16) + substr (sha256_a, 24, 8);
  • aes_iv = substr (sha256_b, 0, 8) + substr (sha256_a, 8, 16) + substr (sha256_b, 24, 8);

где x = 0 для сообщений от клиента к серверу и x = 8 для сообщений от сервера к клиенту.¶

В устаревшем MTProto 1.0 значения msg_key, aes_key и aes_iv вычислялись иначе (см. этот документ).¶

Младшие 1024 бита auth_key в вычислении не участвуют. Их можно (вместе с остальными битами или отдельно) использовать на клиентском устройстве для шифрования локальной копии данных, полученных от сервера. Младшие 512 бит auth_key на сервере не хранятся, поэтому, если клиентское устройство шифрует ими локальные данные, а пользователь теряет ключ или пароль, расшифровать локальные данные невозможно (даже если данные с сервера удастся получить).¶

В MTProto 1.0, когда алгоритмом AES шифровался блок данных, длина которого не кратна 16 байтам, перед шифрованием данные дополнялись от 0 до 15 случайными байтами дополнения random_padding до длины, кратной 16 байтам. В MTProto 2.0 это дополнение учитывается при вычислении msg_key. Обратите внимание: MTProto 2.0 требует от 12 до 1024 байт дополнения — по-прежнему при условии, что итоговая длина сообщения кратна 16 байтам.¶

Использование MTProto 2.0 вместо MTProto 1.0 #

Клиент может использовать в рамках одного TCP-соединения либо только MTProto 2.0, либо только MTProto 1.0. Сервер определяет используемый протокол по первому полученному от клиента сообщению, после чего применяет то же шифрование для своих сообщений и ожидает, что клиент будет использовать его и дальше. Мы рекомендуем использовать MTProto 2.0; MTProto 1.0 устарел и поддерживается только ради обратной совместимости.¶

Важные проверки #

При получении зашифрованного сообщения обязательно следует проверить, что msg_key действительно равен средним 128 битам SHA-256 расшифрованных данных, перед которыми дописан 32-байтовый фрагмент auth_key, и что msg_id чётен для сообщений от клиента к серверу и нечётен — для сообщений от сервера к клиенту.¶

Кроме того, необходимо хранить идентификаторы (msg_id) последних N сообщений, полученных от другой стороны, и, если приходит сообщение с msg_id меньшим, чем все сохранённые значения, или равным любому из них, такое сообщение игнорируется. В противном случае msg_id нового сообщения добавляется в набор, а если число сохранённых значений msg_id превышает N, самое старое (то есть наименьшее) забывается.¶

Сверх того, следует игнорировать значения msg_id, которые отстоят более чем на 30 секунд в будущее или более чем на 300 секунд в прошлое. Это особенно важно для сервера. Клиенту это тоже полезно (для защиты от атаки повтора), но лишь тогда, когда он уверен в своём времени (например, если оно синхронизировано с временем сервера).¶

Тем не менее некоторые сервисные сообщения от клиента к серверу, содержащие данные, отправленные клиентом серверу (например, msg_id недавнего клиентского запроса), могут обрабатываться на клиенте, даже если время выглядит «неверным». Особенно это касается сообщений о смене server_salt и уведомлений о неверном времени клиента. См. Мобильный протокол: сервисные сообщения.¶

Хранение авторизационного ключа на клиентском устройстве #

Пользователям, обеспокоенным вопросами безопасности, можно предложить защитить авторизационный ключ паролем примерно так же, как это сделано в ssh. Для этого перед ключом дописывается значение криптографической хеш-функции от него, например SHA-256, после чего вся строка целиком шифруется алгоритмом AES в режиме CBC на ключе, равном (текстовому) паролю пользователя. Когда пользователь вводит пароль, сохранённый защищённый ключ расшифровывается и проверяется сверкой значения SHA-256. С точки зрения пользователя это практически не отличается от обычного пароля к приложению или сайту.¶

Незашифрованные сообщения #

Специальные сообщения в открытом виде могут использоваться для создания авторизационного ключа, а также для синхронизации времени. Они начинаются с auth_key_id = 0 (64 бита), что означает отсутствие авторизационного ключа. Сразу за этим следует тело сообщения в сериализованном виде, без внутренних и внешних заголовков. Перед телом сообщения добавляются идентификатор сообщения (64 бита) и длина тела в байтах (32 байта).¶

В открытом виде может передаваться лишь очень ограниченный набор сообщений специальных типов.¶

В оригинале длина тела указана как «32 байта» — это опечатка: поле занимает 32 бита (4 байта), что видно из схемы незашифрованного сообщения ниже, где message_data_length имеет тип int32.¶

Схематичное представление сообщений #

Зашифрованное сообщение #

auth_key_id
int64		msg_key
int128		encrypted_data
bytes

Зашифрованное сообщение: encrypted_data #

Содержит шифротекст следующих данных:¶

salt
int64		session_id
int64		message_id
int64		seq_no
int32		message_data_length
int32		message_data
bytes		padding12..1024
bytes

Незашифрованное сообщение #

auth_key_id = 0
int64		message_id
int64		message_data_length
int32		message_data
bytes

MTProto 2.0 использует от 12 до 1024 байт дополнения (padding) вместо 0..15 байт, применявшихся в MTProto 1.0¶

Создание авторизационного ключа #

Обычно авторизационный ключ создаётся для каждого пользователя один раз — при установке приложения, непосредственно перед регистрацией. На деле сама регистрация происходит уже после создания авторизационного ключа. Тем не менее пользователю можно предложить заполнить регистрационную форму, пока ключ генерируется в фоне. Интервалы между нажатиями клавиш пользователем можно использовать как источник энтропии для получения качественных случайных чисел, необходимых при создании авторизационного ключа.¶

Смотрите Создание авторизационного ключа.¶

В ходе создания авторизационного ключа клиент получает свою серверную соль (её предстоит использовать вместе с новым ключом для всего обмена данными в ближайшее время). Затем клиент создаёт зашифрованную сессию на только что сгенерированном ключе, и весь дальнейший обмен (включая передачу регистрационных данных пользователя и проверку номера телефона) идёт внутри этой сессии — пока клиент не создаст новую. Клиент вправе в любой момент создать новую или дополнительную сессию, выбрав новый случайный идентификатор сессии session_id.¶
