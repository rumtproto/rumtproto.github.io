Транспортные протоколы #

Обеспечивают доставку зашифрованных контейнеров вместе с внешним заголовком (далее — Payload, полезная нагрузка: готовые к передаче байты, которые транспорт переносит как есть) от клиента к серверу и обратно. Определено несколько транспортных протоколов:¶

  • TCP
  • WebSocket
  • WebSocket поверх HTTPS
  • HTTP
  • HTTPS

Для подключения к адресам (endpoint) WebSocket и HTTP используется следующий формат URI:¶

  • Формат URI
    • Формат URI для TLS

TCP #

Транспорт TCP устроен предельно просто: полезная нагрузка, сформированная выбранным транспортом MTProto, передаётся по обычному TCP-сокету через порт 80, 443, 5222 или другой (иной номер порта может вернуть help.getConfig).
Учтите: если у dcOption установлен флаг this_port_only, клиент обязан использовать только указанный порт и не пробовать никакие другие.
Учтите также: если в config установлен флаг force_try_ipv6, клиент обязан отдавать предпочтение IPv6 перед IPv4 для всех транспортов MTProto, даже если доступно соединение по IPv4.¶

Разбиение потока на кадры берёт на себя выбранный транспортный протокол MTProto.¶

Для транспорта TCP не существует неявных подтверждений: все сообщения обязаны подтверждаться явно. Чаще всего подтверждения помещаются в контейнер вместе со следующим запросом или ответом, если тот отправляется в ближайшее время. Например, так почти всегда происходит с клиентскими сообщениями, содержащими RPC-запросы: подтверждение обычно приходит вместе с RPC-ответом.¶

WebSocket #

Транспорт WebSocket реализуется практически так же, как TCP: к выбранному серверу MTProto устанавливается соединение WebSocket через порт 80 с использованием указанного формата URI.¶

Примечание: заголовок Sec-WebSocket-Protocol: binary обязан присутствовать в данных рукопожатия.¶

Разбиение полезной нагрузки на кадры по-прежнему выполняет выбранный транспортный протокол MTProto, а не сообщения WebSocket: длина полезной нагрузки MTProto задаётся транспортным протоколом MTProto, а не длиной отдельных сообщений WebSocket. Проще говоря, все данные, принимаемые и отправляемые через сообщения WebSocket, следует рассматривать как единый дуплексный поток байтов — точно так же, как в случае с TCP.¶

При использовании транспорта WebSocket обязательна обфускация транспорта. Ошибки транспорта передаются обычным способом, как и в TCP. Код закрытия WebSocket всегда будет равен 1000 (нормальное закрытие), независимо от фактического статуса завершения. Во всех случаях строка описания — это настоящий код ошибки в десятичной записи (возможно, дополненный пробелами спереди или сзади до постоянной длины), и её можно спокойно игнорировать.¶

Пример реализации: MadelineProto.¶

WebSocket поверх HTTPS #

Чтобы установить соединение WebSocket поверх HTTPS, достаточно воспользоваться форматом URI для TLS. Всё остальное совпадает с обычным WebSocket.¶

Примечание: заголовок Sec-WebSocket-Protocol: binary обязан присутствовать в данных рукопожатия.¶

HTTP #

Примечание: при разработке браузерных клиентов вместо HTTP рекомендуется транспорт WebSocket — благодаря полнодуплексной потоковой логике, близкой к TCP; это избавляет от необходимости в длинном опросе поверх HTTP (long polling — приём, при котором запрос удерживается открытым, пока не появятся данные) и от связанных с ним задержек при передаче RPC-ответов.¶

Реализуется поверх HTTP/1.1 (с keepalive), работающего через традиционный TCP-порт 80. Можно использовать и HTTPS.¶

Разбиение сообщений на кадры не выполняется транспортными протоколами MTProto — им занимается сам протокол HTTP. Ошибки транспорта тоже передаются не обычным способом: они просто возвращаются как обычные коды состояния HTTP.¶

HTTP-соединение привязывается к сессии — session здесь означает контекст обмена сообщениями между клиентом и сервером, — а точнее, к паре «сессия + идентификатор ключа», указанной в последнем полученном пользовательском запросе; как правило, сессия одна и та же во всех запросах, но хитрые HTTP-прокси могут это нарушить. Сервер вправе вернуть сообщение в HTTP-соединение, только если оно относится к той же сессии и только если сейчас очередь сервера (то есть от клиента получен HTTP-запрос, на который ответ ещё не отправлен).¶

Общая схема работы такова. Клиент открывает к серверу одно или несколько keepalive-соединений HTTP или HTTPS. Если требуется отправить одно или несколько сообщений, из них формируется payload, после чего выполняется POST-запрос к URL/api, куда эта нагрузка передаётся в качестве данных. Кроме того, допустимы HTTP-заголовки Content-Length, Keepalive и Host.¶

Получив запрос, сервер может либо немного подождать (если запрос требует ответа по истечении короткого тайм-аута), либо сразу вернуть ответ-заглушку (лишь подтверждающий получение контейнера). В любом случае ответ может содержать произвольное число сообщений. Одновременно сервер вправе отправить любые другие сообщения, которые он придерживал для этой сессии.¶

Кроме того, существует особый RPC-запрос длинного опроса (действителен только для HTTP-соединений), передающий максимальный тайм-аут T. Если у сервера есть сообщения для этой сессии, они возвращаются немедленно; в противном случае происходит переход в состояние ожидания — до тех пор, пока у сервера не появится сообщение для клиента или пока не истекут T секунд. Если за T секунд ничего не произошло, возвращается ответ-заглушка (специальное сообщение).¶

Когда серверу нужно отправить сообщение клиенту, он ищет HTTP-соединение, которое принадлежит нужной сессии и находится в состоянии «отвечаю на HTTP-запрос» (включая длинный опрос); найдя такое, он добавляет сообщение в контейнер ответа для этого соединения и отправляет пользователю. В типичном случае сервер выдерживает небольшую дополнительную паузу (50 миллисекунд) — на случай, если вскоре у него появятся ещё сообщения для этой сессии.¶

Если подходящего HTTP-соединения нет, сообщения помещаются в очередь отправки текущей сессии. Впрочем, они попадают туда в любом случае и лежат там, пока клиент явно не подтвердит получение. Для всех протоколов клиент обязан вернуть явное подтверждение в разумный срок (его можно добавить в контейнер вместе со следующим запросом).¶

Важно: если подтверждение не приходит вовремя, сообщение может быть отправлено повторно (возможно, уже в другом контейнере). Стороны обязаны быть готовы к этому самостоятельно и обязаны хранить идентификаторы последних полученных сообщений (а такие дубликаты — игнорировать, а не выполнять действие ещё раз). Чтобы не хранить идентификаторы вечно, предусмотрены специальные сообщения сборки мусора, использующие монотонность идентификаторов сообщений.¶

Если очередь отправки переполняется или если сообщения находятся в ней дольше 10 минут, сервер их забывает. Это может произойти и раньше, если у сервера заканчивается место в буферах (например, из-за серьёзных проблем с сетью, приведших к разрыву большого числа соединений).¶

HTTPS #

Чтобы установить соединение поверх HTTPS, достаточно использовать формат URI для TLS. Всё остальное — так же, как при обычном HTTP.¶

Формат URI #

При подключении к обычным адресам WebSocket и HTTP обязательно применять следующий формат URI:¶

http://X.X.X.X:80/api(w)(s)

Кроме того, допускается следующий URI — но только для адресов HTTP и защищённого WebSocket (для обычных соединений WebSocket он непригоден):¶

http://(name)(-1).web.telegram.org:80/api(w)(s)(_test)

Флаг w добавляется, когда требуются заголовки CORS для подключения из браузера.
Флаг s включает API WebSocket.
Подстановка name в доменном варианте задаёт идентификатор дата-центра (DC), к которому выполняется подключение:¶

  • pluto => DC 1
  • venus => DC 2
  • aurora => DC 3
  • vesta => DC 4
  • flora => DC 5

К имени дата-центра можно дописать -1, чтобы повысить предел одновременных запросов к одному имени хоста.
Флаг _test при подключении к доменному варианту URL указывает, что подключаться следует к тестовым дата-центрам.¶

Формат URI для TLS #

При подключении к адресам HTTPS и WSS через порт 443 можно использовать только URI с доменным именем:¶

https://(name)(-1).web.telegram.org:443/api(w)(s)(_test)

Пояснения к подстановкам смотрите в разделе Формат URI.¶

Примеры реализаций: tdlib, MadelineProto (сторона клиента), MTProxy (сторона сервера).¶
