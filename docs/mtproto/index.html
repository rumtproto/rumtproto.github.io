MTProto — обзор протокола

MTProto — собственный криптографический протокол обмена сообщениями, разработанный для Telegram. Он описывает, как клиент обменивается данными с серверами Telegram: как устанавливается шифрование, как сериализуются и упаковываются сообщения, как они передаются по сети и как подтверждаются.

Эта страница — оригинальное русскоязычное изложение устройства протокола, подготовленное для офлайн-справочника. Английский первоисточник: core.telegram.org/mtproto. Названия всех сущностей протокола сохранены без перевода; при первом упоминании даётся пояснение.

Из чего состоит протокол

Протокол логически делится на три части:

  1. Компонент высокого уровня (RPC query language) — язык запросов/ответов. На этом уровне клиент вызывает методы API (например, отправить сообщение) и получает результаты. Формально это язык TL — формальный язык описания типов и функций, принятый в Telegram: каждый запрос и ответ описывается типизированными конструкторами из схемы. Справочник всех методов — здесь, конструкторов — здесь.

  2. Криптографический (авторизационный) слой — отвечает за установку общего секрета между клиентом и сервером и шифрование каждого сообщения. Ключевые понятия:

    • auth_key (авторизационный ключ) — долговременный общий ключ длиной 2048 бит, который клиент и сервер совместно вырабатывают обменом Диффи–Хеллмана и затем используют для шифрования всей переписки. Как он создаётся — см. Создание авторизационного ключа.
    • server_salt (соль сервера) — периодически меняющееся значение, участвующее в шифровании и защищающее от ряда атак.
    • session (сессия) — логическое соединение клиента с сервером в рамках одного ключа auth_key; у сессии есть session_id.

  3. Транспортный компонент — как байты зашифрованных сообщений переносятся по сети: TCP, HTTP, WebSocket и их варианты. См. Транспорты и MTProto-транспорты.

Общий принцип обмена

  • Клиент и сервер обмениваются сообщениями (не «пакетами запрос-ответ» в привычном смысле): каждое сообщение сериализуется, шифруется и передаётся в транспортном контейнере.
  • Сообщение либо требует ответа, либо нет. Подтверждения доставки (ack) передаются отдельными служебными сообщениями — см. Сервисные сообщения и Сообщения о сообщениях.
  • Идентификатор сообщения message_id жёстко привязан ко времени: по нему стороны синхронизируют часы и отсеивают повторы. См. Подробное описание.
  • Несколько сообщений могут упаковываться в один контейнер (msg_container), чтобы уменьшить число транспортных передач.

Схемы и версии

  • Текущая версия — MTProto 2.0 (используется с 2017 года). Версия 1.0 (описание v1) устарела и не рекомендуется к реализации.
  • Для обмена используется несколько «слоёв» схемы:
    • основная схема API — справочник схемы;
    • схема слоя протокола — схема MTProto;
    • схема секретных чатов (сквозное шифрование между пользователями) — схема end-to-end.
  • Машиночитаемые версии схем в формате JSON: API, MTProto, end-to-end.

Безопасность

Клиент обязан выполнять ряд проверок при генерации ключа и расшифровке сообщений — их перечень собран в Рекомендациях по безопасности. Сквозное шифрование секретных чатов устроено отдельно и описано в Секретных чатах; там же — механизм Perfect Forward Secrecy.
