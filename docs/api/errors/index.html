Обработка ошибок #

При работе с API неизбежно возникают ошибки, и клиент обязан корректно их обрабатывать.
Ошибка описывается несколькими параметрами:¶

Код ошибки #

Числовое значение, аналогичное статусу HTTP. Несёт информацию о типе произошедшей ошибки: например, ошибка введённых данных, ошибка приватности или ошибка сервера. Это обязательный параметр.¶

Тип ошибки #

Строковый литерал вида /[A-Z_0-9]+/, кратко описывающий суть проблемы. Например, AUTH_KEY_UNREGISTERED. Это необязательный параметр.¶

База данных ошибок #

Полный список RPC-ошибок, которые могут вернуть все методы API, в удобном для чтения формате JSON доступен по постоянной ссылке /api/errors.json »; ниже описаны его поля:¶

  • errors — все сообщения и коды ошибок для каждого метода (объект).
    • Ключи: коды ошибок в виде строк (числовые строки)
    • Значения: все сообщения об ошибках для каждого метода (объект)
      • Ключи: сообщения об ошибках (строка)
      • Значения: массив методов, которые могут вернуть эту ошибку (массив строк; может быть пустым для ошибок, которые может вернуть любой метод)
  • descriptions — описания для каждой ошибки, упомянутой в errors (а также для некоторых других ошибок, не привязанных к конкретному методу)
    • Ключи: сообщения об ошибках
    • Значения: описания ошибок
  • user_only — полный список методов, которыми могут пользоваться только пользователи, но не боты.
  • bot_only — полный список методов, которыми могут пользоваться только боты, но не пользователи.
  • business_supported — полный список методов, которые боты могут вызывать через бизнес-подключение с помощью invokeWithBusinessConnection.
  • unauthed_allowed — полный список методов, доступных соединениям, которые ещё не выполнили вход.
  • layer — номер слоя, то есть версии схемы TL (целое число).

Сообщения об ошибках и их описания могут содержать подстановки в стиле printf в ключевых позициях; пока используется только %d — он сопоставляет длительности из сообщений об ошибках с их описаниями.¶

Пример:¶

{
    "errors": {
        "420": {
            "2FA_CONFIRM_WAIT_%d": [
                "account.deleteAccount"
            ],
            "SLOWMODE_WAIT_%d": [
                "messages.forwardMessages",
                "messages.sendInlineBotResult",
                "messages.sendMedia",
                "messages.sendMessage",
                "messages.sendMultiMedia"
            ]
        }
    },
    "descriptions": {
        "2FA_CONFIRM_WAIT_%d": "Since this account is active and protected by a 2FA password, we will delete it in 1 week for security purposes. You can cancel this process at any time, you'll be able to reset your account in %d seconds.",
        "SLOWMODE_WAIT_%d": "Slowmode is enabled in this chat: wait %d seconds before sending another message to this chat.",
        "FLOOD_WAIT_%d": "Please wait %d seconds before repeating the action."
    },
    "user_only": [
        "account.deleteAccount"
    ],
    "bot_only": [
        "messages.setInlineBotResults"
    ],
    "business_supported": [
        "messages.sendMessage"
    ],
    "unauthed_allowed": [
        "auth.sendCode"
    ],
    "layer": 224
}

Проверки ради удобства пользователя #

Обратите внимание: информация о пирах (peer — собеседник, чат или канал, с которым ведётся работа) и прочие данные из локального кеша служат ещё и для удобства пользователя, то есть позволяют сразу запретить операцию, которая по этим данным недопустима, вместо того чтобы выполнить её и затем показать ошибку.¶

Такие улучшения следует реализовать всем клиентам, однако сервер в любом случае не даст пользователю выполнить недопустимую операцию и вернёт подходящую RPC-ошибку — ведь иногда недопустимую операцию всё же удаётся инициировать, даже если локальная проверка реализована (см. ниже).¶

Помимо запрета недопустимых операций на стороне клиента, клиентам следует всегда показывать локализованные версии ошибок, возвращаемых сервером (из числа перечисленных в JSON-файле, который можно скачать со страницы RPC-ошибок), чтобы пользователь понимал, почему попытка выполнить операцию не удалась.¶

Иначе говоря, если клиент не предотвратил неудачный вызов метода локально по одной из причин:¶

  • он не реализует локальную проверку ради простоты либо
  • он реализует локальную проверку, но:
    • устаревшие данные о пире указывали, что действие допустимо, тогда как на деле оно уже недопустимо
    • сервер прислал обновление данных о пире, но оно не успело примениться из-за (неизбежной!) гонки между отправкой обновления сервером и отправкой запроса клиентом.
    • по иным неуказанным причинам (новая проверка, введённая новой возможностью в одном из будущих слоёв, и т. п.)

…ему всё равно следует сообщить пользователю, почему запрос не удался, опираясь на описание RPC-ошибки (если оно есть в базе данных ошибок JSON; в противном случае — показав саму RPC-ошибку).¶

Конструкторы ошибок #

Следует предусмотреть механизм обработки ошибок, возвращаемых в конструкторах rpc_error.¶

Ниже приведён список кодов ошибок и их значений:¶

303 SEE_OTHER #

Запрос необходимо повторить, направив его в другой дата-центр.¶

Примеры ошибок: #

  • FILE_MIGRATE_X: запрашиваемый файл в данный момент хранится в другом дата-центре.
  • PHONE_MIGRATE_X: номер телефона, который пользователь пытается использовать для авторизации, привязан к другому дата-центру.
  • NETWORK_MIGRATE_X: IP-адрес источника привязан к другому дата-центру (при регистрации)
  • USER_MIGRATE_X: пользователь, от имени которого выполняются запросы, привязан к другому дата-центру (при регистрации)

Во всех этих случаях строковый литерал с описанием ошибки содержит номер дата-центра (вместо X), в который нужно отправить повторный запрос. Подробнее о перенаправлениях между дата-центрами »¶

400 BAD_REQUEST #

Запрос содержит ошибки. Если запрос был сформирован из формы и содержит введённые пользователем данные, следует сообщить пользователю, что данные нужно исправить, прежде чем повторять запрос.¶

Примеры ошибок: #

  • FIRSTNAME_INVALID: Некорректное имя
  • LASTNAME_INVALID: Некорректная фамилия
  • PHONE_NUMBER_INVALID: Некорректный номер телефона
  • PHONE_CODE_HASH_EMPTY: Отсутствует phone_code_hash
  • PHONE_CODE_EMPTY: Отсутствует phone_code
  • PHONE_CODE_EXPIRED: Срок действия кода подтверждения истёк
  • API_ID_INVALID: Некорректное сочетание api_id/api_hash
  • PHONE_NUMBER_OCCUPIED: Номер телефона уже используется
  • PHONE_NUMBER_UNOCCUPIED: Номер телефона ещё не используется
  • USERS_TOO_FEW: Недостаточно пользователей (например, для создания чата)
  • USERS_TOO_MUCH: Превышено максимальное число пользователей (например, при создании чата)
  • TYPE_CONSTRUCTOR_INVALID: Некорректный конструктор типа
  • FILE_PART_INVALID: Некорректный номер части файла
  • FILE_PARTS_INVALID: Некорректное количество частей файла
  • FILE_PART_X_MISSING: Часть X файла (где X — число) отсутствует в хранилище
  • MD5_CHECKSUM_INVALID: Контрольные суммы MD5 не совпадают
  • PHOTO_INVALID_DIMENSIONS: Некорректные размеры фотографии
  • FIELD_NAME_INVALID: Поле с именем FIELD_NAME некорректно
  • FIELD_NAME_EMPTY: Поле с именем FIELD_NAME отсутствует

401 UNAUTHORIZED #

Неавторизованная попытка воспользоваться возможностями, доступными только авторизованным пользователям.¶

Примеры ошибок: #

  • AUTH_KEY_UNREGISTERED: Ключ не зарегистрирован в системе
  • AUTH_KEY_INVALID: Некорректный ключ
  • USER_DEACTIVATED: Пользователь удалён либо деактивирован
  • SESSION_REVOKED: Авторизация аннулирована, поскольку пользователь завершил все сессии
  • SESSION_EXPIRED: Срок действия авторизации истёк
  • AUTH_KEY_PERM_EMPTY: Метод недоступен для временного авторизационного ключа, не привязанного к постоянному

403 FORBIDDEN #

Нарушение приватности. Например, попытка написать сообщение тому, кто занёс текущего пользователя в чёрный список.¶

404 NOT_FOUND #

Попытка обратиться к несуществующему объекту, например к несуществующему методу.¶

406 NOT_ACCEPTABLE #

Аналогично 400 BAD_REQUEST, но приложение обязано показать ошибку пользователю несколько иначе.
При получении конструктора rpc_error не следует показывать пользователю какое-либо видимое сообщение об ошибке: вместо этого нужно дождаться обновления updateServiceNotification и обработать его обычным образом.
По сути, сразу после выдачи ошибки 406 rpc_error независимо будет отправлено обновление updateServiceNotification с типом popup (то есть НЕ как конструктор Updates внутри rpc_result, а как обычное обновление): это обновление и будет содержать локализованный текст ошибки, который нужно показать пользователю во всплывающем окне.¶

Исключение составляет ошибка AUTH_KEY_DUPLICATED: она возвращается только тогда, когда какой-либо немедийный DC обнаруживает, что авторизованная сессия (session — сеанс работы с аккаунтом; что именно понимается под сессией здесь, уточнено ниже) параллельно отправляет запросы по двум разным TCP-соединениям — с одного и того же или с разных IP-адресов.
Обратите внимание, что для медийных DC параллельные соединения по-прежнему разрешены и даже рекомендуются.
Учтите также, что под сессией здесь понимается сессия входа в аккаунт, описываемая конструктором authorization и получаемая через account.getAuthorizations, а не сессия MTProto.¶

Иными словами, основное соединение с немедийным DC обычно допускает лишь одну сессию MTProto: эту ошибку вызывает открытие дополнительных параллельных основных сессий (то есть нескольких значений session_id — идентификаторов сессии — поверх одного авторизационного ключа либо нескольких TCP-соединений с основным DC).
Впрочем, сервер может явно разрешить несколько параллельных основных сессий, объявив значение tmp_sessions больше 1 в конструкторах config/auth.authorization (см. параллельные сессии »); тогда без появления ошибки AUTH_KEY_DUPLICATED допустимо открыть не больше указанного числа параллельных основных сессий. Если tmp_sessions отсутствует или ≤ 1, обязательно использовать одну основную сессию.
Выделенные сессии для передачи файлов на медийных DC под это ограничение не подпадают и всегда могут открываться параллельно.¶

Если клиент получил ошибку AUTH_KEY_DUPLICATED, значит сессия уже аннулирована сервером и пользователю необходимо сгенерировать новый авторизационный ключ и войти в аккаунт заново.¶

420 FLOOD #

Превышено максимально допустимое число попыток вызвать данный метод с данными входными параметрами — сервер отвечает ожиданием из-за флуда (FLOOD_WAIT) и требует выждать указанное время, прежде чем повторять запрос. Например, при попытке запросить большое количество текстовых сообщений (SMS) для одного и того же номера телефона.¶

Пример ошибки: #

  • FLOOD_WAIT_X: требуется подождать X секунд (где X — число)
  • FLOOD_PREMIUM_WAIT_X: требуется подождать X секунд (где X — число); пользователь также может приобрести подписку Telegram Premium, чтобы снять это ограничение. Подробнее об обработке этой ошибки см. здесь ».

500 INTERNAL #

При обработке запроса произошла внутренняя ошибка сервера — например, сбой при обращении к базе данных или к файловому хранилищу.¶

Если клиент получил ошибку 500 или если вы считаете, что эта ошибка не должна была возникнуть, соберите как можно больше сведений о запросе и об ошибке и передайте их разработчикам.¶

Прочие коды ошибок #

Если сервер вернул ошибку с кодом, не перечисленным выше, её допускается считать эквивалентом ошибки 500 и обрабатывать как внутреннюю ошибку сервера.¶
