Получение обновлений

Оригинальное русскоязычное описание того, как клиент получает и не теряет события сервера. Первоисточник: core.telegram.org/api/updates.

Обновления (Update) — это события: новые сообщения, изменение чатов и пользователей, статусы «печатает», прочтения и т.д. Клиент обязан обрабатывать их надёжно: без пропусков, без повторов и в правильном порядке.

Как обновления приходят

  1. В ответах на запросы. Многие методы возвращают Updates — вместе с результатом приходит пачка обновлений (например, в ответ на отправку сообщения приходит обновление с его данными).
  2. Серверными уведомлениями. В любой момент сервер может прислать одно из:
    • updatesTooLong — «произошло слишком много событий, запросите разницу сами»;
    • updateShortMessage / updateShortChatMessage — одно сообщение;
    • updateShort — одно обновление;
    • updatesCombined / updates — пачка обновлений с пользователями и чатами.

Счётчики и обнаружение пропусков

У каждой «очереди» событий есть свой монотонный счётчик:

  • pts (persistent timestamp) — для сообщений и большинства событий;
  • qts — для очереди секретных чатов;
  • date — время события;
  • seq — устаревший общий счётчик (в современных клиентах полагаться на него не стоит).

Правила обработки:

  1. Хранить последние применённые pts/qts (и date) по каждой очереди.
  2. У каждого входящего обновления известен новый pts и «вес» pts_count; если новый pts != сохранённый + pts_count — в очереди пропуск: нужно запросить разницу.
  3. Разница запрашивается updates.getDifference (или updates.getChannelDifference для каналов); сервер вернёт недостающие события, и цикл продолжается до состояния final.
  4. Клиент должен корректно переживать повторное применение обновлений (например, после перезапуска): уже обработанные сообщения определяются по идентификаторам и пропускаются.

Практические рекомендации

  • Обрабатывайте updatesTooLong как безусловный сигнал «запросить разницу».
  • После переподключения не верьте локальному кэшу: запрашивайте разницу с сохранённого pts.
  • Для очень старых сообщений (вне «окна» серверной очереди) существуют отдельные правила восстановления — см. оригинальный раздел о восстановлении пропусков.
  • Отправка сообщений идемпотентна через random_id: повтор с тем же random_id не создаёт дубликат, а возвращает уже созданное сообщение.
