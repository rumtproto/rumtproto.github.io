Perfect Forward Secrecy #

Связанные статьи #
  • Perfect Forward Secrecy в секретных чатах
  • Рекомендации по безопасности для разработчиков

Эта статья посвящена Perfect Forward Secrecy (совершенной прямой секретности — свойству, при котором компрометация долговременного ключа не позволяет расшифровать перехваченный ранее трафик) в облачных чатах, см. также PFS в секретных чатах.¶

Telegram поддерживает Perfect Forward Secrecy (PFS).¶

Чтобы это стало возможным, клиент вырабатывает постоянный авторизационный ключ (auth_key — долговременный секрет, которым шифруются сообщения) с помощью p_q_inner_data и временный ключ с помощью p_q_inner_data_temp. (Подробнее см. Создание авторизационного ключа.) Эти две операции допускается выполнять параллельно по разным соединениям. Клиент обязан сохранить Unix-метку времени expires_at: expires_at = time + expires_in.¶

Важно: чтобы обеспечить PFS, клиент никогда не должен использовать постоянный auth_key_id напрямую. Каждое сообщение, передаваемое по MTProto, обязано быть зашифровано на temp_auth_key_id (идентификаторе временного ключа), привязанном к perm_auth_key_id (идентификатору постоянного ключа).¶

Непривязанный temp_auth_key_id допускается использовать только со следующими методами:¶

  • auth.bindTempAuthKey
  • help.getConfig
  • help.getNearestDc

Чтобы привязать временный авторизационный ключ к постоянному, клиент формирует специальное сообщение привязки и вызывает метод auth.bindTempAuthKey, используя temp_auth_key. После успешного выполнения auth.bindTempAuthKey клиенту разрешается продолжать работу с API как обычно; кроме того, после каждой привязки клиент обязан заново передать сведения о себе с помощью initConnection.¶

Запрос auth.bindTempAuthKey может также вернуть ошибку ENCRYPTED_MESSAGE_INVALID, которую необходимо обрабатывать так:¶

  • Если и только если постоянный ключ, использованный в запросе, был создан более 60 секунд назад:
    • Удалить и временный, и постоянный ключи.
      Если удалённый постоянный ключ — это основной ключ авторизации (тот, под которым выполнен вход в родной дата-центр (DC) пользователя), значит, пользователь заодно вышел из аккаунта.
    • Заново создать временный и постоянный ключи.
    • Повторить привязку временного ключа к постоянному.
    • В случае успеха, если удалённый ключ не был основным ключом авторизации, заново импортировать авторизацию из родного дата-центра (DC) пользователя.
  • В противном случае — повторить привязку временного и постоянного ключей

Когда срок действия временного ключа истекает, клиенту необходимо выработать новый временный ключ с помощью p_q_inner_data_temp. Затем этот новый временный ключ нужно заново привязать к исходному постоянному ключу. Новый ключ можно выработать и заранее, чтобы к моменту истечения срока действия старого у клиента уже был готов новый.¶

Для дополнительной безопасности клиент может хранить временный авторизационный ключ только в оперативной памяти и никогда не записывать его в постоянное хранилище.¶

Временный авторизационный ключ может перестать действовать в любой момент до expires_at, поскольку на стороне сервера такие ключи тоже хранятся только в оперативной памяти. Будьте готовы корректно обработать возникающие из-за этого ошибки MTProto (несуществующий auth_key_id приводит к ошибке 404).¶

Когда сервер разрешает несколько параллельных основных сессий (session — независимый поток сообщений со своим состоянием; признак — переданное сервером значение tmp_sessions > 1), клиент обязан применять PFS ко всем своим сессиям: каждая сессия вырабатывает собственный временный авторизационный ключ и привязывает его к одному и тому же постоянному ключу.¶
