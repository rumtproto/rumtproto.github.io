Perfect Forward Secrecy #

Telegram поддерживает Perfect Forward Secrecy (PFS — совершенная прямая секретность: компрометация текущего ключа не раскрывает переписку, зашифрованную прежними ключами) в секретных чатах начиная со слоя (layer) 20. См. переход на новые слои.¶

Чтобы сохранить в безопасности прошлую переписку, официальные клиенты Telegram начинают смену ключа, как только на текущем ключе расшифровано и зашифровано более 100 сообщений либо он применяется дольше недели — при условии, что им зашифровано хотя бы одно сообщение. Старые ключи после этого надёжно уничтожаются, и восстановить их нельзя даже при наличии доступа к новым ключам, которые используются сейчас.¶

Любой участник секретного чата может начать смену ключа, как только сочтёт, что текущий ключ используется слишком долго или зашифровал слишком много сообщений. Обратите внимание: не следует запускать новый экземпляр протокола смены ключа, если незавершённый экземпляр уже существует — неважно, какой из сторон он начат.¶

Примечание: сторонние разработчики обязаны обеспечивать такой же уровень безопасности. Все клиенты с поддержкой секретных чатов обязаны уметь инициировать смену ключа и принимать соответствующие сервисные сообщения. См. Рекомендации по безопасности.¶

Протокол смены ключа #

Новые ключи вырабатываются обменом специальными сообщениями, которые шифруются ранее установленными ключами. Протокол смены ключа между сторонами A и B в обычном случае состоит из четырёх шагов:¶

1. decryptedMessageActionRequestKey #

A (инициатор смены ключа) генерирует новое значение a с теми же ограничениями, что и при первоначальном обмене ключами по Диффи–Хеллману, и отправляет B значение pow(g,a) mod p, вложенное в decryptedMessageService:¶

decryptedMessageActionRequestKey#f3c9611b exchange_id:long g_a:bytes = DecryptedMessageAction;
  • exchange_id — случайное число, которым обе стороны опознают именно этот экземпляр протокола смены ключа
  • g_a — значение pow(g,a) mod p

Обратите внимание, что используются те же параметры Диффи–Хеллмана (p,g), что и при первоначальном обмене ключами в этом секретном чате. Передавать их повторно в явном виде не требуется.¶

2. decryptedMessageActionAcceptKey #

Получив описанное выше сервисное сообщение, B проверяет его содержимое и формирует ответ с тем же exchange_id для вновь сгенерированного значения b:¶

decryptedMessageActionAcceptKey#6fe1735b exchange_id:long g_b:bytes key_fingerprint:long = DecryptedMessageAction;
  • exchange_id — тот же, что и в полученном decryptedMessageActionRequestKey
  • g_b — значение pow(g,b) mod p
  • key_fingerprint — 64-битный отпечаток вновь сгенерированного key = pow(g_a, b) mod p, служащий проверкой корректности реализации

На этом этапе B уже может вычислить новый ключ key = pow(g_a, b) mod p и его отпечаток key_fingerprint (последние 64 бита SHA-1 от ключа). Тем не менее до завершения обмена он продолжает пользоваться прежним ключом.¶

Отправив decryptedMessageActionAcceptKey, сторона B уже не может прервать обмен ключами: она обязана быть готова перейти на новый ключ сразу же после получения decryptedMessageActionCommitKey. Поэтому, если B хочет отложить применение нового ключа — например, чтобы сначала заполнить пропуски в нумерации seq_no (последовательный номер сообщения в секретном чате) — она обязана соответствующим образом отложить и ответ decryptedMessageActionAcceptKey.¶

3. decryptedMessageActionCommitKey #

Получив корректный decryptedMessageActionAcceptKey, A выполняет все необходимые проверки и «фиксирует» новый ключ следующим сервисным сообщением:¶

decryptedMessageActionCommitKey#ec2e0b9b exchange_id:long key_fingerprint:long = DecryptedMessageAction;
  • exchange_id — тот же, что и в двух предыдущих сообщениях
  • key_fingerprint — значение хеша (последние 64 бита SHA-1) нового ключа, вычисленного стороной A, для проверки корректности реализации

После этого A может (и обязана) шифровать все последующие сообщения новым ключом.¶

Если сторона A хочет отложить установку нового ключа — например, потому что сначала намерена заполнить имеющиеся пропуски в seq_no, — она обязана соответствующим образом отложить ответ decryptedMessageActionCommitKey.¶

4. Завершающий шаг #

Когда B получает либо decryptedMessageActionCommitKey, либо сообщение, зашифрованное новым ключом и опознанное по значению key_fingerprint, добавленному в начало зашифрованного сообщения (возможна ситуация, когда decryptedMessageActionCommitKey был потерян и будет запрошен повторно позже), она считает, что A перешла на шифрование новым ключом, и поступает так же.¶

Впрочем, прежний ключ допускается хранить, пока в полученных сообщениях остаются пропуски — вплоть до момента перехода на новый ключ. Как только все пропуски заполнены, старый ключ обязан быть надёжно уничтожен.¶

Из этого правила есть одно исключение: SHA-1 исходного ключа (выработанного при установлении данного секретного чата) хранится всегда — он нужен для показа визуализации ключа в клиентах.¶

Прерывание протокола #

Любая из сторон может прервать любой экземпляр незавершённого протокола смены ключа, если только эта сторона ещё не отправила decryptedMessageActionCommitKey или decryptedMessageActionAcceptKey. Чтобы прервать смену ключа, отправьте¶

decryptedMessageActionAbortKey#dd05ec6b exchange_id:long = DecryptedMessageAction;

Это может понадобиться, например, если сторона уже участвует в другом экземпляре протокола смены ключа или если полученные значения g_a, g_b и прочие параметры не проходят проверок безопасности. В последнем случае, возможно, разумнее вообще прервать секретный чат.¶

Уничтожение прежних ключей #

Как только B получает decryptedMessageActionCommitKey, она может безопасно уничтожить прежний ключ — при условии, что пропусков нет. Сторона же A вправе уничтожить прежний ключ только после того, как получит сообщение, зашифрованное новым ключом. Если отправка обычных сообщений не планируется, стороне B следует отправить для этой цели специальное пустое сообщение:¶

decryptedMessageActionNoop#a82fdd63 = DecryptedMessageAction;

Одновременная смена ключа #

Может случиться, что обе стороны одновременно начнут смену ключа, отправив decryptedMessageActionRequestKey и не зная, что то же самое уже сделала другая сторона. Если каждая из них прервёт смену ключа на том основании, что уже участвует в другом экземпляре протокола, начатом ею самой, смена ключа не произойдёт никогда.¶

Из-за такой возможности мы рекомендуем прерывать только тот экземпляр, у которого exchange_id меньше, с возможностью повторно использовать его пару (a,g_a) в экземпляре протокола смены ключа с бо́льшим exchange_id (сравнение выполняется как для типа long, то есть как для знакового 64-битного целого в порядке little-endian).¶

Иначе говоря, если decryptedMessageActionRequestKey получен после того, как A отправила свой decryptedMessageActionRequestKey, но ещё не получила decryptedMessageActionAcceptKey, следует поступить так:¶

  • если exchange_id в отправленном decryptedMessageActionRequestKey больше, чем в только что полученном decryptionActionRequestKey, прервать вновь предложенный экземпляр протокола смены ключа, не отправляя явного decryptedMessageActionAbortKey (другая сторона поступит так же по следующему правилу).
  • если exchange_id в нашем decryptedMessageActionRequestKey меньше, ответить на вновь полученный decryptedMessageActionRequestKey сообщением decryptedMessageActionAcceptKey и участвовать только в том экземпляре протокола смены ключа, который инициирован другой стороной. На этом этапе допускается повторно использовать значение g_a (теперь называемое g_b), сгенерированное для исходного, теперь уже оставленного decryptedMessageActionRequestKey, либо сгенерировать полностью новую пару (b,g_b).
  • в маловероятном (2^{-64}) случае, когда оба exchange_id равны, прервать оба экземпляра, не отправляя явного decryptedMessageActionAbortKey. Другая сторона поступит так же.
Визуализация ключа #

Поскольку все экземпляры смены ключа передаются по защищённому каналу, установленному при создании секретного чата, пользователю необходимо убедиться, что при первоначальном обмене не было атаки типа MITM. Визуализация ключа в клиентах строится из первых 128 бит SHA-1 исходного ключа, созданного при первоначальном установлении секретного чата, за которыми следуют первые 160 бит SHA-256 того ключа, который использовался в момент обновления секретного чата до слоя 46 (совпадает с исходным ключом, если чат был создан на слое 46).¶

Обратите внимание, что параметр key_fingerprint был введён как служебный инструмент (с вводящим в заблуждение названием) и не имеет отношения к визуализации ключа в клиентах.¶
