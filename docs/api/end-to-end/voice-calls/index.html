Сквозное шифрование голосовых звонков #

Этот документ описывает шифрование голосовых звонков в том виде, в каком оно реализовано в приложениях Telegram версий < 7.0. Шифрование, применяемое в голосовых и видеозвонках в версиях приложений, выпущенных 14 августа 2020 года и позже, описано в этом документе.¶

Связанные статьи #
  • Сквозное шифрование в голосовых и видеозвонках
  • Сквозное шифрование в секретных чатах
  • Рекомендации по безопасности для разработчиков клиентов

Установление голосового звонка #

Прежде чем голосовой звонок будет готов, необходимо выполнить ряд предварительных действий. Вызывающая сторона должна связаться с вызываемой стороной и проверить, готова ли та принять звонок. Кроме того, сторонам нужно согласовать используемые протоколы, узнать IP-адреса друг друга или адреса ретрансляционных серверов Telegram (так называемых рефлекторов — промежуточных узлов, которые вслепую пересылают зашифрованные пакеты, когда прямое соединение между сторонами невозможно), а также с помощью обмена ключами Диффи — Хеллмана выработать одноразовый ключ шифрования для этого звонка. Всё это выполняется параллельно при помощи нескольких методов Telegram API и связанных с ними уведомлений. Настоящий документ подробно описывает выработку ключа шифрования. Остальные этапы согласования со временем будут описаны отдельно.¶

Выработка ключа #

Обмен ключами Диффи — Хеллмана, как и весь протокол создания нового голосового звонка, во многом схож с тем, что применяется в секретных чатах. Прежде чем читать дальше, рекомендуется изучить статью по ссылке.¶

Тем не менее в него внесены важные изменения, упрощающие процедуру проверки ключа. Ниже приведён полный обмен данными между двумя взаимодействующими сторонами — вызывающей (A) и вызываемой (B) — через серверы Telegram (S).¶

  • A вызывает messages.getDhConfig, чтобы узнать 2048-битное простое число Диффи — Хеллмана p и генератор g. От клиента ожидается, что он проверит, безопасное ли простое число p, и выполнит все проверки безопасности, необходимые для секретных чатов.
  • A выбирает случайное значение a, 1 < a < p-1, и вычисляет g_a:=power(g,a) mod p (256-байтовое число) и g_a_hash:=SHA256(g_a) (длиной 32 байта).
  • A вызывает (отправляет серверу S) phone.requestCall, где среди прочих есть поле g_a_hash:bytes. При этом вызове данное поле заполняется значением g_a_hash, а не самим g_a.
  • Сервер S выполняет проверки настроек приватности и отправляет обновление updatePhoneCall с конструктором phoneCallRequested на все активные устройства B. Помимо сведений о личности A и прочих значимых параметров, это обновление содержит поле g_a_hash, заполненное полученным от A значением.
  • B принимает звонок на одном из своих устройств, сохраняет полученное значение g_a_hash для этого экземпляра протокола создания голосового звонка, выбирает случайное значение b, 1 < b < p-1, вычисляет g_b:=power(g,b) mod p, выполняет все необходимые проверки безопасности и вызывает метод phone.acceptCall, у которого среди прочих есть поле g_b:bytes — оно заполняется самим значением g_b (а не его хешем).
  • Сервер S отправляет updatePhoneCall с конструктором phoneCallDiscarded на все остальные устройства, авторизованные стороной B, чтобы этот же звонок нельзя было принять ни на одном из них. С этого момента сервер S работает только с тем устройством B, которое первым вызвало phone.acceptCall.
  • Сервер S отправляет стороне A обновление updatePhoneCall с конструктором phoneCallAccepted, содержащее полученное от B значение g_b.
  • A выполняет все обычные проверки безопасности для g_b и a, вычисляет ключ Диффи — Хеллмана key:=power(g_b,a) mod p и его отпечаток key_fingerprint:long, равный младшим 64 битам SHA1(key), — так же, как в секретных чатах. Затем A вызывает метод phone.confirmCall, передавая g_a:bytes и key_fingerprint:long.
  • Сервер S отправляет стороне B обновление updatePhoneCall с конструктором phoneCall, содержащее значение g_a в поле g_a_or_b:bytes и key_fingerprint:long
  • На этом этапе B получает значение g_a. Он проверяет, что SHA256(g_a) действительно равно ранее полученному значению g_a_hash, выполняет все обычные проверки безопасности Диффи — Хеллмана и вычисляет ключ key:=power(g_a,b) mod p и его отпечаток, равный младшим 64 битам SHA1(key). Затем он проверяет, что этот отпечаток совпадает со значением key_fingerprint:long, полученным от другой стороны, — это контрольная проверка корректности реализации.

На этом обмен ключами Диффи — Хеллмана завершён, и у обеих сторон есть общий секретный ключ key длиной 256 байт, которым шифруется весь дальнейший обмен данными между A и B.¶

Крайне важно принимать каждое обновление только один раз для каждого экземпляра протокола выработки ключа, отбрасывая любые дубликаты и альтернативные версии уже полученных и обработанных сообщений (обновлений).¶

Шифрование голосовых данных #

Обе стороны — A (вызывающая) и B (вызываемая) — преобразуют голосовую информацию в последовательность небольших фрагментов, или пакетов, размером не более 1 килобайта каждый. Эта информация шифруется на общем ключе key, выработанном в ходе первоначального обмена, и передаётся другой стороне — либо напрямую (P2P), либо через ретрансляционные серверы Telegram (так называемые рефлекторы). Настоящий документ описывает только процесс шифрования каждого фрагмента, оставляя за скобками кодирование голоса и части, зависящие от сети.¶

Инкапсуляция низкоуровневых голосовых данных #

Низкоуровневый фрагмент данных raw_data:string (закодированный звук без какой-либо обвязки), полученный от голосового кодировщика, сначала инкапсулируется в один из двух конструкторов типа DecryptedDataBlock — по аналогии с типом DecryptedMessage, который используется в секретных чатах:¶

decryptedDataBlock#dbf948c1 random_id:long random_bytes:string flags:# voice_call_id:flags.2?int128 in_seq_no:flags.4?int out_seq_no:flags.4?int recent_received_mask:flags.5?int proto:flags.3?int extra:flags.1?string raw_data:flags.0?string = DecryptedDataBlock;
simpleDataBlock#cc0d0e76 random_id:long random_bytes:string raw_data:string = DecryptedDataBlock;

Здесь out_seq_no — порядковый номер фрагмента среди всех отправленных этой стороной (нумерация начинается с единицы), а in_seq_no — наибольший известный out_seq_no из полученных пакетов. Параметр recent_received_mask — это 32-битная маска, по которой отслеживается доставка последних 32 пакетов, отправленных другой стороной. Бит i установлен, если получен пакет с out_seq_no, равным in_seq_no-i.¶

Старшие 8 бит в flags зарезервированы для нужд нижележащего протокола (того, который формирует и интерпретирует raw_data), и никогда не будут использованы для дальнейших расширений decryptedDataBlock.¶

Параметры voice_call_id и proto обязательны до тех пор, пока другая сторона не подтвердит приём хотя бы одного пакета, прислав пакет с ненулевым in_seq_no. После этого они становятся необязательными, и, если нижележащему протоколу так удобнее, допускается использовать конструктор simpleDataBlock.¶

Параметр voice_call_id (идентификатор голосового звонка — производное от общего ключа значение, одинаковое у обеих сторон) вычисляется из ключа key и равен младшим 128 битам его SHA-256.¶

Строка random_bytes должна содержать не менее 7 байт случайных данных. Поле random_id также содержит 8 случайных байт, которые при необходимости могут служить уникальным идентификатором пакета.¶

Шифрование MTProto #

После инкапсуляции данных в DecryptedDataBlock они сериализуются в TL и шифруются средствами MTProto, причём вместо auth_key (авторизационного ключа, на котором обычно строится шифрование в MTProto) используется key; параметр x следует положить равным 0 для сообщений от A к B и 8 — для сообщений в обратном направлении. Перед зашифрованными данными помещается 128-битный msg_key (ключ сообщения — значение, производное от открытого текста и ключа, из которого выводятся ключ и вектор инициализации AES; как обычно в MTProto), а перед ним — либо 128-битный voice_call_id (при использовании P2P), либо peer_tag (метка стороны — идентификатор, по которому рефлектор понимает, кому переслать пакет; при использовании рефлекторов). Полученный пакет данных отправляется по UDP либо напрямую другой стороне (если возможно соединение P2P), либо на ретрансляционные серверы Telegram (рефлекторы).¶

Проверка ключа #

Чтобы проверить ключ, обе стороны присоединяют к секретному ключу key значение g_a вызывающей стороны ( A ), вычисляют SHA256 и на его основе формируют последовательность эмодзи. Точнее, хеш SHA256 разбивается на четыре 64-битных целых числа; каждое из них делится на общее количество используемых эмодзи (в настоящий момент 333), и по остатку выбирается конкретный эмодзи. Особенности протокола гарантируют, что сравнения четырёх эмодзи из набора в 333 достаточно, чтобы предотвратить прослушивание (атаку «человек посередине» на DH) с вероятностью 0,9999999999.¶

Дело в том, что вместо стандартного обмена ключами Диффи — Хеллмана, которому требуется всего два сообщения между сторонами:¶

  • A->B : (генерирует a и) отправляет g_a := g^a
  • B->A : (генерирует b и настоящий ключ (g_a)^b, после чего) отправляет g_b := g^b
  • A : вычисляет ключ (g_b)^a

мы используем его модификацию с тремя сообщениями, которая хорошо работает, когда обе стороны находятся в сети (что для голосовых звонков и так является обязательным условием):¶

  • A->B : (генерирует a и) отправляет g_a_hash := hash(g^a)
  • B->A : (сохраняет g_a_hash, генерирует b и) отправляет g_b := g^b
  • A->B : (вычисляет ключ (g_b)^a, после чего) отправляет g_a := g^a
  • B : проверяет, что hash(g_a) == g_a_hash, после чего вычисляет ключ (g_a)^b

Смысл здесь в том, что A заранее связывает себя конкретным значением a (и g_a), не раскрывая его стороне B. Стороне B приходится выбирать свои значения b и g_b, не зная настоящего значения g_a, так что она не может перебирать разные значения b, чтобы добиться от итогового ключа (g_a)^b каких-либо особых свойств (например, заранее заданных младших 32 бит SHA256(key)). На этом шаге B связывает себя конкретным значением g_b, не зная g_a. Затем A обязана прислать своё значение g_a; изменить его она уже не может, даже зная теперь g_b, поскольку другая сторона B примет только такое значение g_a, хеш которого был указан в самом первом сообщении обмена.¶

Если некий самозванец выдаёт себя за A или за B и пытается провести атаку «человек посередине» на этот обмен ключами Диффи — Хеллмана, сказанное выше остаётся в силе. Сторона A выработает общий ключ с B — или с тем, кто выдаёт себя за B, — не имея второй попытки изменить свою экспоненту a в зависимости от значения g_b, полученного от другой стороны; а самозванец не сможет подогнать своё значение b под g_a, поскольку обязан зафиксировать значение g_b до того, как узнает g_a. То же самое верно и для выработки ключа между самозванцем и стороной B.¶

Фиксация по хешу в обмене DH оставляет атакующему лишь одну попытку получить в своей атаке правильную визуализацию, а значит, чуть более 33 бит энтропии, представленных четырьмя эмодзи в этой визуализации, достаточно, чтобы сделать успешную атаку крайне маловероятной.¶
