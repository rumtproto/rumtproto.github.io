Подробное описание MTProto

Оригинальное русскоязычное изложение формата зашифрованных сообщений и правил обмена. Английский первоисточник: core.telegram.org/mtproto/description. Термины сохранены без перевода, пояснения даны в скобках и в глоссарии.

Общая структура зашифрованного сообщения

Каждое сообщение, передаваемое после генерации ключа, имеет вид:

auth_key_id (64 бита) | msg_key (128 бит) | зашифрованные данные
  • auth_key_id (идентификатор авторизационного ключа) — 8 байт: нижние 64 бита от SHA1(auth_key). По нему сервер определяет, какой ключ использовать (у клиента может быть несколько ключей — например, по одному на дата-центр).
  • msg_key (ключ сообщения) — 128 бит; вычисляется из содержимого сообщения и auth_key и служит основой для ключа и вектора инициализации AES.
  • Зашифрованные данные — сериализованный открытый текст, зашифрованный AES-256-IGE (IGE, Infinite Garble Extension — режим сцепления блоков, в котором искажение одного блока затрагивает все последующие).

Открытый текст

Внутри шифра находится:

server_salt (64 бита) | session_id (64 бита) | message_id (64 бита) |
seq_no (32 бита) | message_length (32 бита) | тело сообщения
  • server_salt (соль сервера) — 64 бита, периодически меняется сервером; клиент обязан использовать актуальное значение.
  • session_id (идентификатор сессии) — выбирается клиентом при старте сессии; в рамках одной сессии постоянен.
  • message_id — см. ниже.
  • seq_no (sequence number, порядковый номер) — см. ниже.
  • message_length — длина тела в байтах (кратна 4).
  • Тело — сериализованный конструктор схемы (запрос, ответ или служебное сообщение).

Идентификатор сообщения (message_id)

message_id — 64-битное число, жёстко привязанное к часам отправителя:

  • старшие 32 бита — Unix-время отправки;
  • младшие 32 бита — счётчик сообщений, значения которого кратны 4; с каждой новой секундой отсчёт начинается заново.
  • Идентификаторы должны монотонно возрастать; повторное использование идентификатора запрещено.
  • Получатель использует message_id, чтобы отсеивать повторы (запоминая недавние идентификаторы), и для грубой оценки времени.
  • Сервер отклоняет сообщения с идентификаторами, которые сильно отстают от текущего серверного времени или заметно опережают его, — поэтому клиенту необходима синхронизация времени.

Порядковый номер (seq_no)

seq_no связан с делением сообщений на две категории:

  • Связанные с содержимым (content-related) — запросы и уведомления, требующие подтверждения: они увеличивают внутренний счётчик N на единицу; в сообщение записывается значение 2*N + 1 (нечётное).
  • Не связанные с содержимым — подтверждения (msgs_ack), пинги и т.п.: в них записывается 2*N (чётное), счётчик не увеличивается.

Таким образом, по seq_no видно, сколько содержательных сообщений было отправлено в сессии до данного, и это используется в служебных сообщениях о состоянии сообщений.

Контейнеры

Чтобы снизить число передач, несколько сообщений упаковываются в контейнер:

  • Конструктор msg_container содержит список вложенных сообщений; у каждого — свои message_id, seq_no и длина. Сам контейнер содержательным сообщением не считается.
  • Контейнер передаётся и расшифровывается как одно сообщение, но получатель обрабатывает и подтверждает вложенные сообщения по отдельности, по их собственным message_id.
  • Недоставленный контейнер можно отправить повторно целиком. Если же доставлены были не все вложенные сообщения, недостающие запрашивают или пересылают отдельно (см. сообщения о сообщениях).
  • Ограничения: не более 1024 сообщений в одном контейнере; суммарный размер ограничен (порядка 1 МБ); вкладывать контейнер в контейнер нельзя.

Подтверждения (ack)

  • Доставленный запрос/уведомление получатель подтверждает сообщением msgs_ack — список идентификаторов сообщений. Подтверждение не требует ответа.
  • Если отправитель долго не получает ни ответа, ни подтверждения, он может:
    1. повторно отправить сообщение с тем же message_id (если оно ещё не было доставлено);
    2. запросить состояние сообщения служебным сообщением msg_resend_req;
    3. в крайнем случае пересоздать сессию.

Сжатие ответов

Большие ответы сервер может сжимать gzip: вместо полезного тела возвращается конструктор gzip_packed, внутри которого — сериализованный ответ, сжатый алгоритмом gzip. Клиент обязан прозрачно распаковывать такие ответы.

Синхронизация времени

Клиент и сервер имеют собственные часы; чтобы message_id были корректными, клиент должен знать смещение относительно серверного времени:

  • Клиент отправляет ping (для HTTP-транспорта — http_wait) и по message_id ответа и времени его получения вычисляет поправку time_offset = время_сервера − время_клиента и оценку времени оборота (RTT).
  • Смещение рекомендуется измерять регулярно и хранить вместе с «последним известным временем сервера».

Дуплексность и независимость сторон

  • Протокол симметричен: и клиент, и сервер могут отправлять сообщения в любой момент. Серверные уведомления (например, updatesTooLong) приходят без запроса.
  • Соединение может быть разорвано и создано заново; состояние сессии (session_id, счётчики) клиент хранит сам.
  • Одна сессия = одна последовательность seq_no; при пересоздании сессии выбирается новый session_id.

Ошибки

Ошибки уровня RPC возвращаются конструктором rpc_error с кодом и строковым идентификатором ошибки; справочник типовых ошибок описан в разделе ошибок API оригинальной документации. Ошибки транспорта (например, переполнение очереди) возвращаются служебными сообщениями о состоянии.
