# Обработка ошибок

При работе с API неизбежно возникают ошибки, и клиент обязан корректно их обрабатывать.  
Ошибка описывается несколькими параметрами:

#### Код ошибки

Числовое значение, аналогичное статусу HTTP. Несёт информацию о типе произошедшей ошибки: например, ошибка введённых данных, ошибка приватности или ошибка сервера. Это обязательный параметр.

#### Тип ошибки

Строковый литерал вида `/[A-Z_0-9]+/`, кратко описывающий суть проблемы. Например, `AUTH_KEY_UNREGISTERED`. Это необязательный параметр.

#### База данных ошибок

Полный список RPC-ошибок, которые могут вернуть все методы API, в удобном для чтения формате JSON доступен по постоянной ссылке [/api/errors.json »](/api/errors.json/); ниже описаны его поля:

-   `errors` — все сообщения и коды ошибок для каждого метода (объект).
    -   Ключи: коды ошибок в виде строк (числовые строки)
    -   Значения: все сообщения об ошибках для каждого метода (объект)
        -   Ключи: сообщения об ошибках (строка)
        -   Значения: массив методов, которые могут вернуть эту ошибку (массив строк; может быть пустым для ошибок, которые может вернуть любой метод)
-   `descriptions` — описания для каждой ошибки, упомянутой в `errors` (а также для некоторых других ошибок, не привязанных к конкретному методу)
    -   Ключи: сообщения об ошибках
    -   Значения: описания ошибок
-   `user_only` — полный список методов, которыми могут пользоваться только пользователи, но **не** боты.
-   `bot_only` — полный список методов, которыми могут пользоваться только боты, но **не** пользователи.
-   `business_supported` — полный список методов, которые боты могут вызывать через [бизнес-подключение с помощью invokeWithBusinessConnection](/api/bots/connected-business-bots/).
-   `unauthed_allowed` — полный список методов, доступных соединениям, которые ещё не выполнили вход.
-   [@term:layer] `layer` — номер слоя, то есть версии схемы TL (целое число).

Сообщения об ошибках и их описания могут содержать подстановки в стиле `printf` в ключевых позициях; пока используется только `%d` — он сопоставляет длительности из сообщений об ошибках с их описаниями.

Пример:

```
{
    "errors": {
        "420": {
            "2FA_CONFIRM_WAIT_%d": [
                "account.deleteAccount"
            ],
            "SLOWMODE_WAIT_%d": [
                "messages.forwardMessages",
                "messages.sendInlineBotResult",
                "messages.sendMedia",
                "messages.sendMessage",
                "messages.sendMultiMedia"
            ]
        }
    },
    "descriptions": {
        "2FA_CONFIRM_WAIT_%d": "Since this account is active and protected by a 2FA password, we will delete it in 1 week for security purposes. You can cancel this process at any time, you'll be able to reset your account in %d seconds.",
        "SLOWMODE_WAIT_%d": "Slowmode is enabled in this chat: wait %d seconds before sending another message to this chat.",
        "FLOOD_WAIT_%d": "Please wait %d seconds before repeating the action."
    },
    "user_only": [
        "account.deleteAccount"
    ],
    "bot_only": [
        "messages.setInlineBotResults"
    ],
    "business_supported": [
        "messages.sendMessage"
    ],
    "unauthed_allowed": [
        "auth.sendCode"
    ],
    "layer": 224
}
```

### Проверки ради удобства пользователя

[@term:peer] Обратите внимание: [информация о пирах](/api/peers/) (`peer` — собеседник, чат или канал, с которым ведётся работа) и прочие данные из локального кеша служат ещё и для удобства пользователя, то есть позволяют сразу запретить операцию, которая по этим данным недопустима, вместо того чтобы выполнить её и затем показать ошибку.

Такие улучшения следует реализовать всем клиентам, однако сервер в любом случае не даст пользователю выполнить недопустимую операцию и вернёт подходящую [RPC-ошибку](/api/errors/) — ведь иногда недопустимую операцию всё же удаётся инициировать, даже если локальная проверка _реализована_ (см. ниже).

Помимо запрета недопустимых операций на стороне клиента, клиентам следует всегда показывать локализованные версии ошибок, возвращаемых сервером (из числа перечисленных в JSON-файле, который можно скачать со [страницы RPC-ошибок](/api/errors/)), чтобы пользователь понимал, почему попытка выполнить операцию не удалась.

Иначе говоря, если клиент не предотвратил неудачный вызов метода локально по одной из причин:

-   он не реализует локальную проверку ради простоты либо
-   он _реализует_ локальную проверку, но:
    -   устаревшие данные о пире указывали, что действие допустимо, тогда как на деле оно уже недопустимо
    -   сервер прислал обновление данных о пире, но оно не успело примениться из-за (неизбежной!) гонки между отправкой обновления сервером и отправкой запроса клиентом.
    -   по иным неуказанным причинам (новая проверка, введённая новой возможностью в одном из будущих слоёв, и т. п.)

…ему всё равно следует сообщить пользователю, _почему_ запрос не удался, опираясь на описание RPC-ошибки (если оно есть в [базе данных ошибок JSON](#error-database); в противном случае — показав саму RPC-ошибку).

#### Конструкторы ошибок

Следует предусмотреть механизм обработки ошибок, возвращаемых в конструкторах [rpc\_error](/mtproto/service_messages/#rpc-error).

Ниже приведён список кодов ошибок и их значений:

### 303 SEE\_OTHER

Запрос необходимо повторить, направив его в другой дата-центр.

#### Примеры ошибок:

-   FILE\_MIGRATE\_X: запрашиваемый файл в данный момент хранится в другом дата-центре.
-   PHONE\_MIGRATE\_X: номер телефона, который пользователь пытается использовать для авторизации, привязан к другому дата-центру.
-   NETWORK\_MIGRATE\_X: IP-адрес источника привязан к другому дата-центру (при регистрации)
-   USER\_MIGRATE\_X: пользователь, от имени которого выполняются запросы, привязан к другому дата-центру (при регистрации)

Во всех этих случаях строковый литерал с описанием ошибки содержит номер дата-центра (вместо X), в который нужно отправить повторный запрос. [Подробнее о перенаправлениях между дата-центрами »](/api/datacenter/)

### 400 BAD\_REQUEST

Запрос содержит ошибки. Если запрос был сформирован из формы и содержит введённые пользователем данные, следует сообщить пользователю, что данные нужно исправить, прежде чем повторять запрос.

#### Примеры ошибок:

-   FIRSTNAME\_INVALID: Некорректное имя
-   LASTNAME\_INVALID: Некорректная фамилия
-   PHONE\_NUMBER\_INVALID: Некорректный номер телефона
-   PHONE\_CODE\_HASH\_EMPTY: Отсутствует phone\_code\_hash
-   PHONE\_CODE\_EMPTY: Отсутствует phone\_code
-   PHONE\_CODE\_EXPIRED: Срок действия кода подтверждения истёк
-   API\_ID\_INVALID: Некорректное сочетание api\_id/api\_hash
-   PHONE\_NUMBER\_OCCUPIED: Номер телефона уже используется
-   PHONE\_NUMBER\_UNOCCUPIED: Номер телефона ещё не используется
-   USERS\_TOO\_FEW: Недостаточно пользователей (например, для создания чата)
-   USERS\_TOO\_MUCH: Превышено максимальное число пользователей (например, при создании чата)
-   TYPE\_CONSTRUCTOR\_INVALID: Некорректный конструктор типа
-   FILE\_PART\_INVALID: Некорректный номер части файла
-   FILE\_PARTS\_INVALID: Некорректное количество частей файла
-   FILE\_PART\_X\_MISSING: Часть X файла (где X — число) отсутствует в хранилище
-   MD5\_CHECKSUM\_INVALID: Контрольные суммы MD5 не совпадают
-   PHOTO\_INVALID\_DIMENSIONS: Некорректные размеры фотографии
-   FIELD\_NAME\_INVALID: Поле с именем FIELD\_NAME некорректно
-   FIELD\_NAME\_EMPTY: Поле с именем FIELD\_NAME отсутствует

### 401 UNAUTHORIZED

Неавторизованная попытка воспользоваться возможностями, доступными только авторизованным пользователям.

#### Примеры ошибок:

-   AUTH\_KEY\_UNREGISTERED: Ключ не зарегистрирован в системе
-   AUTH\_KEY\_INVALID: Некорректный ключ
-   USER\_DEACTIVATED: Пользователь удалён либо деактивирован
-   SESSION\_REVOKED: Авторизация аннулирована, поскольку пользователь завершил все сессии
-   SESSION\_EXPIRED: Срок действия авторизации истёк
-   AUTH\_KEY\_PERM\_EMPTY: Метод недоступен для временного авторизационного ключа, не привязанного к постоянному

### 403 FORBIDDEN

Нарушение приватности. Например, попытка написать сообщение тому, кто занёс текущего пользователя в чёрный список.

### 404 NOT\_FOUND

Попытка обратиться к несуществующему объекту, например к несуществующему методу.

### 406 NOT\_ACCEPTABLE

Аналогично [400 BAD\_REQUEST](#400-bad-request), но приложение обязано показать ошибку пользователю несколько иначе.  
При получении конструктора `rpc_error` не следует показывать пользователю какое-либо видимое сообщение об ошибке: вместо этого нужно дождаться обновления [updateServiceNotification](/constructor/updateServiceNotification/) и обработать его обычным образом.  
По сути, сразу после выдачи ошибки 406 `rpc_error` независимо будет отправлено обновление [updateServiceNotification](/constructor/updateServiceNotification/) с типом `popup` (то есть НЕ как конструктор [Updates](/type/Updates/) внутри `rpc_result`, а как обычное обновление): это обновление и будет содержать локализованный текст ошибки, который нужно показать пользователю во всплывающем окне.

[@term:session] Исключение составляет ошибка `AUTH_KEY_DUPLICATED`: она возвращается только тогда, когда какой-либо немедийный DC обнаруживает, что авторизованная сессия (`session` — сеанс работы с аккаунтом; что именно понимается под сессией здесь, уточнено ниже) параллельно отправляет запросы по двум разным TCP-соединениям — с одного и того же или с разных IP-адресов.  
Обратите внимание, что для медийных DC параллельные соединения по-прежнему разрешены и даже рекомендуются.  
Учтите также, что под сессией здесь понимается сессия входа в аккаунт, описываемая конструктором [authorization](/constructor/authorization/) и получаемая через [account.getAuthorizations](/method/account.getAuthorizations/), а не сессия MTProto.

[@term:session\_id] Иными словами, **основное** соединение с немедийным DC обычно допускает лишь **одну** [сессию MTProto](/api/datacenter/#parallel-sessions): эту ошибку вызывает открытие дополнительных параллельных основных сессий (то есть нескольких значений [session\_id](/mtproto/description/#session) — идентификаторов сессии — поверх одного авторизационного ключа либо нескольких TCP-соединений с основным DC).  
Впрочем, сервер может явно разрешить несколько параллельных основных сессий, объявив значение `tmp_sessions` больше `1` в конструкторах [config](/constructor/config/)/[auth.authorization](/constructor/auth.authorization/) ([см. параллельные сессии »](/api/datacenter/#parallel-sessions)); тогда без появления ошибки `AUTH_KEY_DUPLICATED` допустимо открыть не больше указанного числа параллельных основных сессий. Если `tmp_sessions` отсутствует или `≤ 1`, обязательно использовать одну основную сессию.  
Выделенные [сессии для передачи файлов](/api/files/#general-considerations) на медийных DC под это ограничение не подпадают и всегда могут открываться параллельно.

Если клиент получил ошибку `AUTH_KEY_DUPLICATED`, значит сессия уже аннулирована сервером и пользователю необходимо сгенерировать новый авторизационный ключ и войти в аккаунт заново.

### 420 FLOOD

[@term:FLOOD_WAIT] Превышено максимально допустимое число попыток вызвать данный метод с данными входными параметрами — сервер отвечает ожиданием из-за флуда (`FLOOD_WAIT`) и требует выждать указанное время, прежде чем повторять запрос. Например, при попытке запросить большое количество текстовых сообщений (SMS) для одного и того же номера телефона.

#### Пример ошибки:

-   FLOOD\_WAIT\_X: требуется подождать X секунд (где X — число)
-   FLOOD\_PREMIUM\_WAIT\_X: требуется подождать X секунд (где X — число); пользователь также может приобрести [подписку Telegram Premium](/api/premium/), чтобы снять это ограничение. Подробнее об обработке этой ошибки см. [здесь »](/api/files/).

### 500 INTERNAL

При обработке запроса произошла внутренняя ошибка сервера — например, сбой при обращении к базе данных или к файловому хранилищу.

Если клиент получил ошибку 500 или если вы считаете, что эта ошибка не должна была возникнуть, соберите как можно больше сведений о запросе и об ошибке и передайте их разработчикам.

### Прочие коды ошибок

Если сервер вернул ошибку с кодом, не перечисленным выше, её допускается считать эквивалентом ошибки 500 и обрабатывать как [внутреннюю ошибку сервера](#500-internal).
