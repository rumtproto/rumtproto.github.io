# Генератор ссылок на файлы

[@term:file_reference] Реализацию и сопровождение [базы данных ссылок на файлы »](/api/file-references/) можно полностью автоматизировать: для этого есть инструмент, который генерирует схему такой базы, и **файл карты базы данных ссылок на файлы**, который этот инструмент создаёт (`file_reference` — короткая метка, выдаваемая сервером вместе с файлом и подтверждающая право на доступ к нему; со временем она перестаёт действовать).

Словарь:

-   **Путь до ссылки на файл** — это путь десериализации, на котором может встретиться поле `file_reference`, например `updateNewMessage.message -> message.media -> messageMediaDocument.document -> document.file_reference`.
-   **Источник ссылки на файл** (или `FileSource`) содержит сведения, по которым клиент может заново запросить документ (а вместе с ним и новую ссылку на файл); например, для приведённого выше пути это `getMessage{peer: updateNewMessage.message.peer, id: updateNewMessage.message.id}` — по нему документ перезапрашивается методом [messages.getMessages](/method/messages.getMessages/) либо [channels.getMessages](/method/channels.getMessages/), смотря какого типа оказался [Peer](/type/Peer/).

Файл карты базы данных содержит **все возможные источники** для **всех возможных путей до ссылок на файлы**.

Он генерируется по набору прописанных вручную правил внутри генератора (именно они и задают сами источники) и по актуальной схеме API — так, чтобы гарантированно выполнялось следующее:

-   С каждым возможным и допустимым местом, где встречается `file_reference`, связан хотя бы один корректный источник: это проверяется рекурсивным обходом всех возможных графов десериализованных объектов, начиная с:

    -   всех конструкторов типа `Update`;
    -   всех конструкторов, которые напрямую возвращает хотя бы один метод;
    -   всех конструкторов, которые хотя бы один метод возвращает напрямую внутри вектора.

    Так покрываются любые TL-объекты, которые вообще могут прийти от API, ведь оно способно вернуть лишь ответы на вызовы методов либо конструкторы [Update](/type/Update/), вложенные в [Updates](/type/Updates/).

    Например, при обходе графа конструктора [updateNewMessage](/constructor/updateNewMessage/) обнаруживаются такие пути до ссылок на файлы:

    ```
    updateNewMessage.message -> message.media -> messageMediaDocument.document -> document.file_reference
    updateNewMessage.message -> message.reply_to -> messageReplyHeader.reply_media -> messageMediaDocument.document -> document.file_reference
    updateNewMessage.message -> message.media -> messageMediaInvoice.extended_media -> messageExtendedMedia.media -> messageMediaDocument.document -> document.file_reference
    ... and many others
    ```

    ...и для каждого из путей система, формирующая файл определений, убеждается, что путь покрыт хотя бы одним источником.

-   Каждый источник обязан использоваться хотя бы в одном пути.

-   Каждый путь, покрытый источником, который опирается на поля под флагами (а они могут оказаться незаполненными, и тогда ссылка на файл останется сиротой, без контекста), обязан покрываться ещё и хотя бы одним источником без флагов (либо такой источник должен на этом конкретном пути обходиться без полей под флагами).

    Например, путь до ссылки на файл `updateStory.story -> storyItem.media -> messageMediaDocument.document -> document.file_reference` _опирался бы_ на источник `getStory{peer: storyItem.from_id, story_id: storyItem.id}` с вызовом [stories.getStoriesByID](/method/stories.getStoriesByID/).

    Однако поле `from_id` конструктора [storyItem](/constructor/storyItem/) на деле находится под флагом и в этом конкретном пути **не** заполнено (оно заполняется, только когда [storyItem](/constructor/storyItem/) возвращается методом [stories.getAllStories](/method/stories.getAllStories/)).

    Валидатор ([это код, которым сформирован файл определений; писать собственный валидатор вам НЕ нужно](https://github.com/danog/MadelineProto/blob/v8/tools/gen_filerefmap.php)) это заметил, и потому пришлось вручную добавить корректный запасной источник `getStory{peer: updateStory.peer, story_id: updateStory.story -> storyItem.id}` — он и присутствует в итоговом файле определений источников.

    Учтите, что файл определений проверен заранее: чтобы реализовать его у себя, проверять ничего дополнительно не нужно, а сказанное выше — лишь пример случая, который успешно покрывает [реализованный здесь валидатор »](https://github.com/danog/MadelineProto/blob/v8/tools/gen_filerefmap.php).

### Запуск

[@term:layer] Чтобы запустить генератор на более новом слое (`layer` — пронумерованная версия схемы API), склонируйте репозиторий, установите зависимости и запустите генератор:

```
git clone https://github.com/danog/MadelineProto.git --recursive
cd MadelineProto
composer update
php tools/gen_filerefmap.php <layer> <inputSchema> <output> <outputJson>
```

Аргументы:

-   `layer` — версия слоя
-   `inputSchema` — новая схема API в формате JSON или TL
-   `output` — сформированный файл карты базы данных ссылок на файлы в сериализованном формате TL
-   `outputJson` — сформированный файл карты базы данных ссылок на файлы в формате JSON

Схема, по которой построен файл карты, лежит в `src/TL_file_ref_map_schema.tl`.

При обнаружении новых, ещё не покрытых путей будет выброшено исключение: чтобы покрыть новые пути, отредактируйте `tools/FileRefExtractor/FileRefGenerator.php`, добавив новый `CallOp`, например:

```
$locations['storyItem'][] = new CallOp(
    'stories.getStoriesByID',
    [
        'id' => new ArrayOp(new CopyOp(new Path([['storyItem', 'id']]))),
        'peer' => new GetInputPeerOp(new Path([['peerStories', 'peer']], true)),
    ],
    'fileSourceStory'
);
```

В этом примере при встрече с конструктором [storyItem](/constructor/storyItem/) создаётся новый `fileSourceStory` со следующими полями:

-   `id`: `storyItem.id`
-   `peer`: `peerStories.peer` (в родителях обязан присутствовать конструктор [peerStories](/constructor/peerStories/)).  
    Генератор автоматически проверяет, что используется только один родительский конструктор (или ни одного).

[@note] Именно второй аргумент `true` в `new Path([['peerStories', 'peer']], true)` помечает путь как родительский: значение берётся не из самого `storyItem`, а из объекта, внутри которого тот встретился при обходе. Обычные, не родительские пути начинаются с конструктора-ключа — отсюда и требование к `Key` в конце страницы.

Генератор автоматически проверяет, что во всех операциях `Op` параметры источника файла одинаковы или хотя бы совместимы, — чтобы породить всего один конструктор источника файла с переданным именем (в данном случае `fileSourceStory`).

Структуру некоторых источников файлов можно задать вручную в массиве `$pre` — на случай, когда источник собирается из частично конфликтующих полей и потому требует полей флагов внутри самого источника.

Этот `fileSourceStory` затем, когда потребуется обновить ссылку на файл, используется при вызове метода [stories.getStoriesByID](/method/stories.getStoriesByID/) со следующими параметрами:

-   `id`: `fileSourceStory.id`
-   `peer`: `fileSourceStory.peer`

Генератор автоматически проверяет, что все вызовы методов пользуются параметрами источника файла одинаково или хотя бы совместимо, — чтобы породить всего один вызов метода на каждый источник файла.

Как видно, это определение объединяет:

-   извлечение контекста
-   формирование источника файла для сохранения в базе данных
-   вызов метода, применяемый к сохранённому источнику файла при обновлении ссылки на файл

...в одном сжатом определении.

`$locations` — это `HashMap<Key, Vector<Op>>`, где:

-   `Key` — конструктор, с которого начинается захват контекста (обязан совпадать с первым элементом путей, не помеченных как родительские)
-   `Op` — объект типа `ActionOp` (`CallOp`, `CopyMethodCallOp`, `GetMessageOp`, `Noop`).
