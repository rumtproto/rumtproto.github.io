# Секретные чаты, сквозное шифрование (версия 1.0, УСТАРЕЛО)

Секретные чаты — это чаты один на один, в которых сообщения шифруются ключом, известным только участникам чата. Обратите внимание, что [схема](/schema/end-to-end/) для секретных чатов со сквозным шифрованием отличается от той, что используется для [облачных чатов](/mtproto/):

### Выработка ключа

Для выработки ключа применяется протокол Диффи — Хеллмана. Подробности см. в [Википедии](https://en.wikipedia.org/wiki/Diffie%E2%80%93Hellman_key_exchange).

Рассмотрим следующий сценарий: пользователь **A** хочет начать шифрованный обмен сообщениями с пользователем **B**.

#### Отправка запроса

Пользователь **A** вызывает [messages.getDhConfig](/method/messages.getDhConfig/), чтобы получить параметры Диффи — Хеллмана: простое число **p** и элемент большого порядка **g**.

Вызывать этот метод перед каждой новой процедурой выработки ключа крайне важно. Значения параметров имеет смысл кешировать вместе с версией, чтобы не получать все значения каждый раз. Если версия, сохранённая на клиенте, всё ещё актуальна, сервер вернёт конструктор [messages.dhConfigNotModified](/constructor/messages.dhConfigNotModified/).

От клиента ожидается проверка того, что **p** — безопасное 2048-битное простое число (то есть что простыми являются и **p**, и **(p-1)/2**, и что 2^2047 < p < 2^2048), а также что **g** порождает циклическую подгруппу простого порядка **(p-1)/2**, то есть является квадратичным вычетом **mod p**. Поскольку **g** всегда равно 2, 3, 4, 5, 6 или 7, это легко сделать с помощью закона квадратичной взаимности, который даёт простое условие на **p mod 4g** — а именно **p mod 8 = 7** для **g = 2**; **p mod 3 = 2** для **g = 3**; никакого дополнительного условия для **g = 4**; **p mod 5 = 1 или 4** для **g = 5**; **p mod 24 = 19 или 23** для **g = 6**; и **p mod 7 = 3, 5 или 6** для **g = 7**. После того как клиент проверил **g** и **p**, результат имеет смысл закешировать, чтобы в дальнейшем не повторять длительные вычисления. Этот кеш можно использовать совместно с кешем, применяемым при [выработке авторизационного ключа](/mtproto/auth_key/).

Если генератор случайных чисел на клиенте неудовлетворителен, имеет смысл передать параметр **random\_length** (random\_length> 0), чтобы сервер сгенерировал собственную случайную последовательность **random** нужной длины. **Важно**: использовать случайную последовательность сервера в исходном виде может быть небезопасно. Её необходимо совместить с клиентской последовательностью — например, сгенерировав клиентское случайное число такой же длины (**client\_random**) и вычислив `final_random := random XOR client_random`.

Клиент **A** вычисляет 2048-битное число **a** (используя достаточную энтропию либо серверное значение **random**, см. выше) и вызывает [messages.requestEncryption](/method/messages.requestEncryption/), передав `g_a := pow(g, a) mod dh_prime`.

[@term:auth_key] Пользователь **B** получает обновление [updateEncryption](/constructor/updateEncryption/) для всех связанных авторизационных ключей `auth_key` (то есть для всех авторизованных устройств) с конструктором чата [encryptedChatRequested](/constructor/encryptedChatRequested/). Пользователю обязательно показывают основные сведения о пользователе **A** и предлагают принять или отклонить запрос.

Оба клиента обязаны проверить, что **g**, **g\_a** и **g\_b** больше единицы и меньше **p-1**. Рекомендуем также проверять, что **g\_a** и **g\_b** лежат в пределах от **2^{2048-64}** до **p - 2^{2048-64}**.

#### Принятие запроса

После того как пользователь **B** подтвердит в интерфейсе клиента создание секретного чата с **A**, клиент **B** также получает актуальные параметры конфигурации для метода Диффи — Хеллмана. Затем он генерирует случайное 2048-битное число **b** по тем же правилам, что и **a**.

Получив **g\_a** из обновления с [encryptedChatRequested](/constructor/encryptedChatRequested/), он может сразу вычислить итоговый общий ключ: `key = (pow(g_a, b) mod dh_prime)`. Если длина ключа меньше 256 байт, следует дополнить его несколькими ведущими нулевыми байтами (padding), чтобы ключ имел длину ровно 256 байт. Его отпечаток **key\_fingerprint** равен последним 64 битам SHA1 (key).

**Примечание:** этот отпечаток служит проверкой корректности процедуры обмена ключами и предназначен для выявления ошибок при разработке клиентского ПО — он не связан с визуализацией ключа, которая используется в клиентах как средство внешней аутентификации в секретных чатах. [Визуализации ключа](/api/end-to-end/pfs/#key-visualization) в клиентах строятся из первых 128 бит SHA1(исходный ключ), за которыми следуют первые 160 бит SHA256(ключ, действовавший на момент обновления секретного чата до слоя 46).

Клиент **B** вызывает [messages.acceptEncryption](/method/messages.acceptEncryption/), передав ему `g_b := pow(g, b) mod dh_prime` и **key\_fingerprint**.

Всем авторизованным устройствам клиента **B**, кроме текущего, отправляются обновления [updateEncryption](/constructor/updateEncryption/) с конструктором [encryptedChatDiscarded](/constructor/encryptedChatDiscarded/). После этого доступ к секретному чату останется только у устройства **B**, которое вызвало [messages.acceptEncryption](/method/messages.acceptEncryption/).

Пользователю **A** будет отправлено обновление [updateEncryption](/constructor/updateEncryption/) с конструктором [encryptedChat](/constructor/encryptedChat/) — для того авторизационного ключа, который инициировал чат.

По значению **g\_b** из обновления клиент **A** также может получить общий ключ `key = (pow(g_b, a) mod dh_prime)`. Если длина ключа меньше 256 байт, следует дополнить его несколькими ведущими нулевыми байтами (padding), чтобы ключ имел длину ровно 256 байт. Если отпечаток полученного ключа совпадает с тем, что был передан в [encryptedChat](/constructor/encryptedChat/), можно отправлять и обрабатывать сообщения. В противном случае необходимо вызвать [messages.discardEncryption](/method/messages.discardEncryption/) и уведомить пользователя.

#### Perfect Forward Secrecy

[@term:Perfect Forward Secrecy] Чтобы сохранить в безопасности прошлую переписку (Perfect Forward Secrecy — совершенная прямая секретность), официальные клиенты Telegram инициируют смену ключа, как только ключ был использован для расшифровки и шифрования более 100 сообщений либо применяется дольше недели, при условии что им было зашифровано хотя бы одно сообщение. Старые ключи затем надёжно уничтожаются, и восстановить их нельзя даже при наличии доступа к новым, используемым сейчас ключам.

> Протокол смены ключей подробнее описан в статье [Perfect Forward Secrecy в секретных чатах](/api/end-to-end/pfs/).

Обратите внимание: чтобы ваш клиент был совместим с официальными клиентами Telegram, он обязан поддерживать Forward Secrecy в секретных чатах.

### Отправка и приём сообщений в секретном чате

#### Сериализация и шифрование исходящих сообщений

Создаётся TL-объект типа [DecryptedMessage](/type/DecryptedMessage/), содержащий сообщение в открытом виде. Для обратной совместимости объект необходимо обернуть в конструктор [decryptedMessageLayer](/constructor/decryptedMessageLayer/) с указанием поддерживаемого слоя (начиная с 8). TL-схема содержимого сообщений со сквозным шифрованием приведена [здесь »](/schema/end-to-end/).

[@term:msg_key] Полученная конструкция сериализуется в массив байт по общим правилам TL. Спереди к получившемуся массиву добавляются 4 байта с длиной массива, не считая этих 4 байт. Ключ сообщения **msg\_key** (значение, привязывающее шифрование к содержимому сообщения) вычисляется как 128 младших бит SHA1 от данных, полученных на предыдущем шаге. Массив байт дополняется случайными данными, пока его длина не станет кратной 16 байтам. Далее вычисляются ключ AES и вектор инициализации (**key** — общий ключ, полученный при [выработке ключа](#key-generation); в MTProto 1.0 **x** = 0):

-   msg\_key = substr (SHA1 (plaintext), 4, 16);
-   sha1\_a = SHA1 (msg\_key + substr (key, x, 32));
-   sha1\_b = SHA1 (substr (key, 32+x, 16) + msg\_key + substr (key, 48+x, 16));
-   sha1\_c = SHA1 (substr (key, 64+x, 32) + msg\_key);
-   sha1\_d = SHA1 (msg\_key + substr (key, 96+x, 32));
-   aes\_key = substr (sha1\_a, 0, 8) + substr (sha1\_b, 8, 12) + substr (sha1\_c, 4, 12);
-   aes\_iv = substr (sha1\_a, 8, 12) + substr (sha1\_b, 0, 8) + substr (sha1\_c, 16, 4) + substr (sha1\_d, 0, 8);

Данные шифруются 256-битным ключом **aes\_key** и 256-битным вектором инициализации **aes-iv** алгоритмом AES-256 в режиме бесконечного зацепления шифротекста (IGE). Спереди к получившемуся массиву байт добавляются отпечаток ключа шифрования **key\_fingerprint** и ключ сообщения **msg\_key**.

Зашифрованные данные вкладываются в вызов API [messages.sendEncrypted](/method/messages.sendEncrypted/) и передаются серверу Telegram для доставки второму участнику секретного чата.

#### Расшифровка входящего сообщения

Перечисленные выше шаги выполняются в обратном порядке. При получении зашифрованного сообщения вы **обязаны** проверить, что msg\_key **действительно** равен 128 младшим битам SHA1-хеша расшифрованного сообщения. Если слой сообщения выше того, который поддерживается клиентом, пользователя необходимо уведомить, что версия клиента устарела, и предложить обновиться.

#### Порядковые номера

[@term:seq_no] Чтобы защититься от возможных манипуляций, все сообщения необходимо трактовать в их исходном порядке. В секретных чатах предусмотрен особый механизм ведения счётчиков seq\_no (порядковых номеров сообщений) независимо от сервера.

> Правильная работа с этими счётчиками подробнее описана в статье [Порядковые номера в секретных чатах](/api/end-to-end/seq_no/).

Обратите внимание: чтобы ваш клиент был совместим с официальными клиентами Telegram, он обязан поддерживать порядковые номера в секретных чатах.

#### Отправка зашифрованных файлов

Все файлы, отправляемые в секретные чаты, шифруются одноразовыми ключами, никак не связанными с общим ключом чата. Предполагается, что перед отправкой зашифрованного файла его адрес будет приложен снаружи зашифрованного сообщения — через параметр **file** метода [messages.sendEncryptedFile](/method/messages.sendEncryptedFile/), — а ключ для непосредственной расшифровки будет передан в теле сообщения (параметр **key** в конструкторах [decryptedMessageMediaPhoto](/constructor/decryptedMessageMediaPhoto/), [decryptedMessageMediaVideo](/constructor/decryptedMessageMediaPhoto/) и [decryptedMessageMediaFile](/constructor/decryptedMessageMediaPhoto/).

Перед отправкой файла в секретный чат вычисляются 2 случайных 256-битных числа, которые послужат ключом AES и вектором инициализации для шифрования файла. Шифрование AES-256 в режиме бесконечного зацепления шифротекста (IGE) применяется здесь таким же образом.

Отпечаток ключа вычисляется следующим образом:

-   digest = md5(key + iv)
-   fingerprint = substr(digest, 0, 4) XOR substr(digest, 4, 4)

Зашифрованное содержимое файла хранится на сервере почти так же, как и содержимое [файла в облачных чатах](/api/files/): по частям, вызовами [upload.saveFilePart](/method/upload.saveFilePart/). Последующий вызов [messages.sendEncryptedFile](/method/messages.sendEncryptedFile/) присвоит сохранённому файлу идентификатор и отправит адрес вместе с сообщением. Получателю придёт обновление с [encryptedMessage](/constructor/encryptedMessage/), а параметр **file** будет содержать сведения о файле.

Входящие и исходящие зашифрованные файлы можно пересылать в другие секретные чаты с помощью конструктора [inputEncryptedFile](/constructor/inputEncryptedFile/) — это позволяет не сохранять на сервере одно и то же содержимое дважды.

#### Работа с ящиком обновлений

[@term:pts] Секретные чаты привязаны к конкретным устройствам (точнее, к [авторизационным ключам](/mtproto/description_v1/#authorization-key)), а не к пользователям. Обычный ящик сообщений, состояние клиента в котором описывается счётчиком **pts** (монотонно растущим номером состояния), для этого не подходит: он рассчитан на длительное хранение сообщений и доступ к ним с разных устройств.

[@term:qts] Решением этой задачи стала дополнительная временная очередь сообщений. При отправке обновления о сообщении из секретного чата передаётся новое значение **qts** (отдельного счётчика состояния для этой очереди), которое помогает восстановить разницу, если связь надолго прерывалась или обновление было потеряно.

По мере роста числа событий значение **qts** монотонно увеличивается (не всегда на 1). Начальное значение может не быть равным 0 — и не будет.

Получение и сохранение клиентом событий из временной очереди подтверждается явно — вызовом метода [messages.receivedQueue](/method/messages.receivedQueue/) — либо неявно, вызовом [updates.getDifference](/method/updates.getDifference/) (учитывается переданное значение **qts**, а не итоговое состояние). Все сообщения, доставку которых клиент подтвердил, а также любые сообщения старше 7 дней могут быть удалены с сервера — и будут удалены.

При деавторизации очередь событий соответствующего устройства принудительно очищается, а значение **qts** теряет смысл.

## Переход на новые слои

[@term:layer] Вашему клиенту следует всегда хранить максимальный слой (`layer` — номер версии схемы, определяющий набор доступных конструкторов), который заведомо поддерживается клиентом на другой стороне секретного чата. При первом создании секретного чата это значение следует инициализировать числом 8 — это первый слой, в котором появились секретные чаты. Значение удалённого слоя обязано обновляться сразу же после получения _любого_ пакета со сведениями о более высоком слое, а именно:

-   любого сообщения секретного чата, содержащего _layer\_no_ в своём `decryptedMessageLayer` со значением _layer_\>=17, либо
-   сервисного сообщения [decryptedMessageActionNotifyLayer](/constructor/decryptedMessageActionNotifyLayer/), обёрнутого так, как если бы это был конструктор [decryptedMessageService](/constructor/decryptedMessageService/) устаревшего слоя 8 (конструктор `decryptedMessageService#aa48327d`).

#### Уведомление удалённого клиента о своём локальном слое

Чтобы сообщить удалённому клиенту о своём локальном слое, ваш клиент обязан отправить сообщение типа `decryptedMessageActionNotifyLayer`. Это уведомление необходимо обернуть в конструктор подходящего слоя. Например, если удалённый слой для данного чата считается ниже 17, уведомление необходимо обернуть так, как если бы это был конструктор `decryptedMessageService` устаревшего слоя 8 (конструктор `decryptedMessageService#aa48327d`), — несмотря на то, что конструктора `decryptedMessageActionNotifyLayer` в слое 8 на самом деле нет.

Есть три случая, когда ваш клиент обязан уведомить удалённый клиент о своём локальном слое:

1.  Сразу после создания нового секретного чата, немедленно по завершении успешного обмена секретным ключом.
2.  Сразу после того, как значение удалённого слоя обновилось до 17 или выше. Исключение — случай, когда данный секретный чат был создан менее 15 секунд назад: тогда уведомление уже отправлено (см. пункт 1).
3.  Сразу после того, как локальный клиент был обновлён до версии с поддержкой нового слоя секретных чатов. В этом случае уведомления необходимо разослать по **всем** существующим на данный момент секретным чатам. Учтите, что это требуется только при переходе на новые слои, содержащие изменения в реализации секретных чатов (например, при обновлении клиента со слоя 17 до слоя 18 этого делать не нужно).

> Обратите внимание: все ожидающие отправки сообщения устаревшего слоя обязаны быть отправлены до уведомления о смене слоя (подробнее об этом — в статье [Работа с порядковыми номерами](/api/end-to-end/seq_no/#preventing-gaps)).
