# Конструкторы min

[@term:min] В некоторых ситуациях конструкторы [user](/constructor/user/) и [channel](/constructor/channel/) содержат сокращённый набор полей (хотя `id` присутствует всегда) и имеют установленный флаг `min` — признак «урезанного» объекта. Так сделано из соображений производительности и приватности.

Получив такие конструкторы, клиент обязан сначала проверить, есть ли уже объект пользователя или чата без флага `min` в [локальной базе пиров »](/api/peers/).  
Если он там есть, клиенту следует объединить удалённый и локальный объекты, игнорируя те поля удалённого объекта, которые указаны на страницах [user](/constructor/user/) и [channel](/constructor/channel/).

[@term:access_hash] Кроме того, клиент обязан сохранить контекст (по аналогии со [ссылками на файлы](/api/file-references/)), в котором был встречен пользователь или канал. Позже, когда клиенту понадобится передать пользователя или канал во входном аргументе (например, передать `access_hash` — хеш доступа к объекту — чтобы получить профиль, отключить уведомления, узнать сведения о блокировке и так далее), контекст используется для формирования конструктора `input*FromMessage` вместо обычных `inputUser`, `inputChannel` или `inputPeer`.

-   [inputPeerUserFromMessage](/constructor/inputPeerUserFromMessage/)
-   [inputPeerChannelFromMessage](/constructor/inputPeerChannelFromMessage/)
-   [inputUserFromMessage](/constructor/inputUserFromMessage/)
-   [inputChannelFromMessage](/constructor/inputChannelFromMessage/)

Значение `access_hash` из конструктора с флагом `min` пригодно для использования только при определённых условиях, указанных на страницах [user](/constructor/user/) и [channel](/constructor/channel/).

Обычно конструкторы `min` встречаются в сообщениях внутри групп и каналов. Когда находится сообщение, упоминающее такого пользователя или канал (как отправителя, переславшего, автора оригинала и тому подобное), конструктор обязательно нужно связать с идентификатором этого сообщения и с чатом, где это сообщение встретилось.

#### Пример

Допустим, из супергруппы ([фактически канала](/api/channel/)) `123456789` получено [сообщение](/constructor/message/) с идентификатором `34`. Это сообщение отправлено пользователем с `from_id` `102424212`. Контейнер [updates](/api/updates/), в котором пришло сообщение, содержит в поле `users` пользователя с ID `102424212`, но у него установлен флаг `min`, а переданный `access_hash` может отсутствовать либо иным образом не годиться для формирования обычного конструктора [inputPeerUser](/constructor/inputPeerUser/), которым отправляют сообщения или выполняют другие действия.

Клиент в этом случае связывает `102424212` с каналом `123456789` и идентификатором сообщения `34`. Если и когда клиенту потребуется взаимодействовать с пользователем `102424212`, он сформирует один из упомянутых выше конструкторов `*FromMessage`, задав:

-   `msg_id` равным `34`
-   `peer` равным [InputPeer](/type/InputPeer/), связанному с каналом `123456789`
-   `user_id` равным `102424212`

`user_id` можно также задавать идентификаторами пользователей, встреченных в `fwd_header` (сообщения, пересланные от пользователя, можно использовать для взаимодействия с исходным отправителем, если у него не включены настройки приватности для пересылок). Точно так же годятся пользователи, упомянутые в сообщении через [messageEntityMentionName](/constructor/messageEntityMentionName/).

То же самое можно проделать с [каналами](/api/channel/), помеченными флагом `min`.

[@note] Иными словами, конструкторы `*FromMessage` не содержат самого хеша доступа: вместо него они передают, где пир был встречен (`peer` и `msg_id`), а сервер по этой ссылке сам восстанавливает нужный `access_hash`.

Примеры реализаций: [Telegram для iOS](https://github.com/peter-iakovlev/Telegram-iOS), [tdlib](https://github.com/tdlib/td).
