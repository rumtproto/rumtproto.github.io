# Оптимизация на стороне клиента

### Упрощённое подтверждение доставки сообщения

[@term:quick ack] [@term:random_id] Исходящее сообщение можно считать отправленным, как только сервер назначил ему идентификатор. Обычно клиент узнаёт об этом из результата метода [messages.sendMessage](/method/messages.sendMessage/). Сервер MTProto предоставляет механизм [«быстрых подтверждений»](/mtproto/mtproto-transports/#quick-ack) (`quick ack` — короткий отклик транспортного уровня, который сервер шлёт до того, как обработает сам запрос). Получив такое подтверждение, клиент может быть уверен, что вызов метода отправки сообщения как минимум полностью принят сервером и поставлен в очередь на обработку, и вправе сообщить пользователю об успешной доставке. Возможна ситуация, когда фактический ответ сервера так и не дойдёт до клиента: соединение разорвалось или приложение перезапустилось в самый неподходящий момент. Чтобы корректно обрабатывать такие случаи, можно использовать особый тип уведомления, которое сервер формирует при вызове [updates.getDifference](/method/updates.getDifference/), — [updateMessageID](/constructor/updateMessageID/). Обрабатывая это уведомление, клиент по идентификатору **random\_id** (`random_id` — случайное число, которое клиент сам присваивает сообщению при отправке) сопоставляет ранее переданное сообщение с тем, которое дошло до сервера. Если при вызове [updates.getDifference](/method/updates.getDifference/) такого уведомления для одного из ранее отправленных сообщений нет, клиент обязан пометить это сообщение как недоставленное.

### Серверная соль

[@term:server salt] Серверная соль (`server salt`) — 64-битное число, добавляемое к каждому исходящему и входящему сообщению. Сейчас одна соль живёт 1 час, после чего считается недействительной, и на все содержащие её сообщения сервер возвращает ошибку. В сообщении об ошибке приходит правильная соль, которую можно сразу же использовать для отправки. При таком подходе клиент, подключающийся к серверу реже одного раза в час, всегда будет вынужден ждать, пока не получит новую соль. Для повышения производительности существует специальный метод [get\_future\_salts](/mtproto/service_messages/#request-for-several-future-salts): он заранее получает список солей, которые будут действительны в течение заданного периода после вызова — например, суток. Для каждой соли указывается время начала и время окончания действия. Соли перекрывают друг друга на полчаса. Мы рекомендуем всегда использовать запись с наибольшим оставшимся временем жизни.

### Загрузка файлов и передача данных на сервер

[@term:session] Мы рекомендуем создавать для этих задач отдельные соединения и сессии (`session` — независимый поток сообщений со своей нумерацией, привязанный к авторизационному ключу). Помните, что лишние сессии необходимо удалять, когда они больше не нужны. Файлы имеет смысл скачивать по нескольким соединениям — оптимально держать пул. А вот для передачи данных на сервер, чтобы добиться наилучшего результата, хватает одного соединения.

[@term:ping] API работы с файлами рассчитан на операции с данными по частям. В простейшей реализации процесс загрузки файлов на сервер выглядит так: отправить запрос, дождаться ответа, отправить следующий запрос и т. д. Такой подход не оптимизирует использование сетевых ресурсов, а время отклика (`ping` — задержка между отправкой запроса и получением ответа) сказывается на нём чрезвычайно сильно. Передача и приём оптимальны, когда через одно соединение непрерывно выполняются два запроса или больше. При такой организации передача на сервер выглядела бы так:

1.  Отправить запрос 1
2.  Отправить запрос 2
3.  Дождаться ответа на запрос 1
4.  Отправить запрос 3
5.  Дождаться ответа на запрос 2
6.  Отправить запрос 4
7.  и т. д.

Это поможет снизить влияние задержки `ping` и максимально загрузить канал.

### Массовая отправка сообщений

Иногда клиенту нужно передать серверу сразу несколько вызовов метода отправки сообщения — в одном сообщении или в нескольких идущих подряд. Однако сервер может выполнить эти запросы не по порядку: для повышения производительности запросы обрабатываются разными серверами, а это вносит в процесс некоторую случайность. Поэтому зависимости между запросами приходится задавать явно — с помощью функции

```
invokeAfterMsg#cb9f372d {X:Type} msg_id:long query:!X = X;
```

Фактически это означает, что в начало запроса дописываются 32-битное число `0xcb9f372d` и 64-битный идентификатор того сообщения-запроса, от которого зависит текущий запрос.

### Группировка обновлений

За формирование обновлений (уведомлений о различных событиях на сервере) и за их доставку клиенту отвечают две разные части системы — соответственно API мессенджера и MTProto. Сам по себе MTProto никак не может изменить передаваемые клиенту данные, а серверный API не может реагировать на события соединения между клиентом и MTProto. Представьте ситуацию, когда клиент на какое-то время теряет соединение или намеренно отключается от сети. Если до установки нового соединения произойдёт множество разных событий — контакты выходят в сеть, отправляются сообщения о наборе текста, — то при установке соединения клиент получит большой объём данных со всеми накопившимися событиями, хотя бо́льшая их часть уже неактуальна. Для оптимизации подобных ситуаций и введена группировка сообщений. Если происходят новые события, а клиент не успел «забрать» сформированные ранее обновления, серверный API может объединить их в один пакет.

Клиент может управлять тем, с какого момента сервер MTProto считает соединение потерянным и может приступить к группировке (чем раньше это произойдёт при отсутствии соединения, тем лучше для клиента). Эта возможность реализована через особый тип сообщения Ping — [ping\_delay\_disconnect](/mtproto/service_messages/#deferred-connection-closure-ping), — в котором задаётся задержка, по истечении которой сервер закроет текущее соединение и начнёт группировать сообщения.

Передачу [ping\_delay\_disconnect](/mtproto/service_messages/#deferred-connection-closure-ping) имеет смысл совмещать с другими периодическими задачами, например с обновлением статуса пользователя ([account.updateStatus](/method/account.updateStatus/)).

### Установка статуса набора текста

Если контакт не в сети, вызывать [messages.setTyping](/method/messages.setTyping/) не нужно.
