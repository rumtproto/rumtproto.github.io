# Вызов методов API

### Слои

[@term:layer] Версионирование в API обеспечивается так называемыми слоями TL (`layer` — пронумерованная версия схемы).

Необходимость добавить конструктор нового объекта или добавить/удалить поле в конструкторе создаёт проблему обратной совместимости с предыдущими версиями клиентов API. Ведь простое изменение конструктора в схеме меняет и его номер. Чтобы решить эту проблему, каждое обновление схемы выделяется в отдельный слой.

Слой — это набор обновлённых методов или конструкторов схемы TL. Слои нумеруются последовательно возрастающими числами, начиная с 2. Первый слой — базовый, то есть схема TL без каких-либо изменений.

Существует вспомогательный метод, позволяющий сообщить API, что клиент поддерживает слой `layer`:

```
---functions---

invokeWithLayer#da9b0d0d {X:Type} layer:int query:!X = X;
```

Вспомогательный метод **[invokeWithLayer](/method/invokeWithLayer/)** может использоваться только вместе с [initConnection](/method/initConnection/): переданный слой будет сохранён вместе со всеми остальными параметрами клиента, и все последующие запросы будут использовать это сохранённое значение. [Подробнее ниже](#saving-client-info).

**Примечание**: в некоторых случаях — например, при обновлениях из крупных каналов — API может вернуть конструкторы из более старых слоёв, отличных от текущего слоя соединения.

Клиентам следует трактовать это как серверную ошибку `500` и обрабатывать её, закрывая и заново открывая TCP-сокет, переинициализируя сессию через [initConnection](/method/initConnection/) и вызывая [getDifference](/api/updates/).

### Сохранение информации о клиенте

[@term:auth_key] На сервере можно сохранить информацию о текущем клиенте, связав её с авторизационным ключом (`auth_key` — долговременный секрет, которым шифруются все сообщения клиента). Это помогает устранять проблемы на стороне клиента, возникающие в отдельных сборках, на отдельных устройствах или при отдельных локализациях, а также избавляет от необходимости передавать сведения о слое в каждом запросе.

Вспомогательный метод **[initConnection](/method/initConnection/)** принимает параметры клиента. Этот метод обязательно вызывать при первом обращении к API после перезапуска приложения либо если значение одного из параметров могло измениться.

**initConnection** обязательно вызывать и после каждого [auth.bindTempAuthKey](/method/auth.bindTempAuthKey/).

При вызове этого метода сохраняется и текущий используемый клиентом слой (берётся тот слой, в который был обёрнут [initConnection](/method/initConnection/)). После успешного вызова [initConnection](/method/initConnection/) больше не требуется оборачивать каждый вызов API в **invokeWithLayerN**.

### Отключение обновлений

```
---functions---

invokeWithoutUpdates#bf9459b7 {X:Type} query:!X = X;
```

[invokeWithoutUpdates](/method/invokeWithoutUpdates/) позволяет выполнить запрос, не подписывая используемое соединение на [обновления](/api/updates/) (для [файловых запросов](/api/files/) такое поведение включено по умолчанию).

### Последовательные запросы

По умолчанию сервер обрабатывает параллельные запросы в произвольном порядке. Для случаев, когда клиенту нужно, чтобы определённые запросы обрабатывались в определённом порядке, и он собирается отправить новый запрос до завершения предыдущего, предусмотрены два вспомогательных метода.  
Эти методы позволяют снизить задержку для вызовов, требующих строгого порядка: клиенту не приходится дожидаться результата предыдущего вызова, прежде чем отправить следующий в очереди, — он может отправить их все сразу, обернув (например) каждый в `invokeAfterMsg` с `msg_id` предыдущего запроса.

```
---functions---

invokeAfterMsg#cb9f372d {X:Type} msg_id:long query:!X = X;
invokeAfterMsgs#3dc4b4f0 {X:Type} msg_ids:Vector<long> query:!X = X;
```

[@term:msg_id] Они применимы, например, когда клиент пытается отправить сообщения, накопившиеся за время долгого ожидания восстановления интернет-соединения. В этом случае в каждом запросе перед номером метода необходимо добавить 32-битное число `0xcb9f372d`, а за ним — 64-битный идентификатор сообщения msg\_id (`msg_id` — номер, которым MTProto помечает каждое сообщение сессии), указывающий на предыдущий запрос в очереди.

Второй метод устроен аналогично, но принимает несколько сообщений, которые обязаны быть успешно обработаны до текущего.

Если ожидание превышает 0,5 секунды (в будущем это значение может измениться) и результат так и не появился, метод вернёт ошибку `MSG_WAIT_TIMEOUT`: обработайте её повторной отправкой запроса, по-прежнему обёрнутого в тот же конструктор `invokeAfterMsg`/`invokeAfterMsgs` с теми же `id`/`ids`.

Если какой-либо из предыдущих запросов, упомянутых в `msg_ids` или `msg_id`, завершился неудачей (то есть запрос вернул RPC-ошибку, включая ошибки `FLOOD_WAIT_`), для текущего запроса будет возвращена ошибка `MSG_WAIT_FAILED`: проще всего обработать её, обеспечив локальную синхронизацию — дождаться ответа на все предыдущие `msg_ids`/`msg_id`, прежде чем отправлять запрос повторно.

Если и только если какой-либо из предыдущих запросов тоже завершился ошибкой `MSG_WAIT_FAILED`/`MSG_WAIT_TIMEOUT` и требует повторной отправки, оберните текущий запрос в новый конструктор `invokeAfterMsg`/`invokeAfterMsgs` с новыми идентификаторами предыдущих запросов, которые отправляются повторно вместе с текущим.

#### Сценарий 1

Для наглядности предположим следующую последовательность запросов:

1.  msg\_id=1; `messages.sendMessage message=a`
2.  msg\_id=2; `invokeAfterMsg msg_id=1 (messages.sendMessage message=b)`
3.  msg\_id=3; `invokeAfterMsg msg_id=2 (messages.sendMessage message=c)`

##### Сценарий 1.1

Если первый запрос messages.sendMessage с `msg_id=1` завершится неудачей, оба запроса с `msg_id=2` и `msg_id=3` завершатся ошибкой `MSG_WAIT_FAILED` и их придётся отправить повторно, как показано ниже.  
Чтобы восстановить очередь вызовов, отправьте следующую новую последовательность запросов:

1.  msg\_id=4; `messages.sendMessage message=b` (повторная отправка прежнего запроса с `msg_id=2`)
2.  msg\_id=5; `invokeAfterMsg msg_id=4 (messages.sendMessage message=c)` (повторная отправка прежнего запроса с `msg_id=3`)

##### Сценарий 1.2

Если первый запрос messages.sendMessage с `msg_id=1` выполнится успешно, а второй с `msg_id=2` завершится неудачей, запрос с `msg_id=3` завершится ошибкой `MSG_WAIT_FAILED` и его придётся отправить повторно, как показано ниже.  
Чтобы восстановить очередь вызовов, отправьте следующую новую последовательность запросов:

1.  msg\_id=4; `messages.sendMessage message=c` (повторная отправка прежнего запроса с `msg_id=3`)

#### Сценарий 2

Теперь предположим другую последовательность запросов:

1.  msg\_id=1; `messages.sendMessage message=a`
2.  msg\_id=2; `messages.sendMessage message=b`
3.  msg\_id=3; `invokeAfterMsgs msg_ids=[1, 2] (messages.sendMessage message=c)`

Если один или оба запроса messages.sendMessage с `msg_id=1` и/или `msg_id=2` завершатся неудачей, запрос с `msg_id=3` тоже завершится ошибкой `MSG_WAIT_FAILED` и его придётся отправить повторно, как показано ниже.

Чтобы восстановить очередь вызовов, прежде всего дождитесь ответа на запросы с `msg_id=1` и `msg_id=2`.

Обратите внимание, чем это отличается от сценария 1, где ждать ответа на предыдущие запросы не требуется: в сценарии 1 каждый запрос `invokeAfterMsg` ожидает напрямую лишь один предыдущий запрос, а каждый новый запрос в очереди сцеплен с предыдущим `invokeAfterMsg`, поэтому неудача любого запроса с `msg_id=N` в цепочке немедленно блокирует выполнение всех запросов с `msg_id <= N`.  
Здесь же мы ждём сразу два сообщения, и неудача запроса с `msg_id=1` не мешает выполнению запроса с `msg_id=2`, и наоборот; поэтому при повторной отправке запроса с `msg_id=3` необходимо либо:

-   Дождаться ответов (ошибок или успешных результатов) на **все** запросы, упомянутые в `msg_ids`, и затем отправить такой новый запрос:

    -   msg\_id=4; `messages.sendMessage message=c` (повторная отправка прежнего запроса с `msg_id=3`)
-   ЛИБО дождаться получения RPC-ошибки по любому из запросов, упомянутых в `msg_ids`, и затем отправить такой новый запрос:

    -   msg\_id=4; `invokeAfterMsgs msg_ids=([1, 2] - [$errId]) (messages.sendMessage message=c)` (повторная отправка прежнего запроса с `msg_id=3`)

    То есть отправить `invokeAfterMsgs` повторно со всеми исходными `msg_ids`, кроме того, который завершился неудачей.  
    Процесс может потребоваться повторить, если вновь отправленный `invokeAfterMsgs` тоже завершится неудачей из-за того, что оставшийся запрос, упомянутый в `msg_ids`, также завершился неудачей (то есть если запросы `1` и `2` оба завершатся неудачей с небольшой разницей во времени).

    Очевидно, первый вариант (дождаться ответов — ошибок или успешных результатов — на **все** упомянутые запросы, прежде чем продолжать) проще всего.

Ещё более простой вариант — всегда придерживаться [Сценария 1](#scenario-1), никогда не используя `invokeAfterMsgs` и применяя только сцепленные вызовы `invokeAfterMsg`, что позволяет обойтись без этой чуть более сложной логики восстановления.

#### Порядок вложения вспомогательных методов

**Важно:** если вспомогательные методы **invokeAfterMsg** / **invokeAfterMsgs** используются вместе с **invokeWithLayerN** или другими вспомогательными методами, **invokeAfterMsg** / **invokeAfterMsgs** обязаны всегда оставаться самой внешней обёрткой.

### Сжатие данных

При вызове методов рекомендуется применять сжатие gzip — это уменьшает объём сетевого трафика.

Схема и описание конструктора приведены в [документации по протоколу](/mtproto/service_messages/#packed-object).

#### Сжатие данных при отправке запроса

[@term:gzip_packed] Перед передачей запроса строку, содержащую всё тело сериализованного высокоуровневого запроса (начиная с номера метода), необходимо сжать с помощью gzip. Если получившаяся строка оказалась меньше исходной, есть смысл передать конструктор [gzip\_packed](/mtproto/service_messages/#packed-object) (обёртка, внутри которой лежит сжатый объект).

Делать это при передаче двоичных мультимедийных данных (фотографий, видео) или небольших сообщений (до 255 байт) смысла нет.

#### Распаковка данных

По умолчанию сервер может сжимать ответ на любой запрос, а также [обновления](/api/updates/), по изложенным выше правилам. Если в rpc\_result в качестве ответа получен конструктор [gzip\_packed](/mtproto/service_messages/#packed-object), то следующую за ним строку необходимо извлечь и распаковать. Дальнейшая обработка продолжается уже с полученной новой строкой.

[@note] Строка, о которой идёт речь, — это поле `packed_data` самого конструктора `gzip_packed` (`gzip_packed#3072cfa1 packed_data:bytes = Object`), а не отдельный объект, идущий за ним в потоке.
