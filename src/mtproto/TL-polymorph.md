# Полиморфизм в TL

Следует отметить, что в TL-схеме подавляющего большинства вызовов API полиморфные типы применяются только к типу Vector. Тем не менее представлять себе общую картину всё же полезно.

### Обычные индуктивные типы

Рассмотрим для примера тип IntList, который определяется так:

```
int_cons hd:int tl:IntList = IntList;
int_nil = IntList;
```

Конструкторы «int\_cons» и «int\_nil», а также сам тип «IntList» — это выражения следующих типов (запись A : X означает, что A есть выражение типа X):

```
IntList : Type;
int_cons : int -> IntList -> IntList;
int_nil : IntList;
```

[@term:Type] Ключевое слово _Type_ обозначает тип всех типов. Обратите внимание: Type — это не Object (Object — тип всех термов). Ниже приведён альтернативный синтаксис, который мог бы применяться в каком-нибудь другом функциональном языке программирования (но не в TL):

```
NewType IntList :=
| int_cons hd:int tl:IntList
| int_nil
EndType
```

### Полиморфный тип

TL поддерживает следующий вариант записи (фигурные скобки обозначают необязательные поля, см. ниже):

```
cons {X:Type} hd:X tl:(List X) = List X;
nil {X:Type} = List X
```

А вот альтернативная формулировка на других функциональных языках с зависимыми типами:

```
NewType List {X:Type} :=
| cons {X:Type} hd:X tl:(List X)
| nil {X:Type}
EndType
```

В любом случае с точки зрения формальной теории типов эти варианты эквивалентны друг другу и приводят к определению следующих термов:

```
List : Type -> Type;
cons : forall (X:Type), X -> List X -> List X;
nil : forall (X:Type), X -> List X;
```

В каждом из случаев следует помнить, что запись «A -> B» — это сокращение для «forall (x : A), B» при любой переменной x, не входящей в A и B. Например, тип «cons» можно было бы записать так:

```
cons : forall (X:Type), forall (hd : X), forall (tl : List X), List X
```

или более компактно:

```
cons : forall (X : Type) (hd : X) (tl : List X), List X
```

См. [Исчисление конструкций](https://en.wikipedia.org/wiki/Calculus_of_constructions). Примеры функциональных языков с зависимыми типами, которые поддерживают подобные конструкции, — [Coq](https://en.wikipedia.org/wiki/Coq) и [Agda](https://en.wikipedia.org/wiki/Agda_%28programming_language%29).

В данном случае запись после квантора всеобщности оказывается содержательнее записи после стрелки: именем связанной квантором переменной передаётся имя соответствующего поля конструктора — даже если сама эта переменная нигде в выражении под квантором не встречается. Структурно же все эти записи типа «cons» эквивалентны.

### Сериализация типов (значений типа Type)

Как видно, чтобы сериализовать значение типа List X, полученное применением комбинатора «cons X:Type hd:X tl:(List X) = List X», необходимо:

1.  сериализовать имя комбинатора «cons» в 32-битное число;
2.  сериализовать X (как тип, то есть как значение типа Type), если X — обязательный параметр;
3.  сериализовать голову списка (hd) как значение типа X;
4.  сериализовать хвост списка как значение полиморфного типа List X.

На первом шаге закономерно возникает вопрос: какая именно строка пойдёт на вычисление CRC32. Предлагается брать «`cons X:Type hd:X tl:List X = List X`» без завершающей точки с запятой и без каких-либо скобок (замкнутые типовые выражения однозначно восстанавливаются по префиксу своей конструкции).

На последнем шаге мы рекурсивно решаем ровно ту же задачу — сериализацию значения типа List X; будем считать её решённой по предположению индукции по построению сериализуемого значения. Третий шаг будем считать понятным по той же причине (индукция по построению сериализуемого значения).

Остаётся описать, как передавать (сериализовать) типы, то есть значения типа **Type**. _В TL-схемах типы сейчас встречаются только как необязательные параметры конструкторов и потому никогда не сериализуются явно. Вместо этого их значения выводятся из заранее известного типа сериализуемого значения_.

Для полноты изложения опишем, как типы (значения типа Type) можно было бы сериализовать. Однако имейте в виду, что пока эти сведения практической пользы не несут. См. [Сериализация типов](/mtproto/TL-types/).

### Необязательные аргументы в полиморфных конструкторах

Выше говорилось, что любое подмножество (нескольких первых) параметров любого конструктора можно объявить необязательным, заключив их объявления в фигурные скобки, — но это не вполне точно. Во-первых, такие необязательные параметры могут иметь только тип `Type` или `#` (натуральные числа). Во-вторых, необязательные параметры обязаны входить в тип возвращаемого значения, иначе определить их значение невозможно.

Отметим, что запись @'''constr-id''' означает «полную форму» конструктора (в которой все необязательные параметры становятся обязательными), тогда как '''constr-id'' обозначает его сокращённую форму (без необязательных аргументов). Если необязательных аргументов нет, обе формы совпадают. Полные формы конструкторов в настоящее время не используются.

### Голые полиморфные типы

[@term:bare type] Здесь возникает небольшая проблема. Пусть требуется сериализовать значение голого типа (`bare type` — тип, значения которого передаются без имени конструктора в начале) '%pair string int' или '%pair string Y' (в TL его обычно обозначают просто «pair», хотя запись «%Pair» предпочтительнее). Тогда нельзя одновременно использовать и полный конструктор @pair, и сокращённый pair, поскольку имя конструктора сериализовано не будет. Поэтому необходимо различать голые типы %@pair (сериализуются тип X, тип Y, значение x:X и значение y:Y) и %pair (сериализуются только x:X и y:Y; типы X и Y известны из контекста). На практике почти всегда нужен именно голый тип %pair — и именно это в TL означает «pair» в контексте типа. Поэтому запись

```
record name:string map:(List (pair int string)) = Record;
```

будет сериализована примерно так, как нам и требуется (сериализация элементов списка будет состоять из сериализации int и сериализации string, без каких-либо дополнительных заголовков, типов или имён комбинаторов). Кстати, при вычислении имени комбинатора «record» _'record'_ в приведённом выше примере будет посчитан CRC32 от строки `record name:string map:List pair int string = Record`.

Отметим также, что более точным описанием этого типа была бы запись

```
record name:string map:(List %(Pair int string)) = Record
```
