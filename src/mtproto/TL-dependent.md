# Зависимые типы TL

Основная статья: [Язык TL](/mtproto/TL/).

[@term:nat] В некоторых случаях типы могут зависеть не только от других типов (полиморфизм), но и от параметров другого типа (зависимые типы). Язык TL поддерживает эту возможность весьма ограниченно: зависимость допускается только от натурального параметра, тип которого обозначается символом `#` (синоним `nat` — натуральное число, но он служебный: сейчас TL этот синоним не поддерживает). Значения типа # сериализуются как 32-битные знаковые числа от 0 до 2^31-1.

[@note] «Знаковые» здесь не описка оригинала: под значение отводится 32-битное знаковое целое, поэтому верхняя граница диапазона — 2^31-1, а не 2^32-1.

## Пример: кортежи (векторы) целых чисел

Допустим, мы хотим по индукции определить типы «одно целое число», «два целых числа» и «три целых числа». Определить их можно было бы так:

```
empty = Empty;
single x:int = Single;
pair x:int y:int = Pair;
triple x:int y:int z:int = Triple;
quadruple x:int y:int z:int t:int = Quadruple;
...
```

или так:

```
empty = Empty;
single x:int empty = Single;
pair x:int y:single = Pair;
triple x:int yz:pair = Triple;
quadruple x:int yzt:triple = Quadruple;
```

или так:

```
tnil = Tuple0;
tcons0 hd:int tl:Tuple0 = Tuple1;
tcons1 hd:int tl:Tuple1 = Tuple2;
tcons2 hd:int tl:Tuple2 = Tuple3;
...
tcons_n hd:int tl:Tuple_n = Tuple_(n+1)
```

[@term:boxed] Первые два варианта дают одну и ту же сериализацию. Например, `(2 3 9):%triple` и `(2 (3 9)):%triple` сериализуются как три 32-битных числа: `2 3 9`. Последний вариант лучше подчёркивает индуктивный характер определения, но в нём используются boxed-типы (типы «в обёртке», сериализация которых начинается с номера конструктора). С теоретической точки зрения это хорошо, однако приводит к «лишним» именам конструкторов в сериализации.

[@term:bare] Поэтому будем писать `%Type-Ident`, обозначая bare-тип («голый» тип, сериализуемый без номера конструктора), который соответствует boxed-типу `Type-Ident` с единственным конструктором. Если этот конструктор называется `constructor`, то по определению %`Type-Ident` = %`constructor`. Теперь наше определение можно записать так:

```
tnil = Tuple0;
tcons_n hd:int tl:%Tuple_n = Tuple_(n+1)
```

Если теперь вынести _n_ из имени типа и сделать его параметром полиморфного (точнее, зависимого) типа, то на подходящем функциональном языке можно было бы записать примерно следующее:

```
NewType Tuple (n : #) :=
| tnil = Tuple 0
| tcons n:# hd:int tl:%(Tuple n) = Tuple (S n)
EndType;
```

На языке TL это выглядит так:

```
tnil = Tuple 0;
tcons {n:#} hd:int tl:%(Tuple n) = Tuple (S n);
```

Функция `S : # -> #` и константа `O : #` (это `0`) — это переход к следующему натуральному числу (`S n = n + 1`) и константа «нуль». Таким образом, тип `#` (синоним `nat`) ведёт себя так, как если бы его определяли в TL через конструкторы

```
O = nat;
S nat = nat;
```

или, в синтаксисе, более привычном для других функциональных языков,

```
NewType nat :=
| O
| S nat
EndType;
```

Типы всех определённых комбинаторов:

```
O : #
S : # -> #
Tuple : # -> Type
tnil : Tuple 0
tcons : forall n : #, int -> Tuple n -> Tuple (S n)
```

или

```
Tuple : forall n : #, Type;
tcons : forall n : #, forall hd : int, forall tl : Tuple n, Tuple (S n)
```

Обратите внимание, что в данном случае конструктор `tnil` не зависит от параметра _n_, а `tcons` — зависит.

Аналогичным образом можно определить полное двоичное дерево высоты _h_ со строками в листьях:

```
tleaf value:string = BinTree 0;
tnode {h:#} left:(BinTree h) right:(BinTree h) = BinTree (S h);
```

Или произвольное дерево, все листья которого находятся на расстоянии _h_ от корня, а все узлы помечены целыми числами:

```
hleaf value:int = Tree 0;
hnode {n:#} left:(Tree n) next:(Tree (S n)) = Tree (S n)
hnil {n:#} = Tree (S n)
```

Другой вариант:

```
hleaf' value:int = Tree' 0;
hnode' {n:#} children:(list (Tree' n)) = Tree' (S n)
```

## Полиморфные зависимые типы

Попробуем определить тип `Tuple X n`, значения которого — _n_\-ки значений типа `X`. Тем самым `Tuple` окажется одновременно полиморфным и зависимым:

```
Tuple : Type -> # -> Type;
```

В привычном синтаксисе функциональных языков:

```
NewType Tuple {X : Type} {n : #} :=
| vnil : Tuple X 0
| vcons {n:#} hd:X tl:%(Tuple X n) : Tuple X (S n)
EndType
```

или, в синтаксисе TL,

```
vnil {X:Type} = Tuple X 0;
vcons {X:Type} {n:#} tl:(%Tuple X n) = Tuple X S n
```

В итоге получаем термы следующих типов:

```
vnil : forall X : Type, Tuple X 0
vcons : forall X : Type, forall n : #, X -> Tuple X n -> Tuple X (S n)
```

или

```
vnil : forall X : Type, Tuple X 0
vcons : forall X : Type, forall n : #, forall hd : X, forall tl : Tuple X n, Tuple X (S n)
```

## Зависимые суммы

Только что определённый нами `Tuple` отличается от встроенного типа `Vector`. А именно: тип `Vector` формально зависит от одного аргумента (типа), тогда как наш `Tuple` — от двух (типа и числа):

```
Tuple : Type -> # -> Type;
Vector : Type -> Type;
```

Встроенный `Vector` можно было бы определить через наш `Tuple`, взяв «сумму по всем _n_ : #»:

```
vector {X:Type} n:# v:(%Tuple X n) = Vector X;
```

Тем не менее у нашего `Tuple` есть свои преимущества. Например, мы можем определять такие типы данных, как:

```
matrix_10x10 a:(%Tuple (%Tuple double 10) 10) = Matrix_10x10;
```

В любом случае помните: при вычислении номера комбинатора `matrix_10x10` нужно убрать все скобки и считать CRC32 от строки `matrix_10x10 a:%Tuple %Tuple double 10 10 = Matrix_10x10`.

Более того, мы можем определять матрицы произвольного размера:

```
matrix {X:Type} m:# n:# a:(%Tuple (%Tuple X m) n) = Matrix X;
```

Если же взять здесь vector, длина строки (_m_) хранилась бы в каждой строке, то есть _n_ раз.

Заметьте, что сериализации значений типов `%Tuple X n` и `vector X` (известного также как `%vector X` и `%Vector X`) почти совпадают при _n > 0_: в обоих случаях получается одно 32-битное число (равное _n-1_ или _n_ в зависимости от варианта), за которым следуют сериализации _n_ объектов типа _X_. (Это не вполне верно: значения типа `%Tuple X n` можно сериализовать, только если _n_ — константа или значение, известное из одного из предшествующих полей объемлющей записи; но тогда это _n_ нигде не будет сериализовано явно).

## Специальный синтаксис для повторений

Ввиду важности описанной выше конструкции она встроена в язык TL следующим образом. В объявлении любого комбинатора допускается подструктура вида \[ _имя-поля-массива_ ":" \] \[ _nat-ident_ `*` \] "\[" _описание-поля_ ... "\]”, где _nat-ident_ — имя любого ранее встреченного поля типа # (если оно не указано явно, берётся самое последнее). Абстрактно эта подструктура эквивалентна следующему:

```
aux_type *field-descr* ... = AuxType;
*current_constructor* ... [ *array-field-name* ":" ] (%Tuple aux_type *nat-ident*)
```

Например, матрицы 10×10, векторы и произвольные матрицы можно определить так:

```
matrix {X:Type} m:# n:# a:n*[ m*[ X ] ] = Matrix X;
matrix_10x10 a:10*[ 10*[ double ]] = Matrix_10x10;
vector {X:Type} # [ X ] = Vector X;
```

Последний вариант уже встречался нам в качестве «определения» «встроенного типа» `Vector`.

Разумеется, в повторяющейся части может находиться несколько полей сколь угодно сложного вида. Более того, помимо самого _n_ в качестве счётчика повторений допускаются выражения вида _(n+const)_ и _(const+n)_, где _const_ — небольшая неотрицательная константа; это сокращённая запись для _S (S ( ... (S n) ... ))_:

```
repeat_np1 n:# a:(S n)*[ key:string value:string ] = Dictionary;
```

Для вычисления CRC32 эти выражения преобразуются к виду `(const+X)` без внутренних пробелов. Кроме того, символ `*` в этом случае не отделяется пробелами ни слева, ни справа.

## Сериализация зависимых типов

Сериализация зависимых и полиморфных типов не представляет принципиальной сложности: в нашем распоряжении есть комбинаторы ненулевой арности со значениями типа Type. Например, тип `Tuple double 10 : Type` сериализуется как `'Tuple' '%double' 10`. Отметим, что на практике в настоящее время необходимости сериализовать типы — зависимые или нет — фактически не возникает.

## Необязательные параметры комбинаторов в TL

Необязательные параметры комбинаторов в TL обязаны обладать следующими свойствами:

-   необязательные параметры обязаны быть именно первыми несколькими аргументами комбинатора;

-   значение любого необязательного параметра обязано полностью определяться типом результата комбинатора.

Например, в `cons {X:Type} hd:X tl:(list X) = list X` параметр `X` можно сделать необязательным, поскольку он находится в самом начале списка аргументов и однозначно определяется типом результата `list X`. Аналогично, в `tcons {X:Type} {n:#} hd:X tl:(%Tuple X n) = Tuple X (S n)` значения X и n полностью определяются по типу результата `Tuple X (S n)`, а значит, их можно сделать необязательными параметрами.

Обычно имеет смысл перенести все аргументы конструктора, удовлетворяющие второму условию, в начало списка, расположить их в том порядке, в каком они появляются среди параметров типа результата, и сделать необязательными. При таком подходе полная версия конструктора требуется редко — только когда нужно передать значение полиморфного или зависимого типа как значение типа Object. Во всех остальных случаях тип ожидаемого значения уже известен из контекста, а значит, все необязательные параметры могут быть восстановлены при разборе.

См. также [Необязательные параметры комбинаторов и их значения](/mtproto/TL-optargs/).
