# Сервисные сообщения

#### Ответ на RPC-запрос

Ответ на RPC-запрос обычно упакован следующим образом:

```
rpc_result#f35c6d01 req_msg_id:long result:Object = RpcResult;
```

[@term:req_msg_id] Здесь req\_msg\_id — идентификатор сообщения, отправленного другой стороной и содержащего RPC-запрос. Благодаря этому получатель понимает, что результат относится именно к этому конкретному RPC-запросу. Одновременно такой ответ служит подтверждением того, что другая сторона получила сообщение req\_msg\_id.

Заметьте, что ответ на RPC-запрос тоже нужно подтвердить. Чаще всего подтверждение совмещается с передачей следующего сообщения — к нему может быть присоединён контейнер с сервисным сообщением-подтверждением.

#### Ошибка RPC

Поле result, возвращаемое в ответ на любой RPC-запрос, может также содержать сообщение об ошибке в следующем формате:

```
rpc_error#2144ca19 error_code:int error_message:string = RpcError;
```

#### Отмена RPC-запроса

[@term:msg_id] В некоторых ситуациях клиент не хочет получать ответ на уже отправленный RPC-запрос — например, потому что ответ оказался длинным, а клиент решил обойтись без него из-за недостаточной пропускной способности канала. Просто разорвать TCP-соединение недостаточно: сервер при первой же возможности повторно отправит недоставленный ответ. Поэтому клиенту нужен способ отказаться от приёма RPC-ответа, фактически подтвердив его получение до того, как ответ действительно получен, — это успокоит сервер и не даст ему пересылать ответ заново. Однако клиент не знает msg\_id (идентификатор сообщения) RPC-ответа до того, как получит сам ответ; ему известен только req\_msg\_id, то есть msg\_id соответствующего RPC-запроса. Поэтому используется специальный запрос:

```
rpc_drop_answer#58e4a740 req_msg_id:long = RpcDropAnswer;
```

Ответ на этот запрос возвращается в виде одного из следующих сообщений, упакованных в rpc\_result и требующих подтверждения:

```
rpc_answer_unknown#5e2ad36e = RpcDropAnswer;
rpc_answer_dropped_running#cd78e586 = RpcDropAnswer;
rpc_answer_dropped#a43ad8b7 msg_id:long seq_no:int bytes:int = RpcDropAnswer;
```

[@term:seq_no] Первый вариант ответа используется, если сервер ничего не помнит о переданном req\_msg\_id (например, если ответ на него уже был дан). Второй вариант используется, если ответ был отменён во время обработки RPC-запроса (при этом сам RPC-запрос всё же был обработан полностью); в этом случае тот же самый rpc\_answer\_dropped\_running возвращается и в ответ на исходный запрос, причём оба этих ответа требуют подтверждения от клиента. Последний вариант означает, что RPC-ответ был удалён из исходящей очереди сервера, а клиенту передаются его msg\_id, seq\_no (порядковый номер сообщения) и длина в байтах.

Заметьте, что rpc\_answer\_dropped\_running и rpc\_answer\_dropped служат подтверждениями того, что сервер получил исходный запрос (тот самый, ответ на который мы хотим забыть). Кроме того, как и для любых RPC-запросов, любой ответ на rpc\_drop\_answer служит подтверждением для самого rpc\_drop\_answer.

[@term:session] Вместо rpc\_drop\_answer можно после сброса соединения создать новую сессию (`session` — контекст обмена сообщениями между клиентом и сервером), удалив старую через destroy\_session.

#### Сообщения, связанные с запросом, изменением и получением статуса других сообщений

См. [Мобильный протокол: сервисные сообщения о сообщениях](/mtproto/service_messages_about_messages/)

#### Запрос нескольких будущих солей

[@term:server_salt] Клиент в любой момент может запросить у сервера несколько (от 1 до 64) будущих серверных солей (`server_salt` — 64-битное значение, подмешиваемое в каждое сообщение) вместе с периодами их действия. Сохранив их в постоянной памяти, клиент сможет отправлять с ними сообщения и в дальнейшем, даже если сменит сессию: серверная соль привязана к авторизационному ключу, а не к конкретной сессии.

```
get_future_salts#b921bd04 num:int = FutureSalts;
future_salt#0949d9dc valid_since:int valid_until:int salt:long = FutureSalt;
future_salts#ae500895 req_msg_id:long now:int salts:vector<future_salt> = FutureSalts;
```

Клиент обязан проверить, что req\_msg\_id в ответе действительно совпадает с msg\_id запроса get\_future\_salts. Сервер возвращает не более num будущих серверных солей (может вернуть меньше). Ответ служит подтверждением запроса и сам подтверждения не требует.

#### Сообщения-пинги (PING/PONG)

```
ping#7abe77ec ping_id:long = Pong;
```

Ответ обычно возвращается в том же соединении:

```
pong#347773c5 msg_id:long ping_id:long = Pong;
```

Эти сообщения не требуют подтверждений. Сообщение pong передаётся только в ответ на ping, при этом ping может быть инициирован любой из сторон.

#### Отложенное закрытие соединения + PING

```
ping_delay_disconnect#f3427b8c ping_id:long disconnect_delay:int = Pong;
```

Работает как ping. Кроме того, получив это сообщение, сервер запускает таймер, который закроет текущее соединение через disconnect\_delay секунд, если не придёт новое сообщение того же типа, автоматически сбрасывающее все предыдущие таймеры. Если клиент, например, отправляет такие пинги раз в 60 секунд, он может задать disconnect\_delay равным 75 секундам.

#### Запрос на уничтожение сессии

[@term:auth_key_id] Используется клиентом, чтобы сообщить серверу, что тот может забыть данные другой сессии, принадлежащей тому же пользователю (то есть с тем же auth\_key\_id — идентификатором авторизационного ключа). Результат применения этого запроса к текущей сессии не определён.

```
destroy_session_ok#e22045fc session_id:long = DestroySessionRes;
destroy_session_none#62d350c9 session_id:long = DestroySessionRes;

---functions---

destroy_session#e7512126 session_id:long = DestroySessionRes;
```

#### Уведомление о создании новой сессии

Сервер уведомляет клиента о том, что для обработки клиентского сообщения пришлось создать новую сессию (с точки зрения сервера). Если после этого сервер получит в рамках той же сессии сообщение с ещё меньшим msg\_id, для этого msg\_id будет сформировано аналогичное уведомление. Для больших значений msg\_id такие уведомления не создаются.

```
new_session_created#9ec20908 first_msg_id:long unique_id:long server_salt:long = NewSession
```

Параметр unique\_id генерируется сервером при каждом (пере)создании сессии.

[@term:long poll] Клиент обязан подтвердить это уведомление. Оно нужно, например, чтобы клиент понял, что в приходящем от сервера потоке уведомлений long poll — длинного опроса, когда сервер удерживает запрос открытым до появления новых данных, — действительно образовался «пробел» (пользователь мог какое-то время не получать уведомления).

Обратите внимание, что сервер может в одностороннем порядке уничтожить (закрыть) любые существующие клиентские сессии вместе со всеми ожидающими сообщениями и уведомлениями, не отправляя никаких уведомлений. Это происходит, например, если сессия долго неактивна, а у сервера заканчивается память. Если клиент в какой-то момент решит отправить серверу новые сообщения в рамках старой сессии, уже забытой сервером, будет сформировано такое уведомление «создана новая сессия». Ожидается, что клиент корректно обработает подобные ситуации.

### Контейнеры

_Контейнеры_ — это сообщения, содержащие несколько других сообщений. Применяются, чтобы передать сразу несколько RPC-запросов и/или сервисных сообщений по протоколу HTTP или даже по TCP или UDP. Другая сторона может принять или отвергнуть контейнер только целиком.

#### Простой контейнер

Простой контейнер переносит несколько сообщений следующим образом:

```
msg_container#73f1f8dc messages:vector message = MessageContainer;
```

Здесь message — это любое сообщение вместе с его длиной и msg\_id:

```
message msg_id:long seqno:int bytes:int body:Object = Message;
```

`bytes` — количество байт в сериализованном теле сообщения. Все сообщения в контейнере обязаны иметь msg\_id меньше, чем у самого контейнера. Контейнер не требует подтверждения и не может содержать другие простые контейнеры. При повторной отправке сообщения могут быть объединены в контейнер иначе или отправлены по отдельности.

Контейнер MTProto может содержать не более `1024` сообщений. Клиентам следует группировать подтверждения, запросы статуса и запросы на повторную отправку сообщений в три отдельных сервисных сообщения — [`msgs_ack` »](/mtproto/service_messages_about_messages/#acknowledgment-of-receipt), [`msgs_state_req` »](/mtproto/service_messages_about_messages/#request-for-message-status-information) и [`msg_resend_req` »](/mtproto/service_messages_about_messages/#explicit-request-to-re-send-messages), — каждое не более чем с 8192 идентификаторами.

Пустые контейнеры также допустимы. Сервер использует их, например, чтобы ответить на HTTP-запрос, когда истёк таймаут, заданный в http\_wait, а передавать нечего.

[Пример реализации](https://github.com/tdlib/td/blob/master/td/mtproto/SessionConnection.cpp).

#### Копии сообщений

Иногда требуется повторно отправить старое сообщение, msg\_id которого уже недействителен. Тогда оно оборачивается в контейнер-копию:

```
msg_copy#e06046b2 orig_message:Message = MessageCopy;
```

После получения сообщение обрабатывается так, как если бы обёртки не было. Однако если доподлинно известно, что сообщение orig\_message.msg\_id уже было получено, новое сообщение не обрабатывается (при этом и оно само, и orig\_message.msg\_id подтверждаются). Значение orig\_message.msg\_id обязано быть меньше msg\_id контейнера.

Сейчас это не используется, поскольку старое сообщение можно обернуть в простой контейнер с тем же результатом.

#### Упакованный объект

Используется, чтобы заменить любой другой объект (точнее, его сериализацию) на сжатое (gzip) представление:

```
gzip_packed#3072cfa1 packed_data:string = Object;
```

На данный момент такая упаковка поддерживается в теле RPC-ответа (то есть в качестве result в rpc\_result), и сервер формирует её для ограниченного набора высокоуровневых запросов. Кроме того, её можно применять для передачи несервисных сообщений (то есть RPC-запросов) от клиента к серверу.

### HTTP Wait / длинный опрос

Чтобы сервер мог в дальнейшем отправлять клиенту сообщения по протоколу HTTP, используется следующий особый сервисный запрос, не требующий подтверждения (и передаваемый только через HTTP-соединение):

```
http_wait#9299359f max_delay:int wait_after:int max_wait:int = HttpWait;
```

При получении такого сообщения (или контейнера, содержащего такое сообщение) сервер либо ждёт `max_delay` миллисекунд, после чего пересылает клиенту все удерживаемые сообщения, если в сессии есть хотя бы одно сообщение в очереди (при необходимости упаковав их в контейнер, куда могут быть добавлены и подтверждения), либо ждёт появления такого сообщения не дольше `max_wait` миллисекунд. Если сообщение так и не появится, передаётся пустой контейнер.

Параметр `max_delay` задаёт максимальное число миллисекунд, которое может пройти между первым сообщением для этой сессии и передачей HTTP-ответа. Параметр `wait_after` работает так: получив самое свежее сообщение для конкретной сессии, сервер ждёт ещё `wait_after` миллисекунд на случай, если появятся новые. Если новых сообщений нет, передаётся результат — контейнер со всеми сообщениями. Если появляются новые сообщения, таймер `wait_after` сбрасывается.

При этом параметр `max_delay` имеет более высокий приоритет, чем `wait_after`, а `max_wait` — более высокий, чем `max_delay`.

Это сообщение не требует ни ответа, ни подтверждения. Если контейнер, переданный по HTTP, содержит несколько таких сообщений, поведение не определено (фактически будут использованы параметры последнего из них).

Если в контейнере нет `http_wait`, применяются значения по умолчанию: `max_delay=0` (миллисекунд), `wait_after=0` (миллисекунд) и `max_wait=25000` (миллисекунд).

Если пинг от клиента до сервера занимает много времени, может иметь смысл задать `max_delay` сопоставимым по величине со временем пинга.

## Уничтожение постоянного авторизационного ключа

```
destroy_auth_key_ok#f660e1d4 = DestroyAuthKeyRes;
destroy_auth_key_none#0a9f2259 = DestroyAuthKeyRes;
destroy_auth_key_fail#ea109b13 = DestroyAuthKeyRes;

---functions---

destroy_auth_key#d1435160 = DestroyAuthKeyRes;
```

[@term:auth_key] `destroy_auth_key` следует вызывать всякий раз, когда постоянный авторизационный ключ (`auth_key` — долговременный секрет, общий для клиента и сервера) больше не нужен, например после выхода пользователя из аккаунта.
