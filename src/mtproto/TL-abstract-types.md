# Двоичная сериализация и абстрактные типы TL

[Язык TL](TL) описывает _абстрактные_ типы данных в духе общей теории типов (точнее, теорий зависимых интуиционистских типов Мартина-Лёфа), никак не оговаривая, как значения этих типов должны быть представлены в памяти, при сохранении на диск или при передаче по сети. Статья же о [двоичной сериализации](serialize) посвящена задаче эффективной сериализации значений абстрактных типов. Для этого вводится понятие _конкретного_, или _сериализованного_, типа — множества сериализаций всех возможных значений соответствующего абстрактного типа. При этом сериализации принимают значения во множестве A\* слов в алфавите _A_, состоящем из 2^32 символов — 32-битных целых чисел.

Чтобы схема TL (то есть «программа» на языке TL) описывала сериализацию значений абстрактных типов, нужно объяснить, как конкретный тип _\[T\]_ (подмножество _\[T\]_ множества A^\*) связан с абстрактным типом _T_ (определённым в TL) и как значения абстрактного типа _T_ соответствуют значениям конкретного типа _\[T\]_ (то есть элементам _\[T\]_).

Сериализация — это построение элемента _\[T\]_ по значению абстрактного типа _T_. Обратный процесс называется десериализацией.

Значения абстрактного типа _T_ можно представлять по-разному. Обычно в памяти используются деревья или графы, а при желании — набор узлов, каждый из которых содержит некоторый тег («тип узла») и несколько указателей на другие узлы и/или значения встроенных примитивных типов вроде `int`. Однако для общих рассуждений удобно записывать значения абстрактного типа _T_ в виде строки, а именно S-выражения. Напомним, что S-выражение — это либо атом (значение примитивного типа, например целое число или строковая константа в кавычках, либо идентификатор, соответствующий встроенной или определённой функции), либо разделённый пробелами список S-выражений, заключённый в скобки. В нашем случае применяются S-выражения, первый элемент которых — идентификатор комбинатора, а остальные элементы (их количество зависит от арности комбинатора) — S-выражения, представляющие значения полей (или параметров) выбранного комбинатора. При этом типы S-выражений-аргументов и тип S-выражения результата (то есть всего выражения целиком) обязаны согласовываться.

Например, для схемы

```
pair x:int y:int = Pair;
pnil = PairList;
pcons hd:Pair tl:PairList = PairList;
```

вот примеры значений абстрактного типа `PairList`, записанных как S-выражения:

```
(pnil)
(pcons (pair 2 3) (pcons (pair 9 4) (pnil)))
```

Обычно мы пишем _E : T_ (читается «_E_ типа _T_»), когда хотим сказать, что _E_ — значение типа _T_. Будем считать, что существует встроенный тип _Type_, значения которого — сами типы. Таким образом, запись _T : Type_ означает, что _T_ — это тип.

Например, можно написать:

```
PairList : Type;
(pcons (pair 2 3) (pcons (pair 9 4) (pnil))) : PairList;
```

Преобразование абстрактного значения в сериализованное, вообще говоря, устроено просто (и при желании может быть определено по индукции):

-   Значение _n_ примитивного типа `int` сериализуется само в себя (как односимвольное слово в алфавите _A_).

-   Сериализация строковой константы (значения примитивного типа string) — это последовательность 32-битных чисел, описанная в статье [Двоичная сериализация](serialize).

-   Сериализация S-выражения `(C E1 ... Er) : T`, где `C` — комбинатор арности _r_ с типами аргументов _T1_, ..., _Tr_ и типом результата _T_ (то есть _C : T1->T2->...->Tr->T_), — это конкатенация _номера комбинатора_ _C_ (32-битного числа, однозначно определяющего комбинатор; обычно оно равно CRC-32 строки его описания на TL) и сериализаций значений _E1_ типа _T1_, _E2_ типа _T2_, ..., _Er_ типа _Tr_.

Если обозначить через _\[T\]_ конкретный тип, соответствующий абстрактному _T_, а через _\[E\]_ — элемент _\[T\]_, соответствующий значению _E_ типа _T_, то последнее правило можно записать так:

-   _\[T\]_ — это объединение по всем конструкторам типа _C_ _T1->T2->...->Tr->T_ (то есть возвращающим значение типа _T_) прямых произведений _{C} x \[T1\] x \[T2\] x ... x \[Tr\]_, где _{C}_ — одноэлементное множество, состоящее из номера комбинатора _C_. Поскольку _{C}<>{C'}_ при _C<>C'_, это задаёт взаимно однозначное отображение значений абстрактного типа _T_ (записанных с помощью S-выражений) во множество _\[T\]_.

Значения встроенных «одетых» типов `Int` и `String` сериализуются так, как если бы они были определены через `int x:int = Int;` и `string s:string = String;`, то есть сериализации целочисленной или строковой константы предшествует номер комбинатора (конструктора) `int` или `string`. В виде S-выражений это записывается как `(int 5)` или `(string "Test")`.

Однако сказанное выше не учитывает некоторых тонкостей — например, существования «голых» типов или различия между функциями (активными комбинаторами, применение которых может быть редуцировано, то есть вычислено) и конструкторами (пассивными комбинаторами, для которых правил редукции нет и быть не может). Кроме того, мы не объяснили, как быть с полиморфными типами и [необязательными параметрами комбинаторов](TL-optargs). Попробуем разобраться с этим сейчас.

### Константы, поверхностные значения и функциональные значения

Разделив комбинаторы на конструкторы и функции, мы можем ввести следующие классы выражений (значений) абстрактного типа _T_:

-   _Константные выражения_: для типов `int` и `string` это все целочисленные и строковые константы; для _T_ это все выражения вида _(C E1 ... Er) : T_, где комбинатор _C : T1->T2->...->Tr->T_ — конструктор, а _Ei : Ti_ — константные выражения типов _Ti_. Иначе говоря, константное выражение — это S-выражение, состоящее только из конструкторов и констант примитивных типов.

-   _Поверхностные выражения_ — это выражения, которые снаружи содержат функциональный комбинатор, но его аргументы при этом константные выражения подходящих типов. Иначе говоря, функциональный комбинатор встречается только на внешнем уровне. (Это не вполне точно; полное объяснение приведено ниже.)

-   _Функциональные выражения_: это выражения, которые могут содержать любые комбинаторы или константы на всех уровнях.

[@term:RPC] На практике чаще всего нужны константные значения (для хранения и передачи любых структур данных, в частности ответов на RPC-запросы — запросы к удалённой процедуре, Remote Procedure Call) и поверхностные выражения (например, в качестве RPC-запросов: тогда функциональный комбинатор внешнего уровня — это имя RPC-функции, которую мы хотим вызвать, а её параметры — аргументы вызова, то есть константные значения). В некоторых случаях полезны произвольные функциональные выражения (например, если мы хотим удалённо передать результат одного RPC-запроса в другой RPC-запрос).

Через _c(T)_ мы будем обозначать подтип абстрактного типа _T_, значениями которого являются константные выражения типа _T_. Очевидно, что у _c(T)_ примерно те же конструкторы, что и у самого _T_ (с заменой типов всех аргументов _Ti_ на _c(Ti)_), но функциональных комбинаторов у него нет.

Аналогично через _f(T)_ мы будем обозначать подтип _T_, значениями которого являются поверхностные выражения типа _T_. Очевидно, что комбинаторы _f(T)_ — это по сути функциональные комбинаторы типа _T_, но к типам их аргументов применяется _c()_: комбинатор _A : T1->...->Tr->T_ превращается в _A' : c(T1)->...->c(Tr)->f(T)_. (Уточнение этого правила см. ниже.)

Таким образом, мы определили два «функционала» _c : Type -> Type_ и _f : Type -> Type_, такие что _forall T : Type, c(T) :- T_ и _forall T : Type, f(T) :- T_ (запись _T :- T'_ означает, что _T_ содержится в _T'_, то есть что _T_ — подтип _T'_).

Мы будем считать, что _c_ и _f_ идемпотентны.

### Голые типы

[@term:naked types] С точки зрения абстрактной теории типов голые типы (naked types — типы, сериализуемые без номера комбинатора, в отличие от встроенных примитивных типов вроде `int` и `string`) не нужны. Однако на практике они чрезвычайно полезны.

Поэтому в TL вводится (частично определённый) идемпотентный унарный оператор `%`, который превращает стандартный функционал (например, выражение типа _...->Type_ или просто _Type_) в другой стандартный функционал того же типа. Если _T_ — тип, то с абстрактной теоретической точки зрения `%T` эквивалентно _c(T)_. Иначе говоря, значения `%T` — это константные значения _T_. Если _T_ — стандартное выражение арности _k_, то есть _T : S1 -> ... -> Sk -> Type_, где каждое _Si=Type_ или _#_, то по определению `%T` — стандартное выражение той же арности _k_, которое задаётся равенством _(%T) a1 ... ak = % (T a1 ... ak)_.

Когда _константное_ значение типа `%T` сериализуется, оно сначала сериализуется как значение типа _T_ (в предположении, что _T_ сам ещё не является голым типом). Затем первый символ сериализации отбрасывается (то есть имя охватывающего комбинатора). Поэтому `%T` — корректное типовое выражение только тогда, когда для `%T` существует не более одного конструктора. Выражение `%T`, где _T : S1 -> ... -> Sk -> Type_, корректно, если при _любом_ выборе параметров _a1 : S1, ... , ak : Sk_ тип _T a1 ... ak_ имеет не более одного конструктора. Использование `%` в остальных случаях некорректно.

Если при любых значениях параметров _a1 : S1, ..., ak : Sk_ для _T a1 ... ak_ существует ровно один конструктор _C_, то TL позволяет писать `C a1 ... ak` вместо `%T a1 ... ak` или `%(T a1 .. ak)`. Иначе говоря, в определённых ситуациях идентификатор `C` служит синонимом `%T`. Это допускается только в контексте типа (при указании типа поля комбинатора или его результата).

Кроме того, предполагается, что `%Int = int` и `%String = string`.

### Модификатор `!`

В TL идемпотентный оператор `!` может модифицировать любой тип, фактически разрешая поверхностные значения там, где сериализуются его константные значения. Однако если _T_ — стандартная функция вида _S1->..->Sr->Type_, то _!T_ определяется равенством `(!T) a1 ... ar = !(T a1 ... ar)` для любых _a1:S1_, ..., _ar:Sr_.

Оператор `!` допускается только в определении типов полей функциональных комбинаторов. Обычно он используется как префикс типа, например:

```
set_timeout {X:Type} timeout:int f:!X = X;
```

В этом случае определяется «обёртка» `set_timeout`. Она принимает два явных параметра: целое число `timeout` и поверхностное выражение типа `X`. Само _X : Type_ — неявный параметр (оно не указывается явно, а выводится из значений остальных параметров и их типов). Обёртка такого рода может пригодиться для изменения поведения RPC-запросов, которые представляют собой поверхностные выражения различных типов. Например, пусть у нас есть функция

```
factorial n:int = int;
```

тогда мы можем обернуть RPC-запрос `(factorial 100)` следующим образом: `(set_timeout 200 (factorial 100))`. Это выражение по-прежнему остаётся поверхностным значением типа `int`, а значит, его можно передать как RPC-запрос.

Ещё один пример — последовательная пара из двух вычислений:

```
pair {X Y : Type} x:X y:Y = Pair X Y;  // constructor
seq_pair {X Y : Type} x:!X y:!Y = Pair X Y; // functional wrapper for sequential computation
par_pair {X Y : Type} x:!X y:!Y = Pair X Y; // functional wrapper for parallel computation
```

Теперь RPC-запрос `(seq_pair (factorial 2) (factorial 3)) : Pair int int` сначала вычисляет факториал 2, затем факториал 3 и возвращает пару `(pair 2 6)`. В данном случае порядок операций не важен, поскольку они не имеют побочных эффектов. Точно так же можно было бы использовать `(par_pair (factorial 2) (factorial 3))`. Однако так бывает не всегда.

Мы можем также определить аналог операции «запятая»:

```
comma {X Y : Type} x:!X y:!Y = Y;
```

Например, эта операция могла бы сначала вычислить `x`, затем забыть результат, вычислить `y` и вернуть `y`.

Обратите внимание, что семантика обёрток `seq_pair`, `par_pair` и `comma` определяется именно там, где они реализованы (как и семантика всех прочих функциональных комбинаторов), а не их объявлением в TL.

В принципе, полиморфные обёртки вроде `set_timeout` могут применяться и, например, для «аннотирования» константных значений в ответе на RPC-запрос. Скажем, сервер может вернуть ответ на запрос вместе со временем его вычисления. Однако значение типа _!X_ обязано быть константным, поскольку именно это ожидается в качестве значения охватывающего выражения. Иначе говоря, `set_timeout 239 E` будет константным (поверхностным) значением типа _X_ тогда и только тогда, когда таково само _E_.

### Модификатор `$`

Идемпотентный модификатор `$` разрешает использовать произвольные функциональные значения подходящего типа там, где обычно допускаются только константы или поверхностные значения. Он рекурсивно преобразует все комбинаторы для всех задействованных типов, отменяя действие `%` и приписывая `$` к типам параметров и к типу результата всех комбинаторов (`$` также добавляется в начало имён преобразованных комбинаторов). Более того, встроенные типы тоже преобразуются (на завершающем этапе): `$int = Int` и `$string = String`.

Это может пригодиться для создания RPC-запроса, который выполняет «глубокое вычисление» переданного ему выражения:

```
compute {X:Type} expr:$X = X;
```

Например, теперь мы можем передать в качестве RPC-запроса следующее:

```
(compute ($factorial ($factorial (int 3)))) : int
```

(Обратите внимание, что тройка оказалась «одета»; комбинатор $factorial имеет тип $int -> $int.)

Это очень мощный инструмент. Его не обязательно реализовывать в самых простых версиях TL. В используемых сейчас схемах TL модификатор `$` не встречается.

### Подробнее о модификаторах

По сути, по крайней мере в применении к сериализации, язык TL по умолчанию подразумевает модификатор _c()_ вокруг типов параметров и результатов всех комбинаторов, а `!` и `$` его отменяют (точнее, `!` только отменяет, а `$` в некотором смысле обращает смысл на противоположный). Именно поэтому в TL нет явного модификатора `c()` и именно поэтому считается, что все функции принимают только константные значения и возвращают константные результаты, если не оговорено иное.

Может показаться, что некоторые функциональные комбинаторы могут иметь тип вида `partial_factorial n:int = $int;` и что RPC-запрос `(partial_factorial 3)` мог бы тогда неожиданно вернуть `($product (int 3) ($product (int 2) ($product (int 1) (int 1)))) : $int`…

О модификаторе `!` правильнее, по-видимому, думать так. Изначально все типы включают только константные значения (и только конструкторы). Модификатор `!` создаёт из каждого типа новый тип — его двойник. У этого нового типа нет собственных конструкторов. Функциональные комбинаторы отличаются от конструкторов тем, что перед типом их результата неявно добавляется `!`. После этого (локальный или удалённый) процесс вычисления выражения можно представить полиморфной функцией `eval : !X -> X`.
